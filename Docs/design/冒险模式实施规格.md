## 0. 一句话范围

在现有**独立 1v1 战斗**之上加一层冒险壳：Slay-the-Spire 式**逐层分岔地图** → 进入节点（战斗 / 事件 / 商店 / 休息 / Boss）→ 结算资源与卡池 → 继续前进 → Boss 通关或失败结束整局。
**不改现有单场战斗规则**（唯一例外：新增回合上限，见 §4）。

## 1. 红线（违反即返工）

| # | 约束 | 检查方式 |
|---|---|---|
| 1 | `Assets/Scripts/Core/` **不得出现 `using UnityEngine`** | asmdef `noEngineReferences` 编译期拦截；新目录 `Core/Adventure/` 必须落在同一 asmdef 内 |

| 6 | **长期存在的节点一律由构建器生成**，可重复运行且不抹掉手改资源 | 地图容器 / 资源栏 / 页面根走 `AdventureUiBuilder` |

## 3. 生命模型（最容易写错的一节）

### 3.1 三个量

| 量 | 归属 | 含义 |
|---|---|---|
| `RunMaxHp` | 冒险（局外） | 本次冒险的**正常生命上限**；休息 / 事件可改 |
| `Battle.MaxHp` | 单场战斗 | 本场可被效果削减的上限；**入场值 = RunMaxHp** |
| `Battle.InitialHp` | 单场战斗 | 入场**当前生命**；`Hp` 从它开始 |

### 3.2 入场（唯一正确写法）

```csharp
// BattleInitialHp = 局外当前生命；BattleMaxHp = 局外正常上限
CharacterDefinition player = new CharacterDefinition(
    id: "player.adventure", name: "你", kind: CharacterKind.Player,
    initialHp: run.Player.Hp,          // 3
    maxHp:     run.Player.RunMaxHp,    // 6
    minimumCardCount: cfg.MinOwnedCards,
    pool: playerPool, abilities: null);
```

- ⚠ `CharacterDefinition` 构造器断言 `initialHp > 0` 且 **`maxHp >= initialHp`**（`Core/Characters/CharacterDefinition.cs:80`）。
  适配器**必须先夹取**：`initialHp = Math.Min(Math.Max(1, hp), runMaxHp)`；冒险层在 `Hp <= 0` 时**根本不该发起战斗**，应先进 `RunLost`。
- ⚠ 不要在 Core 里把 `BattleState.InitialHp = 4` 当硬编码——它只是默认角色的取值，`PlayerState.InitialHp` 实际来自角色定义（`PlayerState.cs:34`）。

### 3.3 战斗结束导入（存活时）

```csharp
run.Player.Hp = result.PlayerFinalHp;   // 战斗内回血带来的增量一并带走
// run.Player.RunMaxHp 不变 —— 战斗内被削的上限不写回局外
```

### 3.4 上限变化的**非对称**规则（关键）

| 来源 | 上限动作 | 当前生命 |
|---|---|---|
| 战斗内效果（过载 `o` / 自燃 `p` / 沉重打击 `h`） | `Battle.MaxHp -= Δ` | 引擎既有规则 `Hp = min(Hp, MaxHp)`（`BattleEngine.cs:1372-1392`） |
| **战斗结束** | 上限**恢复**到 `RunMaxHp` | **不恢复**（明确口径） |
| 冒险事件**提高**上限 | `RunMaxHp += Δ` | **`Hp += Δ`**（Q21，clamp 到新上限） |
| 冒险事件**降低**上限 | `RunMaxHp -= Δ` | `Hp = min(Hp, RunMaxHp)` |
| 休息治疗 | 不变 | `Hp = min(Hp + 2, RunMaxHp)` |

- 冒险事件**不得**把 `RunMaxHp` 降到 1 以下（配置校验直接拒绝，不算玩法）。
- 不变量：`1 <= Hp <= RunMaxHp`；`RunMaxHp >= 1`。
- 战斗内 `Battle.MaxHp` 归 0 → 即刻死亡（既有规则，不要改成"恢复上限救活"）。

### 3.5 验收样例（直接写成断言）

设 `hp0 / max0` 入场，本场削上限 `k`、战斗内回血 `h`：

```
入场 2/6 → 本场上限削到 4（Hp 仍 2）→ 回血 +1 → 3/4 → 战斗结束玩家存活
  → 局外 = 3/6            （上限回 6，当前生命 3）
下一场入场 InitialHp = 3、MaxHp = 6
事件 +2 上限 → 局外 5/8    （当前生命同步 +2）
事件 −1 上限 → 局外 5/7
休息治疗 → 7/7
```

## 4. 回合上限（内核规则改动，唯一动到 `Core/Battle/` 的地方）

### 4.1 规则表述（进 `Docs/rules/01-规则基线.md` §2）

- 一场战斗最多 **40 个完整回合**。**1 回合 = 双方各进攻一次**（沿用规则基线 §2 的既有定义）。
- 连击的追加进攻**不额外计回合**（与推论 P2「每个半场只结算一次」同口径）。
- 第 40 回合结算完仍未分胜负 → **判 seat 0（人类玩家）失败**，结算原因 `TurnLimit`。
- 数值写成**可配置字段**（默认 40），但**必须存在上限**，不允许"无上限"。

### 4.2 实现落点

| 位置 | 改动 |
|---|---|
| `Core/Battle/BattleState.cs` | 新增 `public const int TurnLimit = 40;`（或后续改成可配字段） |
| `Core/Battle/BattleEngine.cs` | 回合推进处：`if (turn >= BattleState.TurnLimit) → 以 seat 0 为败者产出 outcome`，`Reason = "回合上限"` |
| `Core/Battle/BattleSetup.cs` → `DuelMode.TryFinish` | 不改；上限判定由引擎主动触发，不走 `IsDead` 路径 |
| `Docs/rules/01-规则基线.md` §2 | 补一条 |
| `Docs/rules/05-决策记录.md` | 新增「冒险模式定稿（2026-09-25）」条目 |

### 4.3 「双方同时出局」

用户口径：**不可能发生**。但 `DuelMode.TryFinish` 里**确实存在** `winners.Count == 0`（"双方同时出局"）分支（`BattleSetup.cs:67`）。
**处理方式**：保留该分支，`BattleResult` 映射时把"无胜者"按 `PlayerLose` 处理并**记一条告警**；不要删成 `NRE`，也不要让适配器崩。

### 4.4 连带影响（必须做，别漏）

- ⚠ **万局回归的旧结论会漂移**：加了回合上限后，同一种子的胜负与耗时都可能变。必须重跑 `dotnet run -- 10000 20261700` 并在基线上记录新结果。
- `seed 20261601`（已知冷战局，3158 回合）预计被 40 回合上限截断 → `AuraInteractionTests.AiCanFinishGamesWithAurasEnabled` 这条**已红的 EditMode 用例应转绿**。转绿后要把 `00-当前基线.md` §4 的遗留条目改掉。
- 归属：本项放 **P0 / P1**（`AdventureEngine` 的 `Outcome` 映射依赖它），**不要留到 P7**。

### 5.2 `RunState` 字段（权威）

```csharp
public sealed class RunState
{
    public string RunId;                 // "run-20260925-0001"
    public int SchemaVersion;            // 存档格式
    public int ContentVersion;           // 卡表 / 事件 / 配方内容版本
    public int ConfigVersion;            // AdventureConfig / ChapterDefinition 版本
    public int Revision;                 // 每提交一次 +1
    public int RunSeed;                  // 本次冒险基础种子
    public RunStatus Status;
    public string CurrentNodeId;
    public MapGraph Map;                 // 实际生成结果（不是模板）
    public List<string> Route;           // 已走过节点 ID
    public RunPlayerState Player;
    public PendingNode Pending;          // 当前未完成节点（含已付成本、待选候选、续接）
    public List<string> ProcessedCommandIds;  // 幂等记录，存到本次冒险终止
}

public sealed class RunPlayerState { public int Hp, RunMaxHp, Gold; public List<OwnedCardRecord> OwnedCards; }

public sealed class OwnedCardRecord
{
    public string OwnedCardId;    // 稳定持有实例 ID："oc-0007"
    public string BaseCardId;     // "a"
    public int    BaseVersion;
    public string UpgradeId;      // null / "" = 未强化
    public int    UpgradeVersion;

```

- ⚠ **`OwnedCardId` 不复用**：删掉的牌再获得 → 新实例、未强化。若用序号生成，需要一个**单调递增计数器**并进存档。

- **`EquippedCardIds` 不建**（Q1）：`CardPoolIds` 只是从 `OwnedCards` 派生的视图。

### 5.3 命令与幂等

```csharp
public enum AdventureCommandKind
{
    StartRun, EnterNode, ChooseEventOption, CompleteSelection, CancelSelection,
    SubmitBattleResult, ChooseCardReward, SkipReward, UseRestService, LeaveRest,
    BuyItem, UseShopService, LeaveShop, ConfirmNodeResult, AbandonRun
}

public sealed class AdventureCommand
{
    public string CommandId;          // 调用方生成，UUID / 单调串
    public string RunId;
    public string NodeId;             // 若适用
    public int    ExpectedRevision;
    public AdventureCommandKind Kind;
    // 以下为**扁平可选载荷**：Core 里不引入多态序列化 / 反射
    public string   OptionId;
    public string[] SelectionIds;
    public int?     ItemIndex;
    public int?     ServiceKind;
    public BattleResultInput Battle;
}
```

幂等校验顺序（**照抄，别自创**）：

1. 核对 `RunId`；
2. 若 `CommandId` 已在 `ProcessedCommandIds` 里 → **比较载荷**：一致则返回此前结果，不一致 → 返回冲突错误；
3. 校验 `ExpectedRevision`（过期 → 拒绝，资源不变）；
4. 校验当前 `Status` 允许该命令；
5. 在**独立候选状态**上执行 → 校验不变量 → 保存 → 发布为当前状态并更新 UI。

- 相同 `CommandId` 携带不同载荷 = **冲突**，不是安全重试。
- 幂等记录保存到**本次冒险终止**为止，不做跨局账户级记录。
- 磁盘保存失败 → **保留原已提交状态**与同一条待提交结果，允许重试，**不重抽随机结果**，且**不得继续推进界面**。

### 5.4 派生种子

```csharp
int seed = AdventureRng.Derive(runSeed, chapterId, nodeId, purpose, rollIndex);
// 内部只做整数混合（如 xxHash / SplitMix 的定点实现）
```

### 5.5 存档契约

```csharp
[System.Serializable] public sealed class SaveEnvelope
{
    public int SchemaVersion, ContentVersion, ConfigVersion;
    public string Checksum;          // 全部字段的稳定哈希
    public RunStateDto Run;          // 完整 RunState 的扁平副本
    public BattleInputDto PendingBattle;  // 战中退出时用；无则 null
}
```

- **文件布局**：`Application.persistentDataPath/adventure/run.sav` + `run.sav.bak` + 写盘时的 `run.sav.tmp`。
- **原子写**：`tmp` 写完 → `File.Replace(tmp, sav, bak)`；平台不支持时退化为 `Move(sav → bak)` + `Move(tmp → sav)`，并在文档里标注该平台**未实测**。
- **序列化实现选择**：Core 侧的 DTO 全部用 `[System.Serializable]`（来自 `System`，**不引入 UnityEngine**）+ `public` 字段 + `List<T>`；
  **不要用 `Dictionary`**，不要用 `Nullable<T>` 属性，`string` 用 `""` 表示"无"（约定 `"" == null`）。
  Unity 侧用 `JsonUtility` 实际读写。
- **加载顺序**：校验 `SchemaVersion` → `Checksum` → 所有 ID 可解析 → 资源范围合法（`1 <= Hp <= RunMaxHp`、`Gold >= 0`、卡池 ≥ 最小张数）→ 拓扑一致。
- **失败处理**：损坏 / 未知版本 / 内容缺失 → **明确提示 + 保留原文件**，允许显式恢复校验过的备份；**绝不静默开新局**，也不把读档失败当战败。
- 与测试卡池、设置、未来账号解锁**分开存储**。
- **`RunLost` / `RunWon` / `RunAbandoned` 之后**：槽位保留一份**只读战绩**（见第 16 节第 3 条），主菜单 `继续` 不再显示该槽位。

## 6. 地图（P3）

### 6.1 配置

```csharp
public sealed class ChapterDefinition
{
    public string Id; public int Version;
    public int LayerCount;              // 短局 = 8（含 Boss，不含起点）
    public int MinWidth = 2, MaxWidth = 4;
    public int[] ForcedLayerIndex;      // 1-based，节点层
    public NodeType[] ForcedLayerType;
    public NodeTypeWeight[] Weights;    // 普通战 50 / 事件 25 / 商店 15 / 精英 10
    public int MaxGenerateAttempts = 100;
    public int MinShopsOnMap = 1, MinEventsOnMap = 2;
}
```

短局 8 层：强制 `1 = 普通战`、`4 = 休息`、`7 = 休息`、`8 = Boss`，Boss 层宽度 1。

### 6.2 生成算法（有序，别换顺序）

1. **起点**：层 0 单节点 `start`，类型 `Start`。
2. **宽度**：层 1..7 宽度在 `[2,4]` 内取值（用派生种子 `Map` + `rollIndex`），层 8 = 1。
3. **保底通路**：先随机生成**至少一条** start → Boss 的完整路径。
4. **加分支 / 汇合**：其余节点按"就近列号"连接上下层，每个节点 `out-degree ∈ [1,2]`、`in-degree ≥ 1`；层 0 的 `out-degree` 可到 3。
5. **交叉拒绝**：同两层之间，若两条边的 `(fromColA − fromColB) * (toColA − toColB) < 0`，则不能共存（共享端点的分岔 / 汇合允许）。
6. **类型分配**：先写死强制层 → 再对剩余节点按权重归一化抽取 → 每次抽完立即检查禁连规则，违反则重抽（有界重试）。
7. **校验**（见 6.3）；不通过 → **整图重生成**，最多 `MaxGenerateAttempts`（100）次。
8. 超限 → 抛**可诊断错误**：携带 `seed`、`chapterId`、失败的**具体约束名**；**不无限重生成、不静默取消必经恢复点**。
9. 生成结果写入存档（保存**实际图**，不是模板 + 种子）。

### 6.3 校验器（每条都要）

| 约束 | 说明 |
|---|---|
| 双向可达 | 每个保留节点都从 `start` 可达，且都能抵达 Boss |
| 无孤立 / 无重复边 / 无回边 / 无死路 | 除终点外不得有出度为 0 的节点 |
| 强制层类型 | 强制层**所有**可达节点都是指定类型（保证每条路线都能经过恢复点） |
| 第 1 层禁连 | 不出现精英 / 商店 / 事件 |
| 精英 | 不早于第 3 层；**同一连线两端不能都是精英** |
| 商店 | 不能相邻两层都是商店 |
| Boss | 唯一终点，宽度 1 |
| 全图保底 | ≥1 商店、≥2 事件节点 |
| 分岔 | 每条路线至少有一次分岔决策（不要求每层都分岔） |
| 交叉 | 没有严格交叉边 |

### 6.4 节点状态与交互

- 状态：`Locked` / `Reachable` / `Current` / `Resolved`。**"当前不可达"必须与"已完成"在视觉上可区分**。
- 地图快照**只暴露节点类型**：不显示事件标题 / 正文 / 选项 / 奖励 / 隐藏抽取 ID。
- 进入节点后**不得通过返回地图另选一条路**；只能完成节点或走它的合法离开选项。
- 拖动地图**不能误触进入节点**（拖拽阈值 + 松手不提交）。
- 地图页要能看：持有卡牌、当前生命 / 上限、金币；进入战斗前明确遭遇类型。
- 高亮不能只靠颜色，**同时用形状 / 描边**。
- 已完成节点不能再次结算。

### 6.5 生成器验收

- 相同 `seed + ConfigVersion + ContentVersion` → **同图**。
- **1000 个种子**跑结构校验全绿（放**纯 C# 自测**，与 `Tools/RuleSelfTest` 同层，随回归一起跑）。
- 每个失败样本都要能打印"哪个约束、哪条边"。

### 7.3 结果复制与归属校验

```csharp
public enum BattleOutcomeKind { PlayerWin, PlayerLose, NoWinner, Aborted }
```

- 在 `OnFinished` 内、**`StopBattle` / 场景销毁之前**读取终局玩家快照与 `Outcome`，转成**只含值**的 `BattleResult`。
- 拒绝**其他冒险 / 旧节点 / 旧 `BattleAttemptId`** 的结束回调；解绑旧订阅、清理协程与 UI 动画。
- `BattleAttemptId`：**退出恢复同一场战斗时复用**，不要"继续一次就生成新的奖励身份"。
- `NoWinner` → 按 `PlayerLose` 处理 + 告警（§4.3）。

### 7.4 「重开本场」（R1 口径）

- 冒险内**保留**重开入口，但**不记录尝试次数、不做统计**。
- 重开 = 回到本场战斗开始：同敌人、同卡池、同 `BattleSeed`、同 `InitialHp`，允许重新操作。
- 实现上等价于"用存档里的战前快照重建 BattleRequest"，**不要**复用旧的 `CardInstance`。
- 战斗中退出进程 → 同样从战前快照恢复；继续游戏时提示明确："**将从本场战斗开始重新进行**"。
- 首版**不做**战斗中途状态序列化 / 决策回放。

## 8. 事件系统（P5）

### 8.1 首版范围（Q19）

首版事件只有三类效果：**商店类 / 强化卡牌 / 回血**。另有保底事件 `event.quiet`「短暂的宁静」（只有离开）。

| 项目 | 首版 | 说明 |
|---|---|---|
| `GiveGold` / `TakeGold` | ✅ | 商店类的价格与收益 |
| `Heal` / `TakeHp` | ✅ | 回血类；**付出后必须仍存活**，否则条件就不合法 |
| `AddCard` / `RemoveCard` | ✅ | 商店类与事件奖励 |
| `ChangeRunMaxHp` | ✅ | 按 Q21：提高 → 当前生命同步 +Δ；降低 → clamp |
| `UpgradeCard` | ✅ | 直接复用 P4U 的强化服务 |
| `ReplaceCard` | ❌ 删除 | 语义（是否保留强化）未定义，六个模板也没用到 |
| `SetRunFlag` | ❌ 保留字段不用 | 首版不建跨节点剧情树 |
| `StartBattle` | ⏸ **待确认**（第 16 节第 1 条） | 与 Q5「少量事件可以触发战斗」冲突，见下 |
| 遗物 / 祝福 / 消耗品 | ❌ | 首版不建系统 |

> ⚠ **范围冲突**：Q5 曾确认「少量事件可以触发战斗」，本轮说「事件先假定只有商店/强化卡牌/回血事件」。
> 规格处理：引擎**保留** `StartBattle` 算子与 `ContinuationId` 的**接口位**（不实现内容），
> 这样第 16 节一旦确认"要"，只需补内容与续接，不需要改契约。**实现者不要自行决定**。

### 8.2 定义与抽取

```csharp
public sealed class EventDefinition
{
    public string Id; public int Version;
    public EventKind Kind;              // Shop / Upgrade / Heal
    public string Title, Body, ArtId;
    public string[] Tags;
    public int Weight;
    public EventCondition[] Conditions;
    public bool Repeatable;             // 首版默认 false
    public EventOption[] Options;
}

public sealed class EventOption
{
    public string OptionId, Text, DisabledReason, ResultText;
    public EventCondition[] Conditions;
    public EventCost[] Costs;
    public EventEffect[] Effects;
    public int NextStep;                // 0 = 回地图(完成节点) / 1 = 选牌 / 2 = 选强化方向 / 3 = 进战斗(暂缓)
}
```

- 抽取：条件过滤 → 权重归一化 → 派生种子 `Event + nodeId` 抽一次；**已触发过的默认不再抽**。
- 全不可用 → `event.quiet` 保底。
- 事件的**正文与选项在进入后**才揭晓；地图只显示"事件"类型。
- 随机分支**在确认选择时只抽一次**，结果与成本、收益、事件状态**一起存档**。

### 8.3 结算规则（照抄上位文档 §9，这里只补工程落法）

1. 显示合法选项；不满足条件的显示**原因**或按配置隐藏。**提交时重新验证**，不能只靠按钮置灰。
2. 先完成必要的选牌 / 参数选择 → 构造完整结果 → 验证最终状态能成立；**确认前不得先扣钱**。
3. 临时选牌可以不立即写盘（未确认时完全不扣资源）；**重载返回该节点最初的未提交选择**。
4. 存在致死代价的选项：文案必须明确，否则条件下就不允许出现。
5. 所有选项都不合法 → 走定义好的**离开分支**，不能卡在没有按钮的页面。
6. 单次事件防重复；权重与出现条件**分离**。
7. **离开 = 完成节点**（Q19）。

### 8.4 内容交付要求

每个事件必须交全：标题、正文、选项文本、**禁用原因**、成本提示、结果文本、离开选项、验收步骤。
不允许只交机制 ID 或 `TODO 文案`。美术未齐时用已有魔法场景 + 明确占位插画，并在报告里标注**尚未通过美术验收**。

| 节点 | 规则 | 工程要点 |
|---|---|---|
| 普通战胜利 | **+15 金** → 独立奖励页：从**未持有**候选里抽 **3 张**，最多选 1，可跳过 | 候选耗尽 → 全部展示；为 0 → 明确"无可选牌"；**不能无限重抽** |

## 10. 卡牌强化（P4U）

### 10.1 数据结构

```csharp
public sealed class CardUpgradeDefinition
{
    public string Id;                  // "upgrade.c.power"
    public int Version;
    public string BaseCardId;          // "c"
    public int BaseVersion;            // 与 CardDef 内容版本绑定
    public UpgradeDirection Direction; // Power / Cooldown / Effect
    public UpgradeRecipe Recipe;
    public string Name, PreviewText;
}

public sealed class UpgradeRecipe
{
    public RecipeKind Kind;            // SetPower / SetCooldown / ReplaceEffect
    public int Delta;                  // SetPower: +1
    public int NewValue;               // SetCooldown: 1
    public int EffectIndex;            // ReplaceEffect
    public int ExpectedOriginal;       // ⚠ 预期原值校验
    public EffectDef NewEffect;
}
```

### 10.2 `CardUpgradeResolver`

- 输入：基础 `CardDef` + `CardUpgradeDefinition`；输出：**新的不可变 `CardDef`**。
- **`Id` / `Name` 不变**；`BaseCardId` 保持不变，强化信息只存在 `OwnedCardRecord` 里。
- **不让基础版与强化版作为两张牌同时进卡池**。
- 应用前必须校验：`BaseVersion` 匹配、`EffectIndex` 在范围内、**原值 == `ExpectedOriginal`**。任一不符 → **拒绝应用**（不静默改）。
- 多个效果时**不能只凭 `HandlerId`** 决定改哪一条 —— 用"基础定义版本 + 效果序号 + 预期原值"三元组。

### 10.3 玩家专属目录（隔离）

```csharp
ICardCatalog playerCatalog = PlayerCatalogBuilder.Build(run.Player.OwnedCards, baseCatalog, upgradeTable);
CardPool pool = new CardPool(baseIds, playerCatalog);      // ✅ 已支持 catalog 注入
CharacterDefinition def = new CharacterDefinition(..., pool, ...);
```

- `CardPool(IEnumerable<string> ids, ICardCatalog catalog = null)` **已存在**（`CharacterDefinition.cs:18`），直接可用。
- ⚠ `CardPool.Resolve()` **按 catalog 顺序**返回牌；玩家目录的 **ID 集合必须与 `OwnedCards` 完全一致**，否则顺序变化会改同种子的牌序。
- **敌人使用基础 / 遭遇目录**；玩家与敌人有同名卡时，强化**只影响玩家**。
- **不修改** `CardLibrary` 静态表；**不把进度写回 ScriptableObject**。
- 每场战斗**重新**从 `OwnedCards` + 配方构造目录 —— 避免 `CardInstance` 回手重置 `EffectivePower` 时丢成长。

### 10.4 规则约束

| 约束 | 内容 |
|---|---|
| 每牌一次 | `UpgradeId` 非空即拒绝再次强化与改方向 |
| 方向数 | 首版所有可强化卡 **≥2 个有实际差异的方向**；不足两条 → 列为**不可强化并说明原因**，不摆无效果占位项 |
| 力量型 | **逐牌审核**；`ForbidsAtkBuff`（沉重打击 `h`）与 `HiddenPower`（模仿 `x`）**默认不得提供**力量型 |
| 周转型 | 结果冷却 **≥1**；基础冷却 ≤1 时不显示。（⚠ 现卡表基础冷却只有 **2–4**，所以该分支**永不触发**，但代码要留着） |
| 效果型 | **只允许白名单配方**；保留触发符号、目标约束、结算阶段（除非配方明确变更）；**禁止**给所有牌叠加强效果 |
| 同名隔离 | 敌人同名牌不变；新冒险与独立战斗不带入升级 |
| 删除重获 | 按**新实例**处理（未强化）；卡牌奖励仍按 `BaseCardId` 去重 |

### 10.5 交互入口

休息点 / 商店服务 /（少量）事件**共用同一套强化流程**：
查看符合条件的目标牌 → 选牌 → 列适用方向 → **显示强化前后力量、冷却、完整效果** → 确认。
确认前可取消（回来源页，不扣资源）；确认时**重新验证**牌仍持有且未强化、方向适用、余额 / 服务次数、`Revision`，**再一次提交**。

### 10.6 卡面显示链路（⚠ 硬性前置）

强化后数值必须在这些位置**同源一致**：

| 位置 | 现状 | 处理 |
|---|---|---|
| 手牌 / 冷却迷你卡 / 长按放大 | 组成式 `CardView_Hand.prefab` | ✅ 直接用有效定义 |
| **头顶出牌 `PlayedCardView` / 飞行卡 `CardTransitView`** | ⚠ **760×1056 成品整图，数值烘焙在图上** | **必须**换成组成式或加同源数值层 |
| 选牌弹窗 / 看对方手牌 / 怪物手牌槽 | ⚠ 用 `Art/CardArt/` **插画**（无框无字） | 同上 |

**不允许**"界面显示新数值、实际按旧数值结算"，也**不允许**"实际按新数值结算、界面显示旧数值"。
若首版决定降级，必须在 UI 上**隐藏**这两处的数值，并在交接文档里写明。

## 14. 可直接落成测试的断言清单

### 14.1 生命 / 继承（§3）

1. `2/6` 入场 + 本场上限削到 4 + 回血 1 → 战斗结束存活 → 局外 **3/6**。
2. 下一场入场 `InitialHp = 3`、`MaxHp = 6`。
3. 战斗内上限被削到 0 → **即刻死亡**；**战后恢复上限不能救活**。
4. 事件 +2 上限 → 局外当前生命**同步 +2**（`5/8`）。
5. 事件 −1 上限 → `Hp = min(Hp, RunMaxHp)`。
6. 战斗内回血溢出入场值时，**增量带出**到局外。
7. 结算后不变量恒成立：`1 <= Hp <= RunMaxHp`、`RunMaxHp >= 1`。

### 14.2 回合上限（§4）

8. 构造一个双方互挡的僵局局 → 第 40 回合结束 → **seat 0 判负**，`Reason = "回合上限"`。
9. `seed 20261601` 不再触发 20000 决策护栏；`AuraInteractionTests` 转绿。
10. 连击的追加进攻**不增加**回合计数。
11. 无胜者分支被触发时，适配器按 `PlayerLose` 处理并**不崩**。

### 14.3 冒险事务（§5）

12. 重复 `CommandId` + 相同载荷 → 返回同一结果，**资源只变一次**。
13. 重复 `CommandId` + 不同载荷 → **冲突错误**，资源不变。
14. 过期 `ExpectedRevision` / 旧 `RunId` → 拒绝，资源不变。
15. 旧节点的战斗结束回调 → **被拒绝**，不发奖。
16. 保存失败 → 已提交状态不丢，同一条结果可重试，**不重抽随机**。
17. 每种 `RunStatus` 下关闭并继续 → 资源、强化、页面正确恢复。

### 14.4 地图（§6）

18. 1000 个种子：可达性、无死路、类型硬约束、**逐路径恢复点**、全图保底全绿。
19. 相同 `seed + 版本` → 同图；重载不变图。
20. 不可达 / 已完成节点 → 拒绝进入。
21. 事件进入前，地图快照**不含**标题 / 正文 / 选项。

### 14.5 奖励 / 服务（§9）

22. 3 选 1 / 候选不足 / **零候选** / 跳过，四种都有一致结果。
23. 删牌到最低 8 张后**不能再删**。
24. 满血治疗置灰；余额刚好 30 → 成功，少 1 金 → 拒绝。
25. 双击购买只成交一次；买后离开再加载**库存不复位**。

### 14.6 强化（§10）

26. 同一持有牌：第一次成功、第二次拒绝；**取消不扣费**、重复点击不重复扣费。
27. 相同 `BaseCardId` 的**敌人卡不变**；新冒险 / 独立战斗不带入升级。
28. 读档恢复、战斗开局换牌、冷却回手、模仿临时变化后**仍保有**应有的强化定义。
29. 冷却不能降为 0；`ForbidsAtkBuff` / `HiddenPower` 牌不提供力量型。
30. 删除后重新获得 → **新实例、未强化**；卡牌奖励仍按 `BaseCardId` 去重。
31. UI 前后对比、战斗快照、引擎结果**三者一致**；力量型 / 周转型 / 效果型各验一次。

### 14.7 旧功能回归

32. 角色配置、独立牌堆、发牌 / 换牌、光环、冷却、战斗结束、设置入口全部不受影响。
33. ⚠ 现有已知失败（僵局那条）**单独标注基线**，不得把任何失败都归为"历史问题"，也不得跳过它宣称全绿。
