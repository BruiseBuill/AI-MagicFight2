# 冒险事件架构：地图 / 事件 / 战斗分离

> 状态：**架构已确认，待实施**（2026-09-26）· 范围：冒险模式的**场景承载与调试方式**
>
> 上位文档：[冒险模式规划](冒险模式规划.md)（范围 / 工作包） · [冒险模式实施规格](冒险模式实施规格.md)（工程落法 / 红线 / 断言）
>
> 本文**只**回答一件事：地图、事件、战斗三者怎么分，以及"每种事件能单独进 Play 调试"怎么落地。
> 其余规则（经济、强化、存档、回合上限）**以实施规格为准**，本文不重复、不覆盖。
> ⚠ 与实施规格 §12「一个冒险入口场景 + 同一流程桥切容器」冲突时，**以本文为准**（更新更晚），并回头修正实施规格 §12。

## 1. 决定（用户口径，2026-09-26）

| # | 决定 | 落地含义 |
|---|---|---|
| A1 | **地图、事件、战斗三者分离** | 三个独立模块，各自有边界；不是"一个大流程脚本里全干" |
| A2 | **战斗本身是一种特殊事件** | 战斗节点 = `NodeType.Battle`，与商店 / 休息 / 强化**同级**，不是平级的另一种东西 |
| A3 | **每种事件能单独做出场景并调试** | 每个事件类型有**自己的场景**，可以**单独进 Play**，不依赖地图、不依赖前一节点 |
| A4 | **第一批先做商店场景** | `Shop.unity` 先跑通；其余事件类型**等做到时再定场景**，不预先拍板 |

> ⚠ A3 / A4 取代实施规格 §12 的"一个 `Adventure.unity` 切容器"。**理由**：调一个商店的经济结算，
> 不该需要先跑完一张地图；每个事件独立成场景后，"进去就能测"。

## 2. 三层职责

```text
┌──────────────────────────────────────────────────────────┐
│ 地图层  Map (MapReady)                                    │
│  · 分岔 DAG、节点类型可见、选路                           │
│  · 只决定「下一步进哪个节点」，不解释节点内部             │
│  · 场景：Adventure.unity（P3 才做，§6.3）                 │
└────────────────────────┬─────────────────────────────────┘
                         │ EnterNode(nodeId)
                         ▼
┌──────────────────────────────────────────────────────────┐
│ 事件层  Event (NodeResolving / 各节点的 Choice 状态)      │
│  · 节点类型的统一抽象：Battle / Shop / Rest / Upgrade / … │
│  · 每个类型一个 EventKind + 一个服务 + 一个场景           │
│  · 全部读 RunState 快照、提交 AdventureCommand            │
└────────────────────────┬─────────────────────────────────┘
                         │ BattleRequest
                         ▼
┌──────────────────────────────────────────────────────────┐
│ 战斗层  Battle (BattleActive)                             │
│  · 现有 1v1 战斗本体，规则不变（例外：回合上限 40）       │
│  · 场景：SampleScene（已有，保留作独立调试）              │
└──────────────────────────────────────────────────────────┘
```

**关键点**：三层之间**只通过 Core 的 `AdventureCommand` / `RunSnapshot` / `BattleRequest` / `BattleResult` 通信**。
没有一层直接调用另一层的 MonoBehaviour。所以任意一层都能被单独启动 —— 这正是 A3 成立的技术前提。

## 3. 「战斗是一种特殊事件」的确切含义

这句话很容易被读成两种意思，先把边界钉死：

| 读法 | 是否成立 | 说明 |
|---|---|---|
| 战斗节点与其他节点**同级**，都是 `NodeType` 的一种 | ✅ **成立** | 这是 A2 的意思。地图上「战斗 / 商店 / 休息 / 强化」平级 |
| 战斗要**走事件系统的那套界面**（标题 / 正文 / 选项） | ❌ **不成立** | 战斗有自己的完整表现层（`BattleCanvas`），不套事件页 |
| 「事件战斗」（Q5 / Q25 的 `StartBattle` 算子）与普通战斗节点是同一件事 | ❌ **不成立** | 前者是**事件内部触发战斗后回来**（`ContinuationId`），后者是地图节点。两者共享 `BattleRequest`，但**续接语义不同** |

所以准确的表述是：

> **`NodeType` 里包含 `Battle`；`Battle` 这一种节点的"解析方式"是切到战斗层，其余节点的解析方式是留在事件层。**

`EventKind` 只描述**留在事件层**的那些类型（Shop / Upgrade / Heal / Quiet…），
`Battle` 不在 `EventKind` 里 —— 它是一个独立节点类型，走独立的解析路径。

### 3.1 节点类型 → 解析路径

| `NodeType` | 解析路径 | 场景 | 首版 |
|---|---|---|---|
| `Start` | 无（起点不解析） | — | ✅ |
| `Battle`（普通 / 精英 / Boss） | **战斗层** | `SampleScene` 机制（复用 `BattleCanvas`） | ✅ |
| `Shop` | 事件层 · `ShopService` | **`Shop.unity`**（本文要做的） | ✅ |
| `Rest` | 事件层 · `RestService` | 待定（做到时定） | ✅ |
| `Event` | 事件层 · `EventResolver` | 待定 | ✅ |
| `Upgrade` | 事件层 · `UpgradeService`（P4U 之后） | 待定 | ⏸ 依赖 P4U |

> `NodeType.Upgrade` 与 `EventKind.Upgrade` 是否合并，**留到做强化时定**；现在不预设。

## 4. 独立场景契约（A3 的落地规则）

每个事件场景都必须能被**单独打开并运行**，因此满足下面四条：

| # | 契约 | 违反症状 |
|---|---|---|
| E1 | 场景**不依赖地图**：携带一份**入口参数**（见 §4.1）即可自行构造节点上下文 | 必须先进地图才能测商店 |
| E2 | 场景**不依赖前一节点**：不读 `Route`、不假设 `Revision` 的具体值 | 换个入口参数就报错 |
| E3 | 场景**不写真实存档**：调试默认用内存 store（`InMemoryRunSaveStore`），要写盘必须显式切换 | 调一次商店把正式存档搞坏 |
| E4 | **Core 侧一切不变**：场景只换"谁在驱动"，`ShopService` / 命令 / 幂等逻辑一行不改 | 出现第二份规则实现 |

> E4 是**红线 3（规则单点）**在场景层面的表述：独立场景只是**换了个入口**，
> 不是"为调试再写一套商店"。调试场景里的商店必须和正式流程里**逐字同一份代码**。

### 4.1 入口参数（调试用）

独立场景需要知道"我是冒险里的第几层、玩家带多少钱和什么卡"。
调试入口提供一份**可序列化字段**（Inspector 可改），在 `Awake` 里组装成 `RunState`：

```csharp
// Assets/Scripts/Unity/Adventure/Debug/ShopSceneEntry.cs（示意，实施时定名）
[Serializable] public sealed class DebugRunSeed
{
    public int    runSeed   = 20260926;   // 派生种子基
    public int    chapterId = 1;          // 章 ID
    public string nodeId    = "debug.shop";
    public int    gold      = 50;         // 走商店时默认 50（§5.4）
    public int    hp = 6, runMaxHp = 6;
    public bool   writeToDisk = false;    // E3：默认不写盘
    public List<string> ownedCards;       // 空 = 用起始牌池（§5.3）
    public AccessorySlot[] accessories;   // ⏸ 首版不建系统，字段保留不用
}
```

规则：

1. **走的是真实流程**：`StartRun(seed)` → 组装 `OwnedCards` → `EnterNode(nodeId)` → `ShopOpen`。
   不绕过 `AdventureEngine`，不直接 `new ShopService`。
2. **派生种子必须用 `AdventureRng.Derive(runSeed, chapterId, nodeId, "Shop", rollIndex)`**（红线 9），
   这样才能"同一个 `runSeed` 反复进商店，看到同一批货"。
3. `writeToDisk = false` 时注入 `InMemoryRunSaveStore`；切到 `true` 才用 `FileRunSaveStore`。
4. 场景里**不新增任何业务规则**，只有"把入口参数翻译成命令"这一段。

## 5. 商店（第一个事件场景）

> 本节是**规则口径**。用户 2026-09-26 确认；与实施规格 §9 冲突处**以本节为准**（见 §7 变更清单）。

### 5.1 货架

- 商店有 **4 个货位**：**3 张原价 + 1 张特价**。
- 原价 **20 金币**，特价 **10 金币**。
- 商品**只从「玩家尚未持有」的卡里出**（`AdventureConfig.RewardPoolIds` 减 `OwnedCards`）——
  已有过的卡**不会再卖**。
- 备货规则（用户口径）：**从未持有池无放回抽 4 张；再由派生种子随机指定其中 1 张为特价**。
  - 抽取种子用途 = `Shop`；`rollIndex` 依次 0..3。
  - 特价位的种子 = 同用途下一个 `rollIndex`（与 4 张抽取**分开**，避免"换一个特价位就换了整批货"）。
- **进入时固定库存与价格并存档**；离开再进（同一节点）**不变货**（实施规格 §9 原口径保留）。

### 5.2 卖光了

- 当「未持有池」**不足 4 张**时，**货位数不变**，缺的位置显示 **"卖光了"**。
- 判定口径（按未持有张数 `n` 分档）：

| `n` | 货架 | 特价 |
|---|---|---|
| ≥ 4 | 4 张可买 | 其中 1 张为 10 金 |
| 2–3 | `n` 张可买 + `(4 − n)` 个「卖光了」空位 | 在**实际存在的**商品里挑 1 张特价 |
| 1 | 1 张可买（**按特价 10 金**，否则 50 金买 20 金的货没有意义）+ 3 个空位 | 唯一的商品即特价 |
| 0 | 4 个空位，**全部"卖光了"** | 无 |

- ⚠ 「卖光了」是**显示状态**，不是一个可点击的"已售罄商品"。空位**不可点**、**不显示价格**。
- ⚠ 空位**不改变货位顺序**：第 4 位永远是特价位、显示特价（若存在）。
  缺货时**优先保留靠前的位**，即"卖光了"从后往前填 —— 这样特价位在缺货时不会离奇地跑到前面。

### 5.3 初始卡池（调试口径）

- 商店场景调试时，**`ownedCards` 留空 = 用起始牌池**：
  `a 暴风雪 · b 冰风暴 · c 凝固 · d 寒流 · f 滚石冲击 · k 电弧 · s 喷泉 · ag 淬火`（8 张）。
- 即开局可卖 **32 张**，**远多于 4 张 → 恒走「≥4」那一档**。
- ⚠ **所以"卖光了"用正常流程测不出来**。调试入口必须提供**收紧 `ownedCards`** 的手段
  （Inspector 里把 `ownedCards` 填成 40 张减 3 张之类），否则 §5.2 的三个分支永远不被执行。
  **这是本场景验收的必测项**（见 §8 断言 6–9）。

### 5.4 金币

- 商店独立场景的**调试默认 `gold = 50`**（用户口径）。
- ⚠ **冒险正式初始金币仍按实施规格 §17.1 的 30**，本次**不改**（见 §7）。

### 5.5 不买就走

- 始终提供**「离开」**；`LeaveShop` = **完成该节点**，回地图（Q19 口径：离开也算完成节点）。
- 商店**不能返回**（一次访问一次性；离开即结束该节点）。
- 一次访问可**买多件**（余额允许、且库存还在）。

### 5.6 首版不做

- **不卖服务**：删牌 / 强化**本次不做**（用户 2026-09-26 确认）。
  - → 与实施规格 §9「删牌 20 金 / 强化 40 金」的**服务部分作废**，见 §7。
  - → `ShopService` 的接口**预留**服务位（`ServiceKind` / `UseShopService` 命令已有），但**首版不产生**这些选项。

### 5.7 结算约束（沿用实施规格 §9）

- 购买**二次验证**：余额 ≥ 价格、卡仍未被持有、该货位仍有库存。
- 禁止负金币、重复买已售、读档刷货。
- 资源与卡牌处理**原子完成**（先验证 → 候选状态上应用 → 校验不变量 → 保存 → 发布）。

## 6. 实施方式

### 6.1 商店场景长什么样

```text
Assets/Scenes/Shop.unity                 ← 新增（A4：第一个事件场景）
├─ AdventureCanvas (Prefab)              ← 复用现有 UiKit 产物（构建器生成，红线 6）
│   ├─ ResourceBar                       金币 / 生命 / 上限（只读快照）
│   ├─ ShopRoot                          由 ShopUiBuilder 生成
│   │   ├─ Title                         "商店"
│   │   ├─ Shelf                         4 个 ShopSlotView（3 普通 + 1 特价）
│   │   └─ LeaveButton
│   └─ CardDetailLayer                   长按看牌（复用 M38 的 CardView_Hand）
└─ ShopSceneEntry (MonoBehaviour)        ← 调试入口：组装 RunState 并驱动
    └─ AdventureDriver                   ← 与正式流程同一份流程桥
```

- 货位卡面**复用 `CardView_Hand.prefab`**（红线：**别再加第二份卡面 Prefab**）。
- **长期节点**（`ShopRoot` / 货位 / 资源栏）由 `ShopUiBuilder` 生成，可重复运行、幂等（红线 6）。
- 数值全部来自 `AdventureConfig`（货位数 / 原价 / 特价 / 商品池），**不写死进引擎**（红线 8）。

### 6.2 代码落点（相对实施规格 §11 的增量）

```text
Assets/Scripts/Core/Adventure/Engine/ShopService.cs        ← 实施规格已有规划，按 §5 实现
Assets/Scripts/Core/Adventure/Content/AdventureConfig.cs   ← 增量字段：
        ShopSlotCount = 4 · ShopPriceNormal = 20 · ShopPriceDiscount = 10
Assets/Scripts/Unity/Adventure/Ui/ShopView.cs               ← 实施规格已有规划

Assets/Scripts/Unity/Editor/ShopUiBuilder.cs                ← 新增（构建器）
Assets/Scenes/Shop.unity                                    ← 新增
```

> ⚠ 上面这些**目录与文件当前都不存在**。P1 建立 `Core/Adventure/` 之后才有落点；
> 本场景的实施**依赖 P1 的契约**（`RunState` / `AdventureCommand` / `IStore`）。

### 6.3 依赖与顺序

| 依赖 | 为什么 |
|---|---|
| P1 冒险内核与契约 | 商店要读 `RunState` / 提交 `AdventureCommand`。**没有 P1 就没有商店** |
| P1 的 `AdventureConfig` | 价格与货位数来自配置 |
| `InMemoryRunSaveStore` | E3：调试默认不写盘 |

→ 所以 `Shop.unity` 是 **P4 里的第一个切片**，不是 P0 / P1 的一部分。
`Adventure.unity`（地图壳）按 P3 走，**不阻塞商店场景**。

### 6.4 调试入口至少要能改的东西

| 字段 | 默认 | 为什么要能改 |
|---|---|---|
| `gold` | 50 | 测"刚好够 / 差 1 金 / 一分钱没有" |
| `ownedCards` | 空（= 起始 8 张） | **测"卖光了"**（§5.3） |
| `runSeed` | 20260926 | 测"同一种子同一批货" |
| `writeToDisk` | `false` | 保护正式存档（E3） |

## 8. 断言清单（本场景的验收）

> 前 5 条可直接落成纯 C# 自测（`Tools/RuleSelfTest/`，与地图 1000 种子同层）；
> 6–9 需要在 `Shop.unity` 里改入口参数人工跑（或用测试入口注入 `ownedCards`）。

| # | 断言 |
|---|---|
| 1 | 未持有 ≥ 4 → 货架 4 张，且**恰好 1 张**价格为 10、其余 3 张为 20 |
| 2 | 同 `runSeed` + 同 `nodeId` → **同一批货、同一张特价**；换 `runSeed` → 换货 |
| 3 | 买掉 1 张后：余额 **−20**（原价）或 **−10**（特价），该货位变空、**不能重复买** |
| 4 | 余额刚好 20 → 买原价成功；余额 19 → **拒绝且资源不变** |
| 5 | `LeaveShop` → 节点完成；再次进入同节点 → **库存与已购状态不变**（不刷新） |
| 6 | 未持有 = 3 → 货架 **3 张可买 + 1 个「卖光了」**，且特价在其中**实际存在**的 1 张上 |
| 7 | 未持有 = 2 → 2 + 2 个空位；特价仍在**存在的**商品里 |
| 8 | 未持有 = 1 → **1 张可买且价格为 10** + 3 个空位 |
| 9 | 未持有 = 0 → **4 个"卖光了"**，无可点项，**仍能离开** |
| 10 | 卖出的卡**确实进入** `OwnedCards`；下次进商店（或重开）**不再出现** |
| 11 | 空位**不可点**、不显示价格、不被任何命令命中 |
| 12 | 调试入口 `writeToDisk = false` 时，**正式存档文件未被写入 / 未被修改** |
