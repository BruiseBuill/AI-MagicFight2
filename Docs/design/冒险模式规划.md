## 1. 目标与阅读顺序

目标是让当前独立战斗成为一次完整冒险中的节点，形成：开始冒险 → 选择路线 → 处理节点 → 获得或付出资源 → 继续前进 → Boss / 失败结算。

先读 [当前基线](../00-当前基线.md)、[规则基线](../rules/01-规则基线.md)、[架构与接口](../engineering/04-架构与接口.md)、[目录规范](../engineering/项目目录规范.md)。本文件只定义候选扩展，不覆盖这些现行来源。

完成需求确认后，将获准规则同步到 `Docs/rules/` 和规则决策记录；将落地接口同步到架构文档。本文件保留范围、依赖、任务和验收索引，避免长期出现两份互相冲突的规则。

## 5. 数据归属与系统边界

建议新增 `Assets/Scripts/Core/Adventure/` 存放纯规则；Unity 侧的流程桥和 UI 分别放到 `Assets/Scripts/Unity/Adventure/` 与既有 UI 目录下。新增资产和目录要保留 Unity `.meta`。这些均为计划路径，当前不存在。

| 数据 / 服务 | 职责 | 关键限制 |
|---|---|---|
| RunState | 单次冒险 ID、状态版本、章、当前位置、节点状态、玩家资源、持有卡牌、事件标记 | 只由冒险引擎提交修改；不保存 MonoBehaviour 或 CardInstance 引用 |

| EventDefinition | 标题正文、权重、条件、选项、结果、结果跳转 | 事件内容与战斗 BattleEvent 命名区分，避免混用 |
| AdventureEngine | 验证选路、进入节点、处理选择、返回只读快照与合法选项 | UI 不能自行扣金币、回血或判断可前往节点 |

| AdventureBattleAdapter | 将冒险状态转为 BattleSetup，将战斗结果转为冒险结果 | 不直接写 PlayerState；带运行 ID、节点 ID、战斗尝试 ID |
| RunSaveRepository | 读取、验证、原子保存、备份和版本处理 | 与测试卡池、设置、未来账号解锁分别保存 |
| AdventureDriver / Views | 连接 Core、战斗桥、存档与界面；维护订阅生命周期 | 规则依然只有一个实现；持久 UI 由构建器生成 |

根据已确认 Q1，只维护当前冒险的可抽卡池，不额外维护 `EquippedCardIds`。为容纳强化，建议权威字段升级为 `OwnedCards: {OwnedCardId, BaseCardId, UpgradeId?}[]`，`CardPoolIds` 只是派生视图，不保存第二份可独立修改的名单。每个 BaseCardId 最多一张，始终满足最少卡数；强化不创造第二张同名牌。**卡池变大只改变单场的抽取组合，不代表强度被"稀释"**（Q14：每张卡强度近乎等价），但奖励仍允许跳过，因为玩家可能单纯不想要。稳定 OwnedCardId 用于选择和存档；若某张牌被删掉后重新获得，建议作为未强化的新持有实例，不能复用已删除实例的升级记录。

## 6. 冒险流程与状态机

候选状态：`MapReady`、`NodeResolving`、`BattleActive`、`EventChoice`、`EventResult`、`RewardPending`、`RestChoice`、`ShopOpen`、`RunWon`、`RunLost`、`RunAbandoned`。选牌 / 选强化方向用当前节点下的 PendingSelection 表达，不能在取消后遗失原事件或商店上下文。

基本流程：

1. 新冒险建立独立 RunState，固定本次种子和配置版本；生成地图并写入初始存档。
2. 地图仅返回当前可到达节点。点击后验证状态版本、边是否合法、目标是否完成，再将目标标记为进行中。
3. 先保存节点内容和战前配置，再打开战斗 / 事件 / 其他节点界面。进入节点不等于完成节点。
4. 普通战斗胜利 → 复制终局结果 → 原子提交生命等变化与待选奖励 → 展示奖励；确认或跳过后完成节点。
5. 事件选择 → 验证条件与结果 → 原子提交成本、收益和结果状态 → 展示结果 → 返回地图。事件引发战斗时保存事件续接标识。
6. 失败（生命归零 / 生命上限归零 / **回合上限 40**）→ 进入 RunLost，结束整次冒险，不允许继续或回地图重打。战斗内**没有放弃 / 认输选项**（Q18）；退出进程的恢复按 Q7，但正常失败不得伪装成"退出重试"。终局存档保留**只读战绩**（Q15）；新冒险重新建立资源、起始牌池和强化状态，不从失败记录继承。
7. Boss 胜利 → 按设计完成最后奖励 / 结局 → 单章通关；多章版才有章节转移。
8. 已完成节点不能再次结算。重入同一存档应恢复当前页面与未完成选择。

所有会改变资源的指令应具备 `RunId + NodeId + ResolutionId + ExpectedRevision`；重复提交返回同一结果或明确已处理。磁盘保存失败时不得继续推进界面并默默丢失进度。

## 7. 地图生成与交互规格

按已确认 Q4，采用逐层分岔方案：

- 使用从起点到 Boss 的有向无环图；起点、终点、每层宽度和深度由章配置定义。
- 先生成至少一条完整路径，再增加分支与汇合，最后分配节点类型。节点分配需要有界重试；失败时返回可诊断错误，不能无限重生成。
- 每个保留节点都能从起点到达，也能抵达 Boss；无孤立节点、重复边、回边或除终点以外的死路。
- 若采用相邻层 / 相邻列连线，把限制写成生成器与校验器共享的明确规则。默认避免难以辨认的交叉线；不要把美术坐标当拓扑约束的唯一依据。
- 普通战、精英、事件、休息、商店、Boss 的分布和禁连规则使用配置；具体数量与“Boss 前必有休息”等保证等待生命 / 经济设计确认。
- 对“每条可行路线至少有多少次恢复”等要求，用路径性质验证；全图存在一个休息点不能证明每条路线都能经过它。
- 可见状态至少包括：已完成、当前、下一步可选、当前不可达。图例解释图标；高亮同时使用形状 / 描边等信号。
- 拖动地图不能误触进入节点。点击不可达节点可以看说明，但不推进流程。是否二次确认由交互试玩确定。
- 地图页需要能查看持有卡牌、当前生命和金币（若有），进入战斗前要明确遭遇类型。
- 建议整章节点类型从开局可见；不显示事件标题、正文、选项、奖励或隐藏抽取 ID。即使内部已固定事件，地图快照也只暴露类型。事件进入后不得通过返回地图换另一条路；只能完成事件或选择其合法离开选项。
- 拓扑建议使用相邻层连线，每层 2–4 个可用节点。生成候选边时拒绝严格交叉：同一对层之间，若两条边满足 `(fromColA-fromColB)*(toColA-toColB)<0` 则不能共存；共享端点的汇合 / 分岔允许。最终再做正反向可达性检查。参数无解时给配置错误，不静默取消必经恢复点。

## 8. 战斗桥接与跨关规则

建议保留独立战斗启动方式，同时新增显式入口，例如 `StartBattle(seed, setup)`；两个入口共享控制器创建和生命周期处理，避免复制一整套战斗逻辑。

冒险入口的责任：

- 使用 RunState 生成玩家定义 / 出战卡池，使用 EncounterDefinition 生成敌人；不能加载或覆盖测试卡池。
- 禁止冒险场景里的 BattleDriver 自动开启默认战斗；由冒险流程在 UI 订阅完成后启动。
- 已结束 / 死亡的冒险不能生成 `InitialHp <= 0` 的角色配置；在冒险层提前转入失败。
- 按已确认 Q2 把剩余生命带入下一场，并设为本场 InitialHp；“本场失血”仍从此处计算。若用户要求其他定义，单独变更规则与测试。
- 收到 OnFinished 后，在 StopBattle / 场景销毁之前读取终局玩家快照与 Outcome，转换为只含值的结果 DTO。
- 拒绝其他冒险、旧节点或旧战斗尝试的结束回调；解绑旧订阅，清理协程和 UI 动画。
- 结果提交同时记录生命变化与奖励待领取状态；“奖励已抽出”和“奖励已领取”是不同状态。

继承矩阵（已确认与工程建议分别标注）：

| 状态 | 建议 | 确认要求 |
|---|---|---|
| 当前生命 | 继承战斗结束时的剩余生命，休息 / 事件可恢复 | Q2 已确认 |
| 被战斗效果削减的最大生命 | 战斗结束且玩家存活时恢复至 RunMaxHp；不增加当前生命 | Q10a 已确认 |
| 冒险事件永久改变的正常生命上限 | 仅改变本次 RunMaxHp；**提高 Δ 时当前生命同步 +Δ**（clamp 到新上限），降低时 `Hp = min(Hp, RunMaxHp)` | Q21 已确认；事件文案要明确「增上限」与「额外治疗」是两个效果 |
| 冷却、手牌、光环、临时力量、模仿变化 | 每战重新初始化 | 工程建议，沿用单场状态生命周期 |
| 本场生成的临时卡 | 不自动变为冒险持有卡 | 工程建议，必须显式冒险奖励才可保留 |
| 漩涡等“永久移出游戏” | 仅本场，不自动删冒险卡池 | 工程建议，避免偷改冒险卡池 |
| 冒险持有牌与强化 | 在本次冒险持续；本场移除 / 模仿不得覆盖强化配方 | Q6 / Q11 已确认；实现方式见 §10.1 |
| 遗物 / 临时祝福 | 首版不建立该系统 | Q6；不把变相遗物塞进事件标记 |
| 正常失败 / 战斗内放弃 | 战斗内**没有**放弃 / 认输选项（Q18）；生命归零、上限归零或回合上限 → 结束冒险 | Q9 / Q10b / Q18 |
| 平局 / 僵局 | 回合上限 40，到限未分胜负 → **判玩家失败**；程序异常不得发奖励或伪装成玩家战败 | Q10b / Q16 已确认；见 §4 与实施规格 §4 |

生命适配必须使用三个不同概念：`RunMaxHp`（本次冒险正常上限）、`Battle.MaxHp`（本场可被削减）、`Battle.InitialHp`（本场入场当前生命）。例：冒险 6 点正常上限、3 点血入场，本场上限削到 4，结束为 2/4，返回冒险为 **2/6**，下一场以 **InitialHp=2、MaxHp=6** 入场。这里的 6/3/4/2 只是验收样例，不是首版平衡数值。

若本场上限已归零或生命归零，先按现有规则结束战斗，**不能用战后恢复上限救活玩家**。被上限夹掉的当前生命也不补回。冒险永久降低上限与战斗临时削上限必须使用不同命令 / 数据字段。

已有能力的使用次数属于单场运行实例；若需要跨战斗累计次数，必须另建冒险持久计数，不能依赖旧运行对象存活。

## 9. 事件系统规格

事件内容采用可编辑配置，转换为纯 C# 定义后进入引擎。首版用有限条件 / 效果集合，不做任意 C# / Lua 执行器，也不默认接入在线生成。

建议字段：稳定事件 ID、内容版本、标题、正文、图片引用、章节 / 标签、抽取权重、出现条件、重复策略、选项列表。

选项包含：稳定 ID、文本、前置条件、成本、结果分支、结果文本、下一步类型。条件至少考虑生命、金币、持有牌、事件标记；实际启用哪些字段取决于首版资源范围。

首版效果算子：获得 / 失去金币、治疗 / 失去生命、改变冒险正常生命上限、获得牌、移除牌、替换牌、强化牌、设置事件标记、启动战斗。遗物、祝福和消耗品不在首版。每个算子必须声明上下限、目标筛选、失败策略和结算顺序。

结算规则：

1. 显示合法选项；不满足条件的选项显示原因或按配置隐藏。提交时重新验证，不能只依赖按钮置灰。
2. 先完成必要的选牌与参数选择，构造完整结果，再验证最终状态能成立；确认前不得先扣钱。
3. 随机分支在确认选择时只抽一次；抽取结果与成本、收益、事件状态一起存档。
4. 如果事件允许付出致死生命，文案必须明确；否则条件应要求付出后仍存活。不能悄悄把致死代价裁成 1 血。
5. 所有选项都不合法时，使用定义好的离开 / 替代分支；不能卡在没有按钮的页面。
6. 触发战斗的事件保存胜 / 败 / 放弃后的续接；战斗奖励和事件奖励明确归属，禁止各发一份造成重复。
7. 单次事件防重复；无可抽事件时使用明确的保底事件。权重与出现条件分离。

“一次选择”指一次有后果的叙事决策；为该决策选一张牌、选强化方向、查看结果并确认不算多段剧情。持牌条件默认按 BaseCardId / 内容标签 / 强化状态匹配冒险卡池，不能检查已经清空的战斗手牌。首版不创建跨节点连续故事树。

事件战斗建议默认不走普通战斗奖励页，只走该事件明确配置的胜利奖励。进入前先原子保存成本、ContinuationId 和完整战斗输入；战中退出后从这个**已付成本的**战前快照恢复，不重付，也不允许退回事件另选。胜利后先导入生命和恢复正常上限，再结算事件收益；失败直接结束冒险，不再发补偿。事件的局外伤害、费用和战斗结果均只提交一次。

候选的 6 个内容模板（仅机制示例，尚非获准剧情和数值）：安全补给、金币换治疗、以生命换牌、满足持牌条件的特殊选项、随机收益与损失、接受挑战进入战斗。每份正式内容交付都需列全条件、成本、成功 / 失败文本、离开选项与验收步骤。

## 10. 卡牌奖励、商店与休息

- 起始牌池单独配置，验证最少牌数和卡牌 ID；不能直接使用当前默认全卡池作为获取新牌的成长起点。
- 卡牌候选建议过滤已有牌，支持少于目标数量的候选和主动跳过。全部拥有时使用已批准的替代资源或明确无卡可选；不能产生无限重抽。
- 按 Q1，获得卡牌直接扩充可抽卡池；奖励页不能绕过无重复和合法 ID 检查，不增加独立装备步骤。
- 删除 / 交换卡牌需验证操作后的可抽卡池；恰好最低数量时不得删除到无法启动下一场。卡牌与资源的处理应原子完成。
- 商店：进入时固定库存、价格和服务次数并存档；购买二次验证余额、持有状态与库存；禁止负金币、重复买已售商品、读档刷货。一次访问可买多件，离开后完成节点，不能返回。建议商品为未持有卡牌，服务为删牌 / 强化；不默认加入刷新、治疗或药水。
- 休息：建议治疗和强化二选一，治疗不超过 RunMaxHp；满血时治疗置灰并解释，无可强化目标时强化置灰。始终提供离开，不消耗无效服务；治疗或强化成功后本节点结束。

### 10.1 分支强化：身份、规则与生效范围

用户已确认每张持有牌只能强化一次、玩家自行选择适用方向。实现中 `UpgradeId == null` 表示未强化；非空后拒绝再次强化和改选方向。不同卡不必拥有完全相同的选项，但首版所有可强化卡至少提供两个有实际差异的有效方向。缺少两条可用配方时暂列为不可强化并说明原因，不摆一个无效果的占位选项。

建议三类配方（数值为待试玩配置）：

| 方向 | 规则作用 | 适用限制 |
|---|---|---|
| 力量型 | 构造更高基础 Power 的有效 CardDef | 不能默认允许 HiddenPower / NoAtkBuff 特殊牌；逐牌审核，不能靠改基础值绕过其设计限制 |
| 周转型 | 构造更低基础 Cooldown 的有效 CardDef | 冷却至少为 1；基础已为 1 时不显示；快速回填、冷却完成触发和无限循环需专项测试 |
| 效果型 | 按明确配方替换 / 修改指定效果或参数 | 只允许该牌白名单配方；保留触发符号、目标约束和结算阶段，除非配方明确变更；禁止任意给所有牌叠加强效果 |

`CardUpgradeDefinition` 建议字段：稳定 ID、版本、适用 BaseCardId、方向、前置条件、替换值 / 效果配方、说明与预览文案。优先显式配方，暂不开发通用运行时脚本或词缀编辑器。一个效果出现多次时不能仅凭 HandlerId 决定修改哪一条；可用基础定义版本 + 效果序号 + 预期原值校验，版本不符时拒绝应用。

`CardUpgradeResolver` 将基础定义与配方组合为新的不可变 CardDef。**BaseCardId 保持不变**，强化信息存在 OwnedCard 记录；不让基础版和强化版作为两张牌同时进入卡池。建议为冒险玩家创建专属 CardCatalog，同 ID 的定义仅在玩家目录中替换；敌方使用独立基础 / 遭遇目录。玩家与敌人拥有同名卡时，强化只影响玩家。

战前把该目录传给 `CardPool(ids, catalog)`，再构造 CharacterDefinition / BattleSetup；不修改 CardLibrary 静态表，也不把进度写回 ScriptableObject。下场再次从 OwnedCards 与配方构造目录，避免 CardInstance 回手重置 EffectivePower 时丢失成长。存档记录基础牌与配方版本；战前还要固定实际生效定义或可严格校验的内容快照，内容缺失时明确拒绝恢复，不能悄悄换成最新版。

### 10.2 强化交互与入口

建议从休息点、商店服务和少量事件共用同一强化流程：查看符合条件的持有牌 → 选牌 → 列出适用方向 → 显示强化前后力量、冷却、完整效果 → 确认。确认前可取消，返回来源页面且不扣资源；确认时重新验证牌仍持有且未强化、方向适用、余额 / 服务次数和 revision，再一次提交。

卡池查看、奖励、选牌弹窗、手牌、冷却卡、长按详情必须显示同一份有效定义。现有头顶出牌与飞行卡含有整图卡面资源，必须核对是否烘焙旧数值；若仍有，接入已有组成式卡面或添加同源数值 / 文案层，不能展示与强化后实际结算矛盾的卡面。角色头像、插画仅需沿用 ArtId。

### 10.3 强化验收重点

- 同一持有牌第一次成功、第二次拒绝；取消与重复点击均不重复扣费。
- 相同 BaseCardId 的敌人卡不变；另开新冒险和独立测试战斗不带入升级。
- 存档恢复、战斗开局换牌、冷却回手、模仿临时变化后仍保有应有的强化定义。
- 冷却不能降为 0，守护 / 双发 / 光环 / 回血削上限 / 连击等特殊效果不能套用未审核的通用增益。
- 删除后重新获得按新实例处理；卡牌奖励仍按 BaseCardId 去重。
- UI 的前后对比、战斗快照和引擎结果一致；至少验证一次力量型、周转型与效果型。

## 11. 随机性与存档

建议使用稳定算法从 `RunSeed + ChapterId + NodeId + Purpose + RollIndex` 派生子种子；不得使用跨进程不稳定的 `string.GetHashCode()`。地图、遭遇、战斗、事件、奖励分开，避免多看一次 UI 改变后续结果。

存档至少包含：格式版本、内容版本、RunId、revision、基础种子、实际地图、已选路线、当前节点 / 页面状态、玩家资源 / 卡牌、已解析遭遇、未领取奖励、事件选择 / 标记 / 续接、已处理结算 ID。

按已确认 Q7：战前存完整战斗输入与固定种子；战斗中退出恢复到战前，继续游戏提示明确“将从本场战斗开始重新进行”。种子相同不代表结果必然相同，玩家重新选择会改变结果。首版不实现战斗中途状态序列化 / 决策回放。正常认输和战败一旦提交就进入终局，不给重试按钮；退出进程允许战前重开是已确认取舍，不包装成严格防重试系统。

完整战前输入至少包含：本场起始当前生命、正常上限、双方实际有效牌定义 / 版本、能力配置、战斗规则版本、敌人 ID、固定种子、事件已付成本与续接、BattleAttemptId。奖励与商店存实际候选及购买状态，不能恢复时重新抽取。

持久化提交建议采用“验证命令 → 在独立候选状态应用 → 校验不变量 → 保存候选状态 → 发布为当前状态并更新 UI”。文件保存失败时保留原已提交状态和同一待提交结果，允许重试，不重抽随机结果。临时选牌可以不立即写盘，只要未确认时完全不扣资源；重载返回该节点最初的未提交选择。成功结算后的 EventResult 和 RewardPending 必须可恢复。

保存采用临时文件 + 原子替换 / 明确平台替代方案 + 可验证备份。加载后先校验版本、ID、资源范围、拓扑与状态一致性。未知版本、已删除内容或损坏存档应给出明确提示并保留原文件，不静默开新局。禁止通过重写正式配置资产保存进度。

## 12. UI、场景与美术工作

流程界面包括：主菜单 / 继续入口、地图、节点说明、战斗、奖励、事件、休息、商店、强化选牌 / 分支预览、胜败结算、冒险卡池查看、设置。卡池查看是只读浏览，不额外加入出战卡组编辑。

优先复用现有战斗 Prefab、CardView、字体与主题。流程承载方案由接线调研后确定：建议增加冒险入口场景，由同一流程桥切换地图与战斗容器，保留独立 SampleScene 做调试；避免复制后分叉维护整套战斗 UI。最终场景加载策略写进实现规格。

要求：

- UI 长期节点由构建器维护；构建器可重复运行，不把用户手改资源悄悄抹掉。
- 冒险设置入口不得暴露“随意改测试卡池后重开当前战斗”的正式玩法漏洞；独立战斗调试入口仍可使用。
- 多次地图 / 战斗往返后无残留射线遮挡、事件订阅、协程或动画；暂停与关闭弹窗逻辑一致。
- 地图节点图标、连线、状态样式、事件插画 / 占位资源列入美术清单；程序可用与美术验收分开报告。
- 长中文、卡牌长名、无奖励、满血、余额不足、空候选、存档错误都有明确界面状态。
- 确认目标屏幕与输入设备后再确定布局、滚动方向和触控命中面积；不能以桌面截图代替移动端验收。

## 13. 实施工作包与依赖

## 17. 试玩配置与内容生产清单

### 17.1 配置起点（建议值，未经过平衡验证）

本表用于让第一版可启动、可测，不是用户已确认的数值要求。统一存于 `AdventureConfig` / `ChapterDefinition` / 奖励及商品配置，不在 UI、引擎和测试里各写一套。优先根据失败层数、每战失血和耗时调整；不因此修改现有独立战斗默认 4/4 生命。

| 参数 | 第一轮试玩建议 | 调整依据 |
|---|---|---|
| 玩家冒险初始生命 / 上限 | 6/6 | 只影响冒险入口；连续数战的容错需实测 |
| 初始金币 | 30 | 保证首个商店通常有至少一次消费机会 |
| 初始卡池 | 8 张，最低保有 8 张 | 起始就是最低值，商店不能先删到 7 张 |
| 卡牌奖励 | 从未持有的奖励白名单中无放回抽 3 张，最多选 1，可跳过 | 合法候选不足时全部展示；为 0 时明确显示无可选牌 |
| 普通 / 精英战金币 | 15 / 30 | 普通战不默认战后回血；精英通过奖励倍率体现风险 |
| 休息治疗 | 恢复 2 点，封顶 RunMaxHp | 不做百分比取整；玩家在治疗 / 强化间权衡 |
| 商店 | 3 个未持有卡牌商品，每个 30 金币；删牌 20；强化 40 | 每件库存与每种服务各一次；可购物后离开 |
| 强化入口 | 休息免费但放弃本次治疗；商店花金币；指定事件给机会 | 不引入强化石等第二货币 |
| 强化数值基线 | 力量型 +1、周转型基础冷却 −1、效果型逐牌配置 | 不是对全部卡牌自动套用的模板 |
| 常规层节点权重 | 普通战 50、事件 25、商店 15、精英 10 | 先满足强制层和禁连规则，再按有效集合归一化抽取 |
| 常规层宽度 | 2–4 个节点 | 控制可读性；节点数量不等于玩家实际经历数量 |
| 生成失败上限 | 单次配置最多尝试 100 次 | 输出种子和失败约束；不可无限循环或悄悄放宽规则 |

普通战胜利获得金币并进入选牌；精英同样选一张牌，金币更高，但**没有专属奖励池**（Q23）。Boss 胜利直接通关，结算页只展示结果与关键数值（**不做战斗统计**），且无下一章时不要求无意义的最后选牌。全部拥有后的卡牌奖励可以跳过，不默认给额外金币；金币已是独立基础奖励，禁止重复补发。

### 17.2 地图节奏配置候选

时间含选路、事件和选牌。先实测单战耗时，再在用户选定的目标区间内调整；不能靠 UI 动画提速承诺达标。

| 节奏档 | 处理节点层数（含 Boss，不含起点） | 强制层建议 | 玩家实际战斗数量大致范围 |
|---|---|---|---|
| 短局 | 8 | 1 普通战、4 休息、7 休息、8 Boss | 2–6，取决于分支与事件战斗 |
| 标准 | 11 | 1 普通战、5 休息、10 休息、11 Boss | 2–9，需继续限制路径构成来收敛时间 |
| 长局 | 14 | 1 普通战、5 / 9 / 13 休息、14 Boss | 2–11，需更多内容避免重复 |

这些是待 Q9b 选择的模板，**首版只做「短局 8 层」**（Q9b 已定），另两档留在配置里，不作为首版同时制作三个难度。每个强制休息层的所有可达节点都为休息点，所以每条路线能经过恢复机会；玩家仍可选强化而不治疗。其它建议硬约束：第 1 层不出现精英 / 商店 / 事件；精英不早于第 3 层；连线两端不能连续为精英；不能连续商店；Boss 为唯一终点。每条路线至少有一个分岔决策，不要求每层都分岔。

整图有商店 / 事件并不等于每条路线都有。首版建议保证全图至少有一个商店、两个事件机会，允许玩家主动绕过；恢复点则采用逐路径保证。若需要控制总战斗数，给每条路径配置最少 / 最多战斗节点约束，并把事件战斗作为额外耗时记录，不冒充地图已知战斗节点。

### 17.3 起始牌池、遭遇与强化配方

建议第一轮冒险起始牌池：`a 暴风雪、b 冰风暴、c 凝固、d 寒流、f 滚石冲击、k 电弧、s 喷泉、ag 淬火`。ID 与名字已对照当前 CardLibrary；这是**供试玩的组合建议**，未证明强弱合理。保留低冷却、高力量、守护、光环与冷却操作，其他卡留作成长候选。首版不增加抽牌 / 弃牌 / 能量体系。

| 遭遇 ID 建议 | 行为差异目标 | 配置要求 |
|---|---|---|
| encounter.normal.frost | 冷却干扰与区域控制 | 从现有减速 / 重置牌选池，生命先用现有 4 点基准 |
| encounter.normal.storm | 连击与手牌换节奏 | 连击牌搭配足够防御能力，不能纯名称换皮 |
| encounter.normal.ward | 守护与光环消耗 | 与另外两套具有明显不同的卡池组成 |
| encounter.elite.overload | 更强连击 / 光环组合，风险换资源 | 可先尝试 5 点生命；固定至少 8 个合法 ID；避免只增加全部数值 |
| encounter.boss.arcane | 一章能力综合考验 | 可先尝试 6 点生命；优先使用现有能力与牌效，首版不附带多阶段 Boss 系统 |

敌人起始顺序沿用现有战斗模式，不暗加偷袭或玩家必定后手。事件战斗可以复用普通或精英遭遇，不必须增加新怪物。内容 AI 必须提交每套完整牌池、生命、奖励和为何有差异的说明；三套普通战至少各实测一次。

强化内容第一批至少覆盖上述 8 张起始卡，每张提供至少 2 个合法方向，并至少有 3 张卡能选效果型。例子：凝固可在力量 +1、冷却 2→1、减速次数 2→3 中选一；冰风暴可把防御光环 +2 改为 +3；淬火可把进攻光环 +2 改为 +3。示例均需效果触发 / 文案一致性验证，不可全局替换同类效果。高级卡分批补配方，不保证全部 40 张首版都可强化；不能强化的卡在预览中明确显示原因。

### 17.4 六个事件模板（剧情与数值草案）

标题仅进入后显示。选项的费用和确定收益必须预先可见；有随机性时明确说明概率及收益范围。每个事件都提供零代价离开选项；限制同一冒险最多触发一次，保底事件除外。

| 稳定 ID / 标题 | 可实现选项 | 条件与结果验收 |
|---|---|---|
| event.spring / 残存的泉水 | 饮用：治疗 1；装走泉边钱袋：金币 +10；离开 | 治疗与拿钱互斥；满血时治疗不可用，不先吞选择 |
| event.healer / 行脚医师 | 支付 15 金币治疗 2；离开 | 金币 ≥15 且未满血；治疗封顶，扣款和治疗一起提交 |
| event.blood_script / 血契书页 | 失去 1 当前生命，选择获得 1 张未持有牌；离开 | 当前生命 >1、合法候选非空；先选牌，确认后统一扣血加牌；取消不扣血 |
| event.frozen_gate / 冻结的门 | 持有凝固（BaseCardId=c）可打开门获得 20 金币；支付 10 金币买通守门者获得一张候选牌；离开 | 持牌条件不消耗该牌，强化后的凝固仍满足；两种路线只选一；候选不足可退出 |
| event.forge / 失控的锻炉 | 支付 10 金币强化一张牌；冒险试炉：50% 金币 +25，50% 损失 1 生命；离开 | 强化有合法目标才可选；试炉要求生命 >1；随机分支提交一次并保存，不可重载换结果 |
| event.challenge / 守卫的赌约 | 接受挑战：触发指定遭遇，胜利获 35 金币与一次选牌；离开 | 固定遭遇；胜利只发事件奖励、不叠普通奖励；战败终止冒险；重载从已进入的战斗开始 |

event.blood_script 的卡牌候选在进入事件时固定；有选择不同成本的事件也应预生成或保存候选，避免打开 / 取消子面板刷新。无事件可抽时使用 `event.quiet`“短暂的宁静”：只有离开，不产生新资源或强制损失。

内容配置交付需要逐项填写标题、正文、选项文本、禁用原因、成本提示、结果文本和战斗续接；不得只交机制 ID 或“TODO 文案”。美术未齐时可用已有魔法场景与明确占位插画，结果报告标注尚未通过美术验收。

## 18. 公共接口与存档契约清单

以下是拟新增职责，不是已存在的 API。P1 负责一次性定名并建立最小契约；后续 AI 引用实际接口，不能各造一套 RunState / Reward / OwnedCard。

| 契约 | 最低字段 / 行为 | 权威归属 |
|---|---|---|
| RunState | RunId、SchemaVersion、ContentVersion、ConfigVersion、Revision、RunSeed、Status、当前节点、实际图、路线、Player、PendingNode、已处理命令 / 结算 ID | AdventureEngine |
| RunPlayerState | Hp、RunMaxHp、Gold、OwnedCards；只在活动冒险要求生命 >0 | AdventureEngine；终局可保存 0 生命 |
| OwnedCardRecord | OwnedCardId、BaseCardId、BaseVersion、UpgradeId?、UpgradeVersion? | 同种牌唯一；持有实例 ID 单次冒险内不复用 |
| AdventureCommand | CommandId、RunId、NodeId（若适用）、ExpectedRevision、类型化载荷 | 驱动提交；Core 校验 |
| AdventureCommandResult | Accepted / Rejected、错误码与原因、结果 revision、只读快照、需要打开的页面 / 战斗请求 | Core；重复命令返回原结果，不再次触发效果 |
| PendingNode | 节点类型、固定内容 ID / 版本、处理阶段、选择上下文、已付成本、待选候选、续接数据 | 节点解析服务 |
| BattleRequest | RunId、NodeId、EncounterId、BattleAttemptId、BattleSeed、完整战斗输入、ContinuationId? | 冒险适配器生成 |
| BattleResult | 对应上述身份、Outcome、玩家终局 Hp / MaxHp、回合数与结算原因 | 战斗桥在销毁前复制；Core 验证归属 |
| MapSnapshot / NodeSnapshot | 节点 ID、类型、位置、边、可达状态、已走路线 | 隐藏事件具体内容；UI 不直接拿可变 RunState |
| ChoiceSnapshot | OptionId、可用性、不可用原因、成本 / 收益预览、选牌约束 | Core 生成；UI 可展示禁用项但不可提交成功 |
| CardPresentation | BaseCardId、OwnedCardId（局外）/ Uid（局内）、有效定义、强化名称、ArtId | 禁止以同名牌全局缓存覆盖不同拥有者的有效定义 |
| SaveEnvelope | 校验信息、完整 RunState DTO、未完成战斗输入、格式与内容版本 | RunSaveRepository；不保存委托、协程、Unity 引用 |

建议命令集：`StartRun`、`EnterNode`、`ChooseEventOption`、`CompleteSelection`、`CancelSelection`、`SubmitBattleResult`、`ChooseCardReward`、`SkipReward`、`UseRestService`、`BuyItem`、`UseShopService`、`LeaveShop`、`ConfirmNodeResult`、`AbandonRun`。取消与完成仅对当前 PendingSelection 有效。StartRun 在应用层执行新局流程，但仍校验配置并保存初始状态。

事件条件接口与效果接口分离：条件只读 Context，返回是否可用和理由；效果在候选状态上执行，不能访问 Unity、磁盘或自建随机数。事件结果包含中止 / 战斗请求 / 待选目标等结构化下一步，不让 UI 根据正文字符串判断跳转。

引擎不直接写文件。AdventureDriver 通过持久化接口完成提交，再发布快照；保存的结果与公开的 revision 必须相同。加载、重复命令、旧 BattleAttemptId 均有明确返回，不抛出后任由流程继续。BattleAttemptId 在退出恢复同一场战斗时复用，禁止继续一次就生成新的奖励身份。

幂等校验顺序建议：先核对 RunId → 若 CommandId / ResolutionId 已处理，比较载荷并返回此前结果 → 再校验 ExpectedRevision 和状态 → 验证并执行。相同命令 ID 携带不同载荷属于冲突，不能冒充安全重试；幂等记录保存至本次冒险终止，不无限增长到跨局账户。

## 19. 工作包详细交接卡

### P0 / P1：范围与冒险内核

- **输入**：第 3 节确认表、第 6 节状态机、第 18 节契约；先核对当前代码，文档中没有的接口不能假定存在。
- **建议落点**：`Core/Adventure/State/`、`Commands/`、`Content/`、`Snapshots/`；Unity 配置适配层放 `Unity/Adventure/Configuration/`。目录只在需要时创建，遵守 asmdef 与 `.meta` 规范。
- **交付**：状态、命令、错误码、不变量、独立候选状态提交；配置校验；带版本的存档 DTO 与存储接口；一份最小固定图测试数据。
- **退出条件**：非法选路 / 重复命令 / 过期版本不改变资源；完整空壳节点能完成一次并仅解锁后继；存档 DTO 可往返；未知卡牌与空卡池在新局前明确报错。
- **不要做**：在地图按钮、事件按钮或 Editor 中复制业务规则；开发通用脚本解释器。

### P2：连续战斗的纵向切片

- **输入**：P1 的权威状态和命令。
- **主要落点**：`BattleDriver.StartBattle` 的显式配置重载、AdventureBattleAdapter、AdventureDriver；Adventure 入口场景 / 容器和构建器。
- **交付**：地图占位 → 战斗 A → 结算 → 战斗 B → 返回；真实单槽存储；事件续接身份先留契约；保留 SampleScene 独立战斗。
- **退出条件**：手动完成至少两场衔接；带伤与战斗削上限按 §8 导入；战中退出后敌人 / 种子 / 入场生命相同；旧结束回调不能结算新节点；测试卡池不污染冒险。
- **关键接线**：禁止默认 Start 自动开局抢跑；先订阅再启动；终局演出结束复制结果再 StopBattle；暂停 / 设置由同一流程控制，不遗留战斗遮罩。

### P3：随机地图与导航

- **输入**：P1 地图契约、P2 节点进入入口、选定节奏档。
- **建议落点**：MapGenerator、MapValidator、MapSnapshot，Unity 地图视图和节点 / 连线 Prefab 构建器。
- **交付**：固定种子生成 / 保存实际图；拓扑和类型约束校验；滚动地图、路线高亮、图例、资源栏与卡池入口。
- **退出条件**：至少 1000 个种子检查可达性、无死路、类型硬约束和恢复机会；相同版本 / 种子同图；完成一条路线后不能回头、跳层或改选已放弃分支；事件未进入前不泄露正文。
- **范围限制**：不做自由地图探索、自动寻路角色移动或复杂场景地形。

### P4：奖励、休息与商店

- **输入**：P1 资源与卡牌身份、P2 战斗结果、§17 配置。
- **交付**：普通 / 精英奖励；奖励候选与库存持久化；卡牌获得、删牌、治疗；共享卡池查看和选牌控件；休息 / 商店节点完整关闭链。
- **退出条件**：已有牌过滤、3 选 1 / 少候选 / 零候选 / 跳过；最低 8 张不能删；满血无效治疗；刚好够钱成功、少 1 金币拒绝；双击买一次；买后继续 / 离开再加载不重置库存。
- **交接给 P4U**：统一服务提交与选牌上下文，禁止另写强化专用货币扣减逻辑。

### P4U：多方向强化

- **输入**：§10.1–10.3 和 P4 服务接口。
- **交付**：纯 C# Resolver、配方校验、玩家目录隔离、预览 UI、休息 / 商店入口和起始 8 张牌配方；补全使用旧卡面数据的展示链路。
- **退出条件**：两种方向的选择对后续战斗产生不同且正确影响；每牌一次；上述八张至少各两条配方；至少三个效果型；读档、模仿、冷却回手及同名敌人验证通过。
- **禁止捷径**：编辑静态 CardLibrary、用全局字典按 BaseCardId 覆盖双方牌、把强化当一场临时 EffectivePower 加值、将界面数值改了就宣称规则完成。

### P5：事件与内容

- **输入**：P2 战斗请求 / 续接、P4 资源和选牌、P4U 强化服务。
- **交付**：条件 / 效果注册、不可用原因、原子费用与结果、事件 UI、§17.4 六模板及保底内容、可在 Inspector 编辑的配置资产与启动前校验。
- **退出条件**：资源条件和持牌条件各验边界；确认前取消不扣费；随机结果不能重载刷新；接受挑战后退出不退还成本、不重付；胜利只领一次、失败无奖励；无候选可安全离开。
- **范围限制**：不做跨节点剧情链、NPC 好感度、遗物、在线生成或新战斗模式。

### P6：恢复与故障加固

- **输入**：P1 已建立的格式；P2–P5 实际运行状态。
- **交付**：目标平台上的临时文件 / 替换 / 备份策略；继续入口、错误反馈、版本和内容缺失处理；覆盖所有稳定页面。
- **退出条件**：在每种稳定状态关闭并继续，资源、强化和页面正确；战中回战前；奖励 / 购物 / 事件结果不重复；损坏主档可显式恢复验证过的备份；保存失败不得消失结果或继续推进。
- **异常处理**：不静默新开冒险，不把读档失败当战败；保留原损坏文件供诊断。写入平台尚未实测就不得宣称支持该平台。

### P7：完整一章与交付

- **输入**：全部前置包、目标设备与僵局规则决定。
- **交付**：章配置、五套遭遇、六事件和保底、起始牌池与配方；真实胜利 / 失败试玩记录；新手信息提示；缺陷清单。
- **退出条件**：从新局到 Boss 通关一次、普通战败一次；覆盖商店购买 / 删牌、休息两种服务、事件战斗、三类强化和战中退出继续；新冒险不继承旧资源或强化。
- **试玩记录字段**：种子、版本、所选路线（节点类型序列）、每层进出的生命与金币、得到 / 跳过 / 删除 / 强化的牌、失败所在层与原因。**不做逐场战斗统计**（回合数、单场耗时等字段全部取消）。用这些数据调整配置，不能仅凭 AI 胜率代表真人体验。
- **最终报告**：已完成范围、实际测试命令与结果、真人步骤与截图、剩余 bug、未验平台；不将现有已知失败当作所有新失败的理由。
