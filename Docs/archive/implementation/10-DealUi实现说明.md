## 2. 为什么非做不可

引擎的 `ChooseReplace` 本来就是**多选**决策：

```
MinSelect = 0 ，MaxSelect = min(替换上限, 候选数)
```

而 M8 的写法是「点一张牌 → 立刻回填那一个序号」，于是：

- 规则说的「**至多替换 3 张**」实际上**只能换 1 张**（`DoReplace` 之后 `_replaceSeat++`，这次决策就用掉了）；
- 玩家完全看不到「已经挑了几张、还能挑几张」；
- 「不替换」只有选项浮层里一颗按钮，跟「换牌」这件事在视觉上不是一个整体。

所以 M9 要做的不是「加个面板」，而是把**多选**这件事真正表达出来。

## 3. 交互设计

```
点手牌  ──► 标记 / 取消标记（上浮 + 金色辉光边框）
           ↓
        发牌台「已选 N / M」实时更新；确认按钮从灰变青
           ↓
点「确认替换」──► 把标记过的序号**一次性**回填引擎
点「不替换…」──► 回填引擎给的 Done 选项
```

四条刻意的决定：

1. **提交只发生在确认按钮上**。点牌不再直接提交 —— 这正是「一次换 3 张」的前提。
2. **按钮文案取自引擎**。`Skip` 按钮显示的是 Done 选项的 `Label`：
   开局是「不替换，开始对局」，补牌后是「保留这张，继续」。UI 里没写死这两句话，
   所以引擎换措辞（或将来加第三种场景）不需要改界面。
3. **一张没标记时「确认替换」不可点**。`MinSelect = 0` 意味着「空选 = 不替换」，
   而「不替换」已经有自己的按钮了 —— 与其让两颗按钮做同一件事，不如把确认按钮压灰。
4. **选项浮层在替换决策期间整个收起**。Done 已经由发牌台承担，
   再在浮层里列一遍就是「同一个动作两个入口」（M8 §3.4 的同一条原则）。

## 4. 节点结构与版式预算

```
TopArea
├─ PromptBar           16 起，58 高       ← 引擎的决策文案（换几张 / 什么场景）
└─ DealPanel           86 起，212 高      ← M9 新增，占用「选项浮层」那一档
   └─ Body (ContentSizeFitter 撑高 = 212)
      ├─ Backdrop / Frame                ← 都 ignoreLayout
      ├─ Counter      34  「已选 0 / 3」   ← 有标记时转高亮色
      ├─ Hint         24  「点手牌标记要替换的牌」
      ├─ ConfirmButton 54 「确认替换」      ← 主色青绿；0 张时走 disabledColor
      └─ SkipButton    48 「不替换，开始对局」
```

**位置核对**（续 `Docs/archive/implementation/09-BattleUi实现说明.md` §5 的那张表）：

| 区块 | 顶部起算 | 高度 |
|---|---|---|
| `PromptBar` | 16 | 58 |
| **`DealPanel`** | **86** | **212** |
| `PickerPanel` | 84 | ≤296 ← 替换期间收起 |
| `DetailPanel` | 底边距 10 | 自适应，顶边最高约 476 |

发牌台底边 298 ≤ 476，与详情浮层不重叠。**开局时双方冷却区都是空的**，中央本来就空着，
所以这一档给得宽；如果将来中央要放别的东西，先回来改这张表。

实测验证：`Body.rect = 420 × 212` —— `ContentSizeFitter` 算出来的高度与
`UiLayout.DealHeight` 的常量**完全吻合**，说明版式账没算错。

## 5. 接线：BattleUi 怎么分流

`Docs/archive/implementation/09-BattleUi实现说明.md` §3.1 的那条规则（「按有没有实体卡在屏幕上分类」）本批多了一个分支：

| 决策 | 谁来承担按钮 | 点手牌做什么 |
|---|---|---|
| `ChooseReplace` | **发牌台**（选项浮层收起） | 标记 / 取消标记，不提交 |
| 其余（进攻 / 防御 / 加速 / 减速 / 送冷却…） | 选项浮层（M8 原样） | 立即提交那一个选项 |

分流只发生在 `BattleUi.HandleDecision` 与 `TryPickByCard` 两个地方，各 3 行。
`DealView` 本身**一条规则逻辑都没写**：候选是哪几张、最多换几张、Done 叫什么，
全部来自 `DecisionSnapshot`（铁律第 3 条）。

降级行为：`_deal` 没接线时，`BattleUi` 回落到 M8 的老路径（点牌即提交），
界面不会空着，只是回到「一次只能换一张」的老毛病。

## 6. 本批挖出来的两个真缺陷

### 6.1 `CardView._button` 从未被赋值 —— **手牌一直点不动**

**症状**：点手牌没有任何反应。标记不出现、牌打不出去、加速/减速选不了目标。

**根因**：`UiKitBuilder` 建卡片 Prefab 时把 `_handRoot` / `_art` / `_glow` / `_dim` / `_group`
都接了，**唯独漏了 `_button`**（`grep '"_button"'` 在整个编辑器目录里零命中）。
于是 `CardView.Awake` 里那行 `_button.onClick.AddListener(...)` 从来没执行过 ——
Button 挂在节点上、EventSystem 也在，但**没人监听**。

连带后果：`SetInteractable` 也退化成空操作（`if (_button != null)` 直接跳过），
所以「不可点的牌」其实照样能点。

**为什么 M8 没发现**：M8 的验收截图是靠 `BattleDriver._autoPlay` 把整局自动打完的
（`_autoPlay` 的注释就写着「调试 / 截图用，不用手点」）。
界面上一眼也看不出异常 —— 压暗归 `_dim`、边框归 `_glow`，都不是这个字段。
**只有真的用手点一下才会露出来。**

**修法**：`UiKitBuilder` 加一个 `WireButton(view)`，在两个卡片 Prefab 建完后各调一次。

**这一条的经验**：`SetInteractable(false)` 这类「空操作也看不出错」的写法，
必须配一条**真的点一下**的验收，光看截图不算数。

### 6.2 引擎把双方补的牌混成一个池子

**症状**（修前实测）：第 2/3 回合补牌后的替换决策里，玩家拿到的是 **2 个候选**，
其中 1 张是**对手刚补的牌**。

**根因**：`DoDrawPhase` 里 `drawn` 累加了**双方**补到的牌，而 `IssueReplace` 把这个混合池
整个交给当前座位；`MaxSelect` 又用 `pool.Count` 算，会得出「能换 2 张其实只有 1 张可选」的错数。

**危害**：

- 玩家侧：多出一个**看得见却换不掉**的假选项（`DoReplace` 查归属后会 `continue`）；
- AI 侧更实：`SimpleAiAgent` 可能挑中玩家的那张牌，然后被同一个归属检查静默跳过 ——
  **这次替换白费**。

**修法**：`IssueReplace` 在非开局那一趟按 `OwnerSeat` 过滤，候选为空就跳过这一位；
`MaxSelect` 改用过滤后的候选数。符合铁律第 3 条「非法选项在生成 Options 时就过滤掉」。

**修后实测**：

| 场景 | 候选总数 | 归属本座 | 归属对手 | MaxSelect |
|---|---|---|---|---|
| 开局 | 6 | 6 | 0 | 3 |
| 补牌（修前） | 2 | 1 | **1** | — |
| 补牌（修后） | **1** | 1 | 0 | 1 |

万局自测重跑：**0 异常 / 0 违规**，胜率 51.5%（原 51.6%）、平均回合 4.58（不变）、
事件总数 1,145,670（原 1,144,928，变多是因为 AI 的替换不再被浪费）。
决策结构断言「序号连续、无重复、非空」依然全绿。

### 6.3 池化复用时「亮没亮」不能记在手牌状态里

`HandView.Update` 每帧都要重算选中态。第一版为了省掉每帧 `SetActive`，
把「当前是否亮着」记在 `HandCardState.Marked` 上做差分 —— **错了**：
卡片回收进池时 `Clear()` 会把辉光关掉，而那份记录还留着 `true`，
之后这张牌再被标记就永远不会亮。

改成把幂等下沉到 `CardView.SetSelected`（`if (_glow.activeSelf != selected)`），
`HandView` 每帧直接喊，不需要任何平行状态。
