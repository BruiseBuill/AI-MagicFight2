# 存档统一玩家卡池（存档 1 / 存档 2）

> **性质**：现行 · **最后核对** 2026-10-01

## 1. 这一批解决什么

在这之前，「玩家的卡池」在四个场景里有**四条互不相干的来路** —— 同一个玩家进不同场景
就是不同的人：

| 场景 | 来的路上是什么 |
|---|---|
| 战斗 `SampleScene` | ① `PlayerCardPoolStore`（`persistentDataPath/test-card-pools.json` 的按角色覆盖，设置面板写它）→ ② 回退 `CharacterConfig.cardPool` = `BattlePool`（`useAllCards`，45 张） |
| 商店 `Shop.unity` | `ShopSceneEntry._ownedCardIds` → `ShopPool` 资产（8 张） |
| 强化 `Upgrade.unity` | `UpgradeSceneEntry._cardIds` → `_pool` → `UpgradePool`（8 张） |
| 女巫工坊 `WitchWorkshop.unity` | `WitchSceneEntry._cardIds` → `_pool` → `UpgradePool`（8 张） |

现在**一个存档 = 一个玩家 = 一份卡池**，四个场景读同一个来源。

## 2. 口径（用户 2026-10-01 拍板）

1. **战斗默认读存档 1（测试档），Inspector 可切到存档 2**；
2. **主存档的初始卡池 = 随机 10 张**（不是沿用那 8 张起始牌池）；
3. **商店买入 / 女巫消耗都写回主存档**（原先只活在本局内存里）。

## 3. 数据结构

新增三个文件（都在 `Assets/Scripts/Unity/Configuration/`）：

```
SaveData（存档数据体 · 一个存档一份落盘）
├─ version / slotId
└─ player : PlayerData（玩家数据体）
      ├─ characterId
      └─ cardIds[]   ← 玩家的卡池（**基础 ID**）
```

| 文件 | 内容 |
|---|---|
| `SaveSlot.cs` | `enum SaveSlot { Test = 1, Main = 2 }` + `SaveSlots`（文件名 / ID / 显示名**只此一处**） |
| `SaveData.cs` | `SaveData`（存档数据体）+ `PlayerData`（玩家数据体），纯数据、无行为 |
| `SaveStore.cs` | 静态读写：`FilePathFor` / `TryLoadPlayer` / `TryLoadCardPool` / `TryLoadCardIds` / `TrySaveCardIds` / `TrySaveCardPool` / `CreateMainStartingPlayer` |

`PlayerCardPoolStore.cs` **已删除**（唯一调用点是 `BattleDriver`，已被 `SaveStore` 取代）。

落盘：`Application.persistentDataPath/save-main.json`（主存档）与 `save-test.json`（测试档）。
原子写沿用 M39 那套（临时文件 + `File.Replace`）。
⚠ 旧的 `test-card-pools.json` **不迁移**，留在原地不读。

### 3.1 两个档位的适用范围是硬约束，不是配置项

| 档位 | 谁能读 | 初始卡池 |
|---|---|---|
| **存档 1 · 测试档**（`SaveSlot.Test`） | **只有战斗**（`BattleDriver._saveSlot` 的默认值）。商店 / 强化 / 女巫的入口类**在代码层面一处都不引用它** | 没有存档时用角色自带的卡池（`BattlePool` = 45 张全表），**不落盘**；点设置面板的「保存并重开」才写文件 |
| **存档 2 · 主存档**（`SaveSlot.Main`） | **战斗（切换后）+ 商店 + 强化 + 女巫工坊** | 文件不存在时**现场随机 10 张并落盘** |

- 战斗切档：`BattleDriver` 的 Inspector 字段 `_saveSlot`（`[Header("存档（玩家卡池的来源）")]`）。
- 随机 10 张用**真随机**（种子取 `Environment.TickCount`）—— 想重抽就把 `save-main.json` 删掉再进场景。
  候选只取**内置卡表**（`CardCatalog.Builtin()`，45 张），不会抽到已经落盘的强化版。
- 10 > `WitchWorkshop.MinPoolSize`（9），所以开新档第一次进女巫工坊是**能开工**的
  —— 旧口径下起始 8 张会让女巫永远「无法进行特殊强化」。

## 4. 卡池 ID 的进出都必须过 `CardUpgrade.PreferUpgraded`

存档里**只写基础 ID**（`"a"`），而界面上拿到的是**解析后**的 ID（`"a+"`）。

- **读**：`SaveStore` 一律走 `CardUpgrade.PreferUpgraded(ids, catalog)`；
- **写**：`SaveStore.TrySaveCardIds` 一律 `CardUpgrade.BaseIdOf(id)` 归一。

为此把原先写死在 `CardPoolConfig.ResolveIds` 里的「基础版 / 强化版只留一份」逻辑
**抽到 Core 的 `CardUpgrade.PreferUpgraded`**（新增），`CardPoolConfig` 改为调用它 ——
两边各写一份的下场是「从卡池资产进场景是强化版、从存档进场景又变回基础版」，且零报错。
它同时是「强化过一次，下次进来那张牌还是 6 点」这条**永久性**的唯一闭环点。

新增 `CardUpgrade.BaseIdOf(string)`（原先只有吃 `CardDef` 的 `BaseId`），
给「按 ID 比同一张牌」用（见下）。

## 5. 四个场景各自的改动

| 场景 | 读 | 写 |
|---|---|---|
| **战斗** `BattleDriver` | `SaveStore.TryLoadCardPool(_saveSlot, character, …)` | `TrySaveCardPool(_saveSlot, pool, …)`（设置面板「保存并重开」） |
| **商店** `ShopSceneEntry` | `SaveStore.TryLoadPlayer(SaveSlot.Main, …)` | 买入一张 → `TrySaveCardIds(SaveSlot.Main, _owned, …)` |
| **强化** `UpgradeSceneEntry` | `SaveStore.TryLoadPlayer(SaveSlot.Main, …)` | **不写**（强化不改卡池 ID，见下） |
| **女巫工坊** `WitchSceneEntry` | 同上 | 确认消耗 → `TrySaveCardIds(SaveSlot.Main, _ids, …)` |

几条不那么显然的：

- **强化场景没有「写回」这一步是对的**：强化把那张牌原地变成 `"a+"`，而卡池里写的仍是
  基础 ID `"a"` —— 下次读的时候 `PreferUpgraded` 自己会换成 `"a+"`。所以「永久 +2」
  从来就不靠存档，靠的是「强化卡已落盘」这个事实。
- **商店的「未持有池」改用基础 ID 比对**（`CardUpgrade.BaseIdOf`）：否则持有 `a+` 时
  货架会再卖一次 `a`，买下去卡池里就有两张同名牌，且零报错。候选仍只取内置卡表
  （`CardLibrary.All`）—— 已经落盘的强化卡是玩家自己强出来的，不该上货架。
- **商店背包改用运行期卡目录**（`CardCatalogAsset.CreateCatalog()`）解析已持有牌 ——
  用内置卡表查不到 `"a+"`，症状是「强化过的牌在背包里凭空消失」。
- **调试覆盖时不写回**：`_ownedCardIds`（商店）/ `_cardIds` / `_pool`（强化、女巫）
  一旦被填，就走调试分支且**不读写存档**（拿调试数据覆盖真实存档是另一种事故）。
  判据是 `_loadedFromMainSave`。
- **设置面板**在状态行下面多打一行「存档：主存档（存档 2） · save-main.json」——
  战斗有两档，不显示的话「保存并重开」写的是哪一份完全看不出来。

## 6. 卡池资产的处置

`BattlePool` / `ShopPool` / `UpgradePool` **三份资产都保留、一份没删**，但：

- `BattlePool` 仍是 `DefaultPlayer.cardPool`（战斗测试档的回退），继续生效；
- `ShopPool` / `UpgradePool` **不再被运行时读取**（`CardPoolBuilder` 仍会建它们，
  `CardPoolConfig` 里两个常量也还在）。留着是为了不动构建器、也不做删除这种不可逆动作；
  真要清，走「只读审计 → 确认 → 再删」那套流程。

  唯一红线仍是那 **12 条既有噪声**（`区域类选项的 k 或匹配张数非法`，

- **`SaveStore` 定点探针**（编辑器里 `execute_code` 直调，跑完把存档还原成原样）：
  1. 主存档不存在 → `TryLoadPlayer(Main)` 落盘 10 张，二读**逐字相同**（不重抽）；

  4. 资产现状：`BattlePool` = `useAllCards`、`ShopPool` / `UpgradePool` = 各 8 张、

### 7.1 没验到的

- **战斗场景与强化场景没进 Play 跑**（女巫工坊与商店实跑过了，见 §7）；
  跨场景的那条完整链路（买一张 → 去强化看它在不在 → 去女巫消耗一张 → 回商店看背包）
  **仍未连起来走过一遍**。
- 女巫工坊的**消耗写回**只在代码路径上核对过（与上面验过的商店写回共用同一个
  `SaveStore.TrySaveCardIds`），**没有真的在 Play 里点一次确认**。
- 女巫消耗后卡池掉到 8 张以下时，`TrySaveCardIds` **不做最低张数校验**（刻意：
  存档是事实记录）。所以「消耗到 7 张」是能落盘的。
- 旧 `test-card-pools.json` 不迁移 —— 如果之前用它调过战斗卡池，那次调的结果会**丢**，
  战斗会回到 `BattlePool`（45 张）那一档。
