# 多轴强化与强化册（强化随存档走）

> **性质**：现行 · **最后核对** 2026-10-02
> **范围**：Core 的强化模型（三轴 + 配方 + 强化册）、存档 v2、四个场景的读取口径、
> 怪物侧强化、调试入口。**不动界面 Prefab**、不动万局随机对局的规则。

## 1. 这一批解决什么

用户 2026-10-02 口径：

> 卡牌包括一份最基础的卡牌的数据库，这些记录着卡牌的最基础的效果。但是在游戏当中，
> 玩家会有自己的卡池，并且会有多份备份，因此玩家的卡池应当随着存档走。如果这点已经实现了
> 的话，你则你需要考虑到强化的情况，玩家的卡牌，包括怪物的卡牌甚至可以强化。有的时候会
> 增加力量，有的时候会增加冷却，有的时候则会改变其效果词条。你需要能保证在改变了这些之后，
> 仍然能被识别到为同一张卡。……例如一张卡既可以增加力量，又可以使其冷却值减小，甚至可以
> 额外再给它加上一个，例如加速效果。但是这张牌仍然还是原来的那张，只不过给它显示加号。

拆成三件事，各自的状态：

| # | 需求 | 现状 |
|---|---|---|
| 1 | 一份**最基础**的卡牌数据库（只记最基础的效果） | **已有** —— `Core/Cards/CardLibrary.cs`，45 张，零 Unity 依赖 |
| 2 | 玩家的卡池**随存档走**，且**有多份备份**（多个档位） | **已实现**（2026-10-01「存档统一玩家卡池」）：一个存档 = 一个玩家 = 一份卡池，`SaveSlot` 两档 |
| 3 | 强化要能**改力量 / 改冷却 / 加效果词条**，多轴可叠，且**始终是同一张牌**（卡面挂 `+`） | **本批新做** |

第 3 件事在改造前是**做不到**的：上一版（2026-09-30 P5）把强化实现成
**「落盘一张新卡资产」**（`Card_a_Up.asset`），于是：

- 强化是**全局事实** —— 全工程只有一张 `a+`。「这个玩家的暴风雪强化过」与「别人的也强化过」分不开；
- **一个基础卡只能有一个强化结果** —— 反复强化是就地覆盖那份资产，所以
  「+2 力量 **且** −1 冷却 **且** 多一条光环」根本表达不出来（覆盖一次只剩最后那个结果）；
- **怪物强化无处安放** —— 怪物没有存档，而资产是全局的；
- 多一个基础卡强化就多一个 `.asset` 进版本控制（那篇文档的「遗留」里已经写明了
  「若以后不想要，改成写 `persistentDataPath` 的 JSON 即可」——本文就是那一版）。

## 2. 改造前后：载体换了，规模没换

| | 改造前（P5，2026-09-30） | 改造后（本批，2026-10-02） |
|---|---|---|
| 强化的载体 | 一份**新卡资产** `Card_a_Up.asset` | 一条**配方** `CardUpgradeRecord`（数据） |
| 强化的内容 | 只有「力量 +2」 | **三个轴**：力量 / 冷却 / 效果词条，可自由叠加 |
| 存在哪里 | `Assets/Resources/Cards/Generated/` + `CardCatalog.generatedCards` | **玩家**：`save-main.json` 的 `player.upgrades`；**怪物**：`CharacterConfig.upgrades` |
| 谁是「同一张牌」 | 卡面 ID 带 `+` 就是强化版 | 同左，但**归一化点**从「卡表里有没有 `<id>+`」变成 `CardUpgrade.BaseIdOf`（配方恒挂基础 ID） |
| 强化版什么时候产生 | 强化那一刻，落盘时就定死 | **读的时候合成**（`UpgradeBook.BuildCatalog`） |
| 一个基础卡能强化几次 | 只有一份结果（覆盖） | 配方是流水，**想叠几笔叠几笔**（受各轴上限约束） |

**唯一没变的两件事**（这是「规模没换」的意思）：

1. 卡面 ID / 卡名的口径 —— 永远只挂一个 `+`，`a` → `a+` → 还是 `a+`；
2. 读取链路上的 `CardUpgrade.PreferUpgraded` —— 强化版只要出现在**卡目录**里，
   卡池 / 商店 / 女巫工坊 / 战斗就都能拿到，**调用点一处没改**。

## 3. 数据结构

```
PlayerData（存档里的那个玩家 = 一份卡池 + 一份强化册）
├─ characterId
├─ cardIds[]        ← 卡池（**基础 ID**）
└─ upgrades[]       ← 强化配方（本批新增）
      └─ CardUpgradeRecord
            ├─ baseId                ← 永远是基础 ID（"a"，不是 "a+"）
            └─ mods[]  CardUpgradeMod
                  ├─ axis            ← Power / Cooldown / Effect
                  ├─ value           ← Power：+N；Cooldown：−N 表示加速
                  └─ trait           ← 效果轴的词条 ID（见 UpgradeTraits）
```

存档示例（`save-main.json`，v2）：

```json
{
  "version": 2,
  "slotId": "main",
  "player": {
    "characterId": "player.default",
    "cardIds": ["a", "b"],
    "upgrades": [
      { "baseId": "a", "mods": [
        { "axis": 0, "value": 2,  "trait": "" },
        { "axis": 1, "value": -1, "trait": "" },
        { "axis": 2, "value": 0,  "trait": "aura.haste" } ] }
    ]
  }
}
```

⚠ `CardUpgradeRecord` / `CardUpgradeMod` **必须能被 `JsonUtility` 序列化**：
`[Serializable]` + public 非只读字段 + 无参构造。凡是属性、只读字段、字典、接口类型，
`JsonUtility` 都**静默丢掉**（不报错，存档少一截）——
这条由自测 `UpgradeBookScenario.CheckJsonShape` 用反射钉住。

## 4. Core API

| 文件 | 内容 |
|---|---|
| `Core/Cards/CardUpgrade.cs` | 强化**唯一口径**：判定（逐轴）+ 合成（`Apply`）+ 同一性（`BaseIdOf` / `UpgradedId`）+ 目录解析（`PreferUpgraded`） |
| `Core/Cards/UpgradeTraits.cs` | **词条库**：9 条可加的效果（加速 / 快速回填 / 连击 / 守护 / 双发 / 4 种光环），各带判据与卡面文案 |
| `Core/Cards/UpgradeBook.cs` | **强化册**：`baseId → 配方` 的不可变表 + `BuildCatalog`（把配方叠到卡目录上） |

几条口径：

- **力量轴**：+2/次，**结果封顶 9**；`HiddenPower`（模仿 X）与 `ForbidsAtkBuff`（沉重打击）
  整体不生效（不是拒绝，是算术上不动 —— 界面上它们仍然「不可选」）。
- **冷却轴**：区间 `[1, 基础冷却值]`。下限 1 是 `CardDef` 的构造约束；
  上限 = 基础值，与规则里 `EffectOp.Slow` 的「减速上限 = 基础冷却值」同口径。
- **效果轴**：只能从 `UpgradeTraits` 里挑，**不引入新算子**（拼的还是 `EffectDef`，
  结算仍走 `BuiltinEffects`）。四条拒绝：未知词条 / 这张牌已经加过同一条 / 卡面本来就有这条算子 /
  力量类词条撞上「进攻力量不能增加」或「力量为 X」。
- **光环词条的触发符号跟卡面已有的光环对齐**（`UpgradeTraits.AuraTriggerFor`）。
  `AuraResolver` 把「剩余指示物」建模成「光环效果列表的**尾部 N 条**」，
  一张牌出现两种符号的光环时，消耗顺序与卡面符号会错位 —— 表现是「亮了两枚、
  效果算的是另一条」，零报错。自测里对全表 × 全词条逐个断言这条不变量。
- **空配方不产生强化版**：`Apply` 原样返回基础定义（一张没强化过的牌不该显示加号）。

## 5. 存档 v1 → v2

`SaveStore.CurrentVersion` 从 1 提到 **2**（多的就是 `player.upgrades`）。

**迁移不需要搬运代码**：旧文件里没有 `upgrades` 这个键时 `JsonUtility` 留空列表，
语义正好是「一张牌都没强化过」。`Read()` 里把这句话显式写出来了，是为了让它可查，
而不是靠默认值蒙对。**v1 的存档直接读得进来**。

另外两处一起改了：

- `TrySaveCardIds` 从「**new 一个 `PlayerData` 写下去**」改成走 `MutatePlayer`（读 → 改 → 写）。
  前者会把没被这次操作碰到的字段一起清空 —— 最典型的是**去商店买一张牌，回来发现所有强化都没了**
  （零报错）。
- `Normalize` 在**读与写都过一遍**：卡池只留非空基础 ID 且去重；强化册同一基础 ID 的多条配方
  **按顺序合并成一条**（追加式字段出现重复说明有人手改过文件，合并才是用户预期的语义）。

## 6. 四个场景怎么接

统一的写法只有一种 —— **先把强化册叠到卡目录上，再去解析卡池**：

```csharp
ICardCatalog catalog = SaveStore.WithUpgrades(baseCatalog, UpgradeBook.FromRecords(player.upgrades));
IReadOnlyList<string> ids = CardUpgrade.PreferUpgraded(player.cardIds, catalog);
```

| 场景 | 改动 |
|---|---|
| 战斗 `BattleDriver` | **一行没改**（走 `SaveStore.TryLoadCardPool`，那里内部叠册） |
| 商店 `ShopSceneEntry` | `_catalog = SaveStore.WithSavedUpgrades(SaveSlot.Main, ResolveCatalog());` |
| 女巫工坊 `WitchSceneEntry` | 同上 |
| 强化 `UpgradeSceneEntry` | 同上 + 确认时改成 `SaveStore.TryAppendUpgrade(...)` 写回主存档 |

⚠ **顺序反了会静默失效**：目录里没有 `a+` 时 `PreferUpgraded` 的判据不成立，
那张牌退回基础版（或干脆被当「不在目录里的 ID」跳过）。症状是
「强化过的牌换个场景又变回原样」，零报错。

⚠ **调试覆盖（Inspector 填了 `_cardIds` / `_pool`）仍然不写存档**：
强化只在内存里生效（`_loadedFromMainSave == false` 分支），与商店 / 女巫同口径 ——
拿调试数据覆盖真实存档是另一种事故。

## 7. 怪物也能强化

强化的载体是**配方**而不是资产，所以「挂在谁的册子上」就是一个自由选择：

| 谁 | 册子在哪 | 谁来叠 |
|---|---|---|
| 玩家 | `PlayerData.upgrades`（随存档） | `SaveStore.WithSavedUpgrades` |
| 怪物 / 精英 / Boss | `CharacterConfig.upgrades`（Inspector 可编辑） | `CharacterConfig.CreateDefinition` 里 `SaveStore.WithUpgrades(catalog, ...)` |

结算侧完全不知道区别 —— 一张牌被强化成什么样，只取决于它挂在谁的册子上。
**「怪物被强化过的牌」与「玩家被强化过的牌」走的是同一套合成规则**，
不存在的第二条路径。

## 8. 界面上「还认得出是同一张牌」

| 位置 | 表现 |
|---|---|
| 卡面 ID / 卡名 | 永远只挂一个 `+`（`暴风雪` → `暴风雪+`），叠十次也不变 `暴风雪++` |
| 卡面插画 | **沿用基础卡的 `ArtId`** —— 强化版 ID 是 `a+` 而插画表里只有 `a`，让新 ID 自己去查会得到一块纯色板（零报错） |
| 「同一张牌」的比较 | 一律走 `CardUpgrade.BaseIdOf`：商店的「未持有」、女巫的「从未强化过」、存档归一 |
| 力量 / 冷却 / 效果栏 | 合成定义上已经是**结果值**，视图层照旧直接读（`CardView` 一行没改） |

## 10. 怎么验 / 怎么用

```text
菜单：魔法乱斗/调试/强化（主存档）/
  · 力量 +2                        ← 与界面完全相同的写入口
  · 冷却 −1（加速）
  · 追加词条「光环：快速回填」      ← 用户举例里的「加速效果」
  · 追加词条「加速」
  · 打印强化册                     ← 每张牌：配方 + 合成后的 ID / 力量 / 冷却 / 光环
  · 清空强化册（复原）
```

每个菜单项都作用在**卡池里第一张还能被这个方向强化**的牌上，日志会打出
「力量 4 → 6 · 冷却 4 → 3 · 光环 0 → 1 · 卡面 a+ / 暴风雪+」。
⚠ 它动的是**真存档**（`save-main.json`）。

## 11. 遗留 / 下一步

- **多方向强化的界面**（P4U 规格 §10 那条）：`Upgrade.unity` 弹窗里加「选方向」——
  接入口已经准备好了，只需要把 `UpgradeSceneEntry.OnUpgradeConfirmed` 里构造的那一笔
  `CardUpgradeMod` 换成「玩家选出来的那一笔」。
- **强化与女巫工坊的关系**：女巫的判据里有「从未被强化过」（`CardUpgrade.IsUpgraded`），
  在配方口径下依然成立（合成定义的 ID 带 `+`）—— 但「女巫强化」与「配方」怎么合流还没定。
- **卡的「多份备份」**：现在两档（测试 / 主存档）是硬编码的 `SaveSlot` 枚举。
  用户口径里的「多份备份」若指**同一玩家的多个槽位**，需要把 `SaveSlot` 换成动态槽位表
  （`SaveData.slotId` 字段与文件名规则已经是按这个方向写的，改的时候不用动配方结构）。
