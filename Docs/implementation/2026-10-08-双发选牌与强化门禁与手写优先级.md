# 双发选牌累积 + 强化门禁 + 卡池手写优先级（2026-10-08）

> **性质**：现行实现记录 —— 三条用户口径的落地（双发防御选牌 / 已强化不能再强化 / 卡池 SO 手写优先级）
> **最后核对**：2026-10-08

用户一次提了三条，分别落在**手牌交互层**、**强化规则层**、**AI 配置层**。

---

## ① 双发防御：选牌改成「累积标记 + 拖拽成对提交」

### 用户口径（原文）

> 玩家防御双发时，修改此时的选牌逻辑，玩家点击了一张牌之后，点击另外一张牌，并不会使得上一张牌的
> 选中状态消失。只选中一张牌，然后将其拖拽进行防御，和现在一样会防御失败，然后弹回去，
> 但并不取消这张牌的选择，仍然相当于玩家只点击了一张牌。

### 旧实现为什么不行

M33（[`31-M33…`](31-M33地震条件减速与拖拽辉光与双发选两张.md) §③）把这一拍做成「**连着拖两张** ——
第一张钉住（`HandView._pinnedUid`）、第二张与它配对才提交」。两个缺口：

1. **钉住的辉光不认点击** —— 玩家点第一张（亮）再点第二张时，第一张的辉光被**单选逻辑**
   （`_selectedUid`，点第二张就把第一张换掉）清掉，看起来像「只选了一张」；
2. **失败的尝试会把已选清掉** —— 拖进来的牌凑不成一对（或只选了一张）时，已标记的那张**留不住**，
   玩家得从头再来一遍。

### 改法

| 位置 | 改动 |
|---|---|
| `HandView` | `_pinnedUid`（单个 int）→ `_picked`（集合，上限 2）+ `_accumulatePick` 开关；新增 `SetAccumulatePick` / `TogglePick` / `AddPick` / `ClearPick` / `PickCount` / `PickedUids` |
| `HandView.OnCardClicked` | 累积模式下「点一下」= 加减标记（**不再**写 `_selectedUid` —— 两条路互斥，否则「点已选的牌取消标记」会被单选辉光重新点亮） |
| `HandView.BeginDrag` | 仍然只清「点击残留」（`_selectedUid`），**不碰** `_picked` —— 这就是「拖拽失败不取消已选」的落点 |
| `HandView.Update` | `marked` 判定并入 `_picked`（双发这一拍两张都亮） |
| `BattleUi.HandleDecision` | 按 `_pendingDouble` 切 `SetAccumulatePick(...)`（与 `SetDropIntent` 同一处） |
| `BattleUi.OnHandCardClicked` | 双发 + `ChooseDefense` 时只刷提示条，**不**落 `PickCardOption`（那一拍的选项是**成对的组合**，点一张凑不出对） |
| `BattleUi.HandleDoubleDefenseDrop` | 重写：拖进来的那张**并进集合** → 不满两张什么都不提交（牌自己滑回手牌）→ 刚好两张才去 `_cardOptions` 里**找**这一对 → 找到就 `Pick(pair)`，找不到只提示、**已选一个都不取消** |
| `BattleUi._pairFirstUid` | 删除（集合接管），`ClearPairPick` 改成 `_hand.ClearPick()` |

交互结果：

- 点一张亮一张、**再点第二张第一张仍然亮**；再点已标记的那张 = 取消它；
- 拖一张进判定区 = 把它并进已选；**两张能凑成引擎给过的合法组合就提交**；
- 只标了 1 张就拖 → 不提交、牌弹回、**标记保留**（等于「还是只点了一张」）；
- 满两张后再拖第三张 → **顶掉最早那张**（玩家刚拖的那张永远在集合里）；
- 集合里的牌换手牌后消失 → `Bind` 时按 uid 剪掉，不留找不到的「名额」。

⚠ 这一拍**仍然不判断任何规则**：能不能配成一对只有引擎给的 `Options` 说了算
（`FindDefensePair` 只是在里面**找**，铁律 3）。

## ② 任何一种强化后的牌，都不能再次强化

### 用户口径（原文）

> 进行任何一种强化后的牌，都不能再次进行强化。

### 改动

唯一落点 = `Core/Cards/CardUpgrade.cs`，**四根轴各加一道门**（都用既有的
`CardUpgrade.IsUpgraded`，不新增状态）：

| 方法 | 覆盖的轴 |
|---|---|
| `CanUpgradePower`（`CanUpgrade` 就是它） | 力量 +2（石台 `AltarRite` 走这条） |
| `CanUpgradeCooldown` | 冷却（加速 / 减速方向） |
| `CanApplyEffect` | 追加词条 |
| `CanTransfer` | 女巫工坊的「搬一条效果过来」 |
| `CanApply` | 上面四个的**分发点**（界面 / AI 走的就是它，自动继承） |

给玩家看的原因是常量 `CardUpgrade.AlreadyUpgradedReason` = **「已经是强化过的牌，不能再次强化」**
（界面直接把它写在压暗的卡面上，见 `UpgradeSceneEntry` / `WitchSceneEntry`）。

### 两条刻意不动的口径

1. **祭品资格不变**：已经强化过的牌**照样能当祭品**（`AltarRite.CanBeSacrifice` /
   `WitchWorkshop.CanBeSacrifice` 都没碰）—— 祭品只是被拿走，它身上没有任何东西要「单独成立」。
2. **强化版仍然按 `+` 后缀识别**：本规则判的是 **ID 带不带 `+`**，与「叠了几笔、叠的是哪个轴」无关
   （后缀本来就不叠加，一个 `a+` 可以同时叠了力量与词条）。

⚠ 连带效果：一处卡池里同时有 `a` 与 `a+` 时，`PreferUpgraded` 让玩家看到的是 `a+`，
所以「玩家手里这张牌能不能再强化」在**界面上**与**规则上是同一件事**（同一次判定）。

## ③ 卡池 SO 上的「手写出牌优先级」

### 用户口径（原文）

> 应当格外设置一个选项，开启选项之后，我可以自己在编辑器当中写入不同卡的使用优先级，
> 而不会被自动计算给覆盖掉。此选项直接放在卡池的 SO 当中就行了。
>
> 补充：与代码中的档位**同方向**（数值越小越先打）；进攻逻辑仍按代码里那套处理；
> **一旦启用了手动，代码当中就不能再对卡的优先级再赋值**。

### 落点

| 位置 | 新增物 |
|---|---|
| `Core/Ai/CardPriorityTable.cs`（新） | `CardPriorityEntry{cardId, priority}` + `CardPriorityTable`（按**基础 ID** 折叠、不认识的 ID 忽略、查不到 → `UnlistedTier = 1000000`） |
| `App/CardPoolConfig` | `useManualPriority` 开关 + `priorities` 表 + `BuildPriorityTable()`（没勾 → `null` = 不插手）+ `PriorityIdsOutsidePool()`（编辑器核对用） |
| `Core/HeuristicAgent` | `ManualPriorities` 属性 + **`PriorityFor(...)`**（唯一的取档位入口） |
| `Core/CharacterDefinition` | `CardPriorities`（与 `AiProfile` 同一条传递路径：`CardPoolConfig → CharacterConfig.CreateDefinition → BattleDriver → MonsterAgentFactory.Create → agent`） |
| `App/Editor/CardPoolConfigInspector` | 表下方一节**只读核对**：实时翻中文名 + 标出「卡表里没有这个 ID」「不在本卡池里」 |

### ⚠ 最关键的一条：门开在**被覆写的那一端之外**

`PriorityOf` / `DefaultPriority` 都是子类可以整体覆写的（`BerserkerAgent.PriorityOf` 先判自己的
「最爱卡」再调 base）。把手写表写进那一端，「怪物子类的偏爱」就会盖掉玩家写进卡池的顺序 ——
而用户要的恰恰是**我写的不能被代码覆盖**。所以门开在 `DecideAttack` / `PredictNextAttack`
共用的 `PriorityFor` 上：

- 表非空（开关勾了且至少填了一行）→ **登记过的卡用表里的数**、**没登记的一律并列最低**；
  四流派档位、回血卡的全局覆盖（「永远最低 / 可回血时最高」）、子类偏爱**全部让位**；
- 表为空 → 原样走 `PriorityOf`（老行为**逐字不变**）。

⚠ 不做「手写值 / 自动档位混着比」那种折衷：两套刻度混起来没人算得清，宁可**二选一**。
所以勾了开关就请把在意顺序的卡都写上，没写的会掉到最后。

⚠ `PredictNextAttack` 也走 `PriorityFor` —— 「玩家点怪物看到的元素」与「它真打出来的那张」
不会因为手写表而分叉（预判与实战同源，是本工程的老口径）。

## 遗留

- ⚠ **真机上「遇到一次敌方双发、把两张点出来拖出去」尚未跑过一遍**（与 M33 / M25 同一条遗留：
  要在一局里正好遇到敌方打出双发牌 荆棘 `t` / 飞叶连击 `u` / 藤蔓 `v` / 狂躁蘑菇 `w`）。
  代码路径已按用户口径逐条对齐，但**手感**（点两张的顺序、拖出去那一刻的判定）只能上手看。
- 手写优先级只作用于**出牌选择**：防御口径、流派判定、光环用法、`IsCardAllowed` 禁卡不受它影响。
