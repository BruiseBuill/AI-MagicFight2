## 1. 用户口径（原文逐条）

1. 「充能这张卡有两个效果，但应当是**第 2 个效果先执行**，然后**计算出总的加速次数**，
   再玩家开始选择加速。」
2. 「怪物的意图，当前的有效点击判定区域太小，应当**覆盖整个怪物模型**，并且点击之后，

4. 「选择牌的界面当中（磁爆 / 充能 / 电弧 / 旋涡），标题底下会有一个
   **当前选择牌数和当前手牌总数的数字显示，不需要显示这个**。」

## 2. 需求 1 · 充能：先挑手牌，算出总加速次数，再一次性问加速目标

### 2.1 卡面与旧顺序

充能（`am`）的 α 队列是 `Haste(1)` + `CoolHandForHaste(1)`，两条都归 **③ 冷却阶段**
（`BuiltinEffects.Register`：`Haste → EffectStage.Cooldown`、`CoolHandForHaste → EffectStage.Cooldown`）。

`EffectWindow` 按 `_effects` 的**入队顺序**逐条推进，而入队顺序 = 卡表声明顺序，于是旧节奏是：

```
出牌 → ①（空）→ ② 对方防御 → ③ 加速 ×1（先问「这一次加速给谁」）
                  → ③ 选冷却手牌 → 每冷却一张再问一次加速 → ④ ⑤
```

**病根**：玩家在**还不知道总共能加速几次**的时候，就得先把第一次加速分配掉。

### 2.2 做法：让 CoolHandForHaste 把同卡同触发的 Haste 吸收进来

`BattleEngine.AddCardEffects` 加了一层 `EnqueueEffects(context, effects, trigger)`：

* 只要这组效果里有 `EffectOp.CoolHandForHaste`，就把同卡同触发的 `EffectOp.Haste`
  **不入队**（否则次数会算两遍）；
* 它给的那几次次数写进那条 `CoolHandForHaste` 的 `Arguments["absorbedHaste"]`（`WithAbsorbedHaste`），
  `BuiltinEffects.CoolHand` 在选完手牌之后一次算总账：

```csharp
int total = count * e.Arg("amount") + e.Arg("absorbedHaste");
foreach (EffectChoice next in Cooldown(c, new EffectDef(c.Trigger, EffectOp.Haste, total))) yield return next;
```

新节奏：

```
出牌 → ①（空）→ ② 对方防御 → ③ 选冷却手牌（第 2 个效果先跑）
                  → 算出总次数 = 1 + 冷却了几张 → ③ 连续问 N 次加速 → ④ ⑤
```

实测（`execute_code` 里真跑引擎、打印玩家座位的决策序列），seed 3：

```
EV attack seat=0 充能
  REQ ChooseCoolHandCards title=['冷却·获加速'] min=0 max=4 opts=4
  REQ ChooseHasteTarget title=['加速'] min=0 max=1 opts=3
  REQ ChooseHasteTarget title=['加速'] min=0 max=1 opts=3
```

—— 选牌在最前、加速次数 = 1（吸收来的基础那次）+ 1（AI 冷却了 1 张）= 2，与口径一致。

### 2.3 为什么不是「把卡表两条效果调个序」

那会**改到卡面**：卡面的效果文字就是按 `CardDef.Effects` 顺序渲染的，调序等于把充能卡面上
那两行也换个位置（用户没要求改卡面）。吸收式合并没有动卡表一行。

### 2.4 顺带：模仿复制来的充能走同一条口径

`EffectCopy`（模仿复制冷却区某张牌的进攻效果）原来是自己 `foreach … AddEffect`。
现在它调同一个 `EnqueueEffects`，所以**复制来的效果表**也按「先选牌、再算总次数」合并 ——
否则复制一份充能会得到「N 次 + 单独一次」两批加速。
⚠ 这也是把吸收来的次数写进 `Arguments` 而**不是**回头去读卡表的原因：
被复制来的那张效果表不属于施法者，只有入队那一刻知道「这批效果是从哪张牌抄来的」。

## 3. 需求 2 · 点怪物看意图：可点区域 + 思考框外观

### 3.1 只把点击面撑大是不够的 —— 真正的病根是射线归属

`ArtLayer/Char_Monster_Click` 原来是 320×340，怪物模型是 398×335（待机帧），
确实小一圈。但**真正让点击「少一大块」的不是尺寸**，而是：

**敌方冷却列的滚动视口（`CoolingScroll_Enemy`）盖在怪物模型上。**

| 节点 | 画布范围 | 兄弟序（ArtLayer 下） |
|---|---|---|
| 怪物模型 `Char_Monster` | x ≈1051…1450，y ≈391…726 | 3 |
| `Char_Monster_Click` | x 1086.5…1406.5，y 407…747（旧值） | 5 |
| **`CoolingScroll_Enemy`**（视口 674×621） | **x 1226…1900，y 344…965** | **8** |
| `HandCount_Monster`（按住看手牌） | x 1381…1505，y 408…448 | 13 |

视口比点击面**后建**（同层绘制顺序 = 兄弟序 → 更靠后 = 画在上、先应答射线），
而它自己**没有任何点击处理器**（它只是 `ScrollRect` 的拖拽面）。
于是模型右半边（x 1226…1450）的点按落到视口上、什么也不发生 —— **且零报错**。

实测（Play 里逐点做 `RaycastAll` + 忠实复刻输入模块的 press/release 分发）：

```
旧版：canvas(1100,560) → Char_Monster_Click → 弹泡 ✔
      canvas(1350,560) → CoolingScroll_Enemy   → press=NONE ✘（点了毫无反应）
      canvas(1246,720) → CoolingScroll_Enemy   → press=NONE ✘
      canvas(1246,430) → CoolingScroll_Enemy   → press=NONE ✘
```

即旧版**有效可点区只剩 x 1086…1226 那 140 px 宽的一条**，与用户「有效点击判定区域太小」完全对得上。

### 3.2 三处几何改动

| # | 项 | 旧 | 新 | 常数 |
|---|---|---|---|---|
| ① | 点击面 | 320×340 @ 脚底+175 | **420×360 @ 脚底+168**（= 模型包围盒 + 四边约 10 px） | `ThinkBubbleClickWidth/Height/CenterY` |
| ② | 思考框位置 | 模型头顶正中（与脚底同轴、徽标之上） | **模型右上角**：x = `CharMonsterX + 200`，y = `CharGroundY + 368` | `ThinkBubbleRightOffsetX` / `ThinkBubbleUpperRightRiseY` |
| ③ | 泡体 / 符号 | 泡体 168（象牙白 `CardBox.png` 九宫格）+ 符号 104 | **泡体 67.2、符号 41.6**（同一个 0.4 系数），**泡体不再画任何东西** | `ThinkBubbleWidth/Height` / `ThinkBubbleIconSize` |

新落点占 x 1412.9…1480.1、y 736.4…803.6，于是：
血量徽标（x 1180.5…1312.5）**横向不再重叠**（旧版是压在它上下）、
头顶出牌面板（x 1119.5…1373.5）也不重叠、敌方冷却列的视口上沿 736 正好让开。

「缩小背后的框」这一条：泡体**已经没有图**了（用户口径「不需要有白色的背景」），
所以「框」只剩两个作用 —— 弹出动画的缩放原点、以及上面那笔版式账；
`UiTheme.ThinkBubbleBackdrop` 与构建器里那段 `Backdrop` 一起删掉（`Art/Ui/CardBox.png` 另有消费者，保留）。

### 3.3 射线归属：把模型那块从冷却视口里挖出来

不能把点击面挪到视口之上 —— 那样**整棵冷却列子树**都落到它下面，迷你卡与槽位徽标
（点选加速 / 减速目标、选区域档全靠它们）会一起点不动，比现在更糟。
也不能把视口缩窄 —— 视口宽 = `槽宽 + 缝 + 卡宽 + 3×步进 = 674`，
一行放满 4 张迷你卡时最左那张会伸到 x ≈1312，缩窄就等于把它裁掉（M11 时期为这件事反复调过）。

所以：

1. `CoolingScroll_Enemy` 的视口 `Image.raycastTarget = false`（**只敌方那侧**，
   玩家侧的 `CoolingScroll_Player` 不动 —— 它不压任何可点目标）；
2. 补两块**只覆盖模型以外**的透明拖拽面：

| 节点 | 尺寸 | 位置（右上角口径） | 覆盖的画布范围 |
|---|---|---|---|
| `DragSurface_Right` | 443.5 × 621 | (0, 0) | x 1456.5…1900，y 344…965 |
| `DragSurface_Top` | 230.5 × 215 | (−443.5, 0) | x 1226…1456.5，y 750…965 |

两块合起来 = 视口矩形 −「模型点击面」矩形（下方那 46 px 窄条略去）。
它们建在内容列与滚动条**之前**（兄弟序 0 / 1）→ 只在「空地」上生效，
迷你卡 / 槽位徽标 / 滚动条照旧优先。

**拖动照样滑得动**：两块都是视口的子节点，EventSystem 找 `IDragHandler` 是
「从命中节点往上找」→ 落到视口上的 `ScrollRect`（与 `CardInteractor.ForwardDragToScroll` 同一个道理）。
实测：在 `DragSurface_Right` 上合成本地拖拽 → `content.anchoredPosition.y` 0 → 90、
`verticalNormalizedPosition` 1.000 → 0.510。

### 3.4 改 `UiLayout` 常量为什么不必重跑构建器

`ThinkBubbleView.ApplyLayout()` 在 `Awake` / `Configure` / `Show` 里按
`UiLayout.ThinkBubble*` **重申**锚点 / 位置 / 泡体尺寸 / 符号边长 / 上浮量。
理由与 `ShopSlotView.Bind` 那次「改了常量、卡面纹丝不动」是同一类：
构建器写进 `BattleCanvas.prefab` 的值不会跟着常量变。运行时重申之后，
挪一个泡只要改常量（本轮就是这么在没重跑构建器的情况下生效的），而且重跑构建器也不会改回去。
⚠ 总时长 / 弹出时长（节奏）仍由构建器经 `Configure` 注入 prefab（本轮没动它们）。

## 4. 需求 3 · 磁暴 / 充能：一张都不选也能确认

`BuiltinEffects.Request` 新增 `allowEmpty` 形参 —— 与既有的 `optional` 的差别只有一个：

| 形参 | `MinSelect` | 额外发一条 Skip 选项？ |
|---|---|---|
| `optional`（加速 / 减速 / 雪崩那族） | 0 | **发**（「跳过加速」） |
| `allowEmpty`（本轮的磁暴 / 充能） | 0 | **不发** |

界面上「可以空着确认」本来就只由 `MinSelect = 0` 表达（`HandPickView.RefreshConfirm`：
`ok = _selected.Count >= _minSelect`），再摆一条「跳过…」反而是语义重复的第二个按钮。
`ContextNoSkip` 跟着变成 `false` —— 与「可以什么都不做」自洽。

`CoolHand` 里只有 `CoolHandForAtk`（磁暴）与 `CoolHandForHaste`（充能）给 `allowEmpty`；
**电弧**（`CoolHandForCombo`，必须恰好 1 张换连击）与**漩涡**（`RemoveFromGame`，强制 1 张）
保持原样 —— 用户只点名了前两者。

⚠ 这条同时**修掉了一条常年 FAIL 的既有断言**：`CoolHandScenario` 一直期望
`expectMin = multiOk ? 0 : 1`，而引擎给的是 1（见 §6）。

## 8. 本轮踩的坑（供后来者）

1. ⭐⭐ **「点不动的区域」先查射线归属，别先改尺寸**：用户说「判定区域太小」，
   听起来是矩形给小了；实测下来主因是**一个更大的、没有任何处理器的射线面盖在上面**。
   判据很简单：在 Play 里对若干点做 `EventSystem.RaycastAll` 并打印
   `hits[0].gameObject.name` + `ExecuteEvents.GetEventHandler<IPointerClickHandler>(hits[0].gameObject)`
   —— 一眼就能看出「命中了谁、它到底处不处理点击」。
2. ⭐ **`Image.raycastTarget = false` 不等于把整棵子树交出去**：本轮的解法和这个直觉相反 ——
   视口不接射线、但它的**子节点**（迷你卡 / 槽位 / 滚动条）照旧接，因为子节点在射线顺序上
   天然排在父节点之上。所以「挖掉一块」可以用「父节点让位 + 补几块更小的接住」来做。
3. ⭐⭐ **`execute_code` 里改完 Prefab 的字段，若那次改动依赖了刚改的 `UiLayout` 常量，
   必须先把 Unity 编译刷完**：本轮第一次刷 Prefab 时 `refresh_unity` 还没跑，
