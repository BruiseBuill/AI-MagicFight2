## 1. 用户要的四条（原话）

| # | 原话 | 落点 |
|---|---|---|
| 1 | 「地图是随机生成的，除了起始节点和最终的节点。**起始节点一定是 camp**」 | `MapGenerator`：起点固定 `MapNodeType.Camp`、终点固定 `Boss`，中间加权随机 |
| 2 | 「中间虽然是随机生成，但**摆的位置一定要能够用桥连接上**」 | 生成器的硬约束「每条边两端**行号差 ≤ 1**」+ `UiLayout.MapNodePosition` 一处算坐标 + `MapView.PlaceBridge` 按两端点反解桥的缩放与旋转 |
| 3 | 「当点击到某一个节点之后，**玩家移动到这个节点上**，如果有这个节点对应的场景的话，就进入到该场景内」 | `MapSceneEntry.OnNodeClicked` → `MapView.PlacePlayer(带动画)` → 到位后 `MapSceneRoutes.SceneFor` 查表 → `SceneManager.LoadScene` |
| 4 | 「在场景里点击**离开**键之后，也应当返回到地图」 | `MapRoutes.LeaveToMap()`；商店 / 石台 / 女巫工坊三个场景的「离开」都调它；战斗场景的结算键变成「回到地图」（见 §5） |

## 2. 地图长什么样（版式账）

画布 1920×1080，**画布绝对坐标 + 锚点左下 (0,0)**（与商店 / `Char*` 那批同口径）。

| 量 | 值 | 为什么 |
|---|---|---|
| 层数（列） | **9** = 起点 + 7 中间层 + Boss | 规格 §6.1「短局 8 层（含 Boss，不含起点）」 |
| 每层最多几行 | **4** | 规格 §6.1 `MinWidth = 2 / MaxWidth = 4` |
| **边长** `MapHexEdge` | **240** | 六向格的边长 = **相邻节点中心距**。六条格子方向全部等于它（2026-10-06） |
| 行距 `MapRowStep` | 边长 × √3/2 ≈ **207.85** | 同层相邻两行的中心距（六向格里它同时也等于边长） |
| 每行错位 `MapRowShear` | 边长 × −1/2 = **−120** | **每往上一层、整行左移半格** —— 这是六向格唯一需要的花招 |
| 起点列 / 底行 | `MapOriginX = 180` / `MapBottomY = 180` | 营地 (0,0) 在左下；Boss (8,3) 落在 (1740, 803.5) |
| 节点中心 | `MapNodeSize = 128` 的正方形外框（图按原比例居中） | 节点图约 274×250，圆盘约 118 |
| 占位（含节点直径） | x ∈ [116, 1804]、y ∈ [116, 867.5] | 左右各留 116、顶到提示线（952）还差 85；底边留 116 给「营地」小字 |

```text
   行 3                                 ● Boss（右上角）
   行 2                        ●  ●
   行 1                 ●  ●
   行 0  ●  ●  ●   ← 营地（起点，固定，左下角）
         L0 L1 L2 …                                     玩家棋子跟着「当前节点」走
```

⚠ **六向格 = 每往上一层、整行往左错半格**：于是「正右一层」与「右上一层」两条边的长度
**都等于边长 240**（方向 0° 与 +60°），全图所有桥**同一个缩放系数**（0.5576）。
2026-10-06 之前是普通的方格（列距 190 / 行距 210 / 不错位），行差 0 的边 190、行差 ±1 的边 283.2
—— 差 1.49 倍，桥只能逐边缩、必然一粗一细（用户 2026-10-05 与 10-06 两次提这条）。

### 2.0 为什么生成器里**没有**「往下一行」

用户口径是「相邻节点之间的距离应该相同 + 标准的六向地图」。几何上可以证明：
**只要同时留着「平 / 上 / 下」三种走法，就一定有两条边的长度不同**。
设正右一层的边向量 `(a, 0)`，同一层往上一行是 `(b, c)`，则三条前向边是
`u = (a, 0)`、`v = (a+b, c)`、`w = (a−b, −c)`；要三边等长 ⇒ `ab = 0` ⇒ `b = 0`
⇒ `√(a²+c²) = a` ⇒ `c = 0` —— 三个邻居落在同一点，矛盾。

而在六向格里，「右下一层」**根本不是格子邻居**：它是 `(−30°, 1.73 × 边长)` 的次近邻
（格子邻居只有「正右 0°」与「右上 60°」两条前向边；另外两条 120° / 300° 是**同一层**里的移动，
本图的 DAG 画不出来）。所以三条前向边里只能留两条 —— 留下的是「平 + 上」，
行号只增不减，地图照样只朝右上角走（Boss 固定在最后一层最后一行）。

> 被否掉的另外两条路：只改版式不改生成器（桥一定一粗一细）；
> 允许**同层边**换来真正的「六向全连」（要改地图 DAG 与 `MapRun` 的推进语义，判定为不值）。

### 2.1 桥：为什么「位置一定连得上」

这是用户第 2 条要求的正面回答，分三层保证：

1. **拓扑层（Core）**：生成时每一步的行号变化只允许 ∈ **{0, +1}**（见 §2.0 ——
   六向格里「往下一行」不是格子邻居），而且同两层之间不允许交叉边 —— 这写成了
   `MapGenerator.Builder.Validate()` 的硬约束，不过就切下一个种子整张重生成
   （`MaxAttempts = 200`）。⚠ 行号只增不减还带来一个额外好处：
   横向用到的范围就是「营地 → Boss」两端，宽度可算死（见 §2 的占位行）。
2. **版式层（`UiLayout`）**：`MapNodePosition(layer, row)` 是**唯一一处**坐标换算，
   桥的两端、玩家的落点、节点的位置全部调它。
3. **表现层（`MapView.PlaceBridge`）**：拿两端点的实际像素差反解桥的变换。

两套桥的素材量出来的事实（写进 `UiLayout` 常量，不是估的）：

| 素材 | 量到的几何 | 意思 |
|---|---|---|
| `08_bridge_straight.png` 315×70 | 可见内容 x 5…309；**桥墩外缘距 305**；两端桥墩各占 5…50 / 265…310（含浅色顶面）；**木板区 50…265（宽 215）**；桥墩偏移在**本地 x 轴**上 | 只缩 x 就精确对齐，木板厚度恒定，**任何角度都能用** |
| `09_bridge_diagonal.png` 243×179 | 端帽不在任何一个轴上 | **本版式已不用它**：两种素材的「单位长」差 1.76 倍，同一个空隙下会缩成一粗一细。所有边一律用直桥素材转角度（全图只有一个缩放系数） |

> ⚠ **2026-10-08 订正**：旧版把「木板区宽 215」误当成了「两端桥墩中心距」，
> 缩放系数因此偏大 1.42 倍 —— 两块桥墩被整块缩小、压进 128 px 的节点平台里，
> 屏幕上只剩木板（用户报「桥的两端仍然没有露出来」）。
> 现在分母换成**桥墩外缘距 305**（`MapBridgeVisibleWidth`），
> 平台半径也从 60 改成实测最小值 **56**（0° 量到 61.2、±60° 量到 56.3 ——
> 平台是八边形，斜着量到的是棱边；取最小值才能保证任意一条边都不留缝）。
> 于是桥墩外缘正好落在平台边缘，**两块桥墩整块露在平台之外**，木板把空隙填满。
>
> 本版式的边只有两种角：同行 **0°**、上一层 **+60°**（生成器只允许行号差 ∈ {0, +1}，见 §2.0）。

## 3. 生成算法（`Core/Map/MapGenerator.cs`）

**不是「先定节点再连边」，而是反过来**：先撒 6 条从起点走到 Boss 的完整路径，
**路径经过的格子就是节点、路径的每一步就是一条边**。这样
「每个节点都能从起点走到、也都能走到 Boss」是**构造出来的**，不需要事后修补
（事后补边正是「连出一条死路」的来源）。

四条不变量（`MapScenario` 1000 个种子逐条验）：

| # | 不变量 | 违反的样子 |
|---|---|---|
| 1 | 起点唯一（`Camp`）、终点唯一（`Boss`） | 用户明确要求「只有起点和终点是固定的」 |
| 2 | 每条边两端**行号差 ≤ 1** | **桥画不出来** —— 地图上少一根线，零报错 |
| 3 | 同两层之间**无交叉边** | 两条路线视觉上穿过对方，玩家分不清谁连谁 |
| 4 | 每个节点都从起点可达、也都能走到 Boss | 走进去**卡死**，而地图上看不出来 |

### 3.1 两条「不这么写就会静默出错」的细节

- **「最晚什么时候必须爬到哪一行」是硬约束**：Boss 固定在最后一行，所以倒数第 L 层的节点
  必须在第 `bossRow − (last − L)` 行之上。这条由 `NeedRow` 一处给出，走路径时每一步都夹一次；
  不夹的话最后一步会出现行号差 2，整张图被丢掉重生成（概率上一直失败 → 走兜底图）。
- **第 1 层的行号是 round-robin 而不是随机**：起点层只有 1 个节点，它是**唯一**
  没法靠「多撒几条路径」自然撑开的层。6 条路径独立随机时，「6 条全选了同一行」的概率约 3%，
  → 第 1 层宽度 1 → 紧接着一列全是单行道。实测 1000 个种子里有 **38 个**中招（其中第 7 层最多）。

### 3.2 类型分配

- 第 0 层 = `Camp`（起点），最后一层 = `Boss`，**第 1 层固定普通战斗**
  （与规格 §6.3「第 1 层禁连」同口径）。
- 第 2..倒数第 2 层按权重抽：战斗 46 / 未知 18 / 商店 14 / 女巫 12 / 石台 10。
- **三项保底**：整张图至少各有 1 个商店 / 女巫 / 石台。理由很实际 ——
  这三张节点图是专门做的，某次随机一个都没抽到，玩家就整局看不到它们；
  而「随机」在这轮要表达的是**路线与分岔**，不是「这次没有商店」。
  正式接入冒险经济时可去掉（`EnsureType` 两行）。

## 4. 节点类型 → 场景（`MapRoutes`：唯一一张表）

| 节点 | 场景 | 说明 |
|---|---|---|
| `Camp` 营地 | **无** | 起点。走过去停在那儿，节点当场结算 |
| `Battle` 战斗 | `SampleScene` | **就是现有的战斗场景**，不新造一个 |
| `Shop` 商店 | `Shop` | P4 已落地 |
| `Witch` 女巫工坊 | `WitchWorkshop` | P6 已落地 |
| `Altar` 石台 | `Upgrade` | P5 已落地 |
| `Unknown` 未知 | **无** | 「事件」的占位 —— 事件系统还没做，所以**故意**不给场景 |
| `Boss` | `SampleScene` | 赢了 = 通关 |

**这张表必须只有一处**：地图（决定点完是切场景还是原地结算）、节点下面那行小字、
构建器（把场景登记进 Build Settings）三处都要用它。各写一份 switch 的话，
加一种节点时必然漏掉一处，而漏掉的样子是**零报错**的：漏了地图那一处 → 点下去什么都不发生；
漏了 Build Settings 那一处 → `LoadScene` 抛错，**玩到那一步才炸**。

⚠ 构建器顺带把 **`Map / SampleScene / Shop / WitchWorkshop / Upgrade` 五个场景登记进 Build Settings**
（原来只有 `SampleScene` 一个！`LoadScene("Shop")` 在登记之前是必然抛错的）。
**Map 排第一 = 正式构建的启动场景**。

## 5. 五个场景之间的往返

```text
Map  ──点可达节点──►  玩家棋子走过去(0.42s) ──停 0.24s──►  有场景？
                                                          ├─ 有 → LoadScene(Shop/Upgrade/Witch/SampleScene)
                                                          └─ 无 → 当场结算这一步
事件场景 ──点「离开」──►  MapRoutes.LeaveToMap() ──► LoadScene("Map")
战斗场景 ──结算键（这时写着「回到地图」）──► MapRun.ReportBattle(胜负) ──► LoadScene("Map")
Map（重进）──► MapSceneEntry.Boot(): 有 PendingIndex 就结算这一步
```

### 5.1 关键设计：结算只在地图那一边发生

`MapRoutes.LeaveToMap()` **不**调 `MapRun.SettleReturn()` —— 结算由地图的
`MapSceneEntry.Awake` 做。一个动作只在一个地方发生，否则
「离开时结算一次 + 回地图又结算一次」会把同一个节点算两遍。

### 5.2 战斗场景的接线（`BattleUi` 三处小改）

- `_mapBattleReturn = MapRun.HasActiveRun && MapRun.InMapBattle`（判据只有 `MapRun` 一处）；
- 结算面板上那个键的标签从「再来一局」改成 **「回到地图」**（用
  `GetComponentInChildren<TMP_Text>` 找它 —— **不为了换两个字去改 Prefab**，
  改 Prefab 就得多跑 M7→M8→M11 三趟构建）；
- `OnAgainClicked` 在冒险里改为 `ReportBattle(胜负)` + `LoadScene("Map")`；
- `HandleStarted` 里把它复位成「再来一局」并清 `_mapBattleReturn`（不收回来下一局就错着）。
- **平局按失败算**（规格 §4.3：适配器把「无胜者」映射成 `PlayerLose`）。

### 5.3 独立场景契约仍然成立

`MapRun.HasActiveRun` 为假时（= 单独打开 `Shop.unity` 进 Play）：
`LeaveToMap()` 返回 false，事件场景照旧只打日志、不切场景；
战斗的结算键照旧是「再来一局」。**三个事件场景 + 战斗场景的既有调试方式一个字节都没变。**

## 6. 界面（`MapCanvas` 节点树）

```text
MapCanvas                        (Canvas + CanvasScaler + GraphicRaycaster + MapView)
├─ Bg_Map                        1920×1080 底面（素材正好是参考分辨率，铺满即可）
├─ BridgeRoot                    桥层（在节点下面）
├─ NodeRoot                      节点层
├─ Player                        玩家棋子（立绘，脚底为 pivot）
├─ Hud                           Hud_Bar + Name / Subtitle / ProgressNumber / GoldNumber
├─ Title                         「冒　险　地　图」
├─ Hint                          「点亮的节点可以前往 · 营地出发，一路走到 Boss」
├─ EndLayer(失活)                Veil + Panel(Peek_Panel) + EndTitle / EndBody / EndButton
└─ Templates(失活)               ← ⚠ 模板挂在这里，**不是** NodeRoot / BridgeRoot 的子节点
   ├─ BridgeStraightTemplate
   ├─ BridgeDiagonalTemplate
   └─ NodeTemplate               (MapNodeView)
      ├─ RingLine                 「可以去」的金色圆角框（CardBox_Line，呼吸缩放）
      ├─ RingCurrent              「你在这儿」的蓝色圆角框
      ├─ Icon                     节点图（7 选 1，按 MapNodeType 查 Sprite[]）
      ├─ Dim                      压暗纱（**与图标同一张图**，见 §8）
      ├─ Label                    节点名（只在「可以去 / 当前」时显示）
      └─ Hit                      透明命中区（**唯一**吃射线的东西）
```

- **模板挂 `Templates` 下**：`MapView.Build` 会把 `NodeRoot` / `BridgeRoot` 的子节点
  **整批清掉**再按图重建，模板混在里面会被一起清掉（第一次重建就空屏，零报错）。
- **命中区是单独一个节点**，不给 `Icon` 开 `raycastTarget`：图层顺序决定 Hit 在 Icon 之上，
  而 `raycastTarget` 是「吃射线」的唯一开关 —— 只有一处打开、只有一处关，状态切换时不会漏。
  `ApplyState` 里**同时**切「压暗 / 亮框 / 小字 / 命中」四样，视觉与射线永远一致。
- **顶栏两个数字位叫 `ProgressNumber` / `GoldNumber`**，不沿用战斗那套
  `HpNumber` / `ResNumber`：地图里**没有「生命」这个量**（战斗的入场生命不由地图给），
  名字留着旧语义会让下一个改的人按名字去猜。

## 7. 运行态（`MapRun`：静态类）

| 字段 | 含义 |
|---|---|
| `Graph` / `Seed` | 这一趟的地图与种子 |
| `CurrentIndex` | 玩家所在节点 |
| `PendingIndex` | **正在进入**的节点（从「点下去」到「从它的场景回来」这一段都不为 −1） |
| `Resolved` | 走过的节点 |
| `Gold` | 金币（商店买卡会写回，地图顶栏读它） |
| `BattleResultPending` / `BattleWon` | 战斗场景留下的胜负 |
| `Won` / `Lost` | 通关 / 旅程结束 |

- **为什么是静态字段而不是 `DontDestroyOnLoad` 单例**：换场景会把场景里的对象全部销毁，
  所以它必须活过 `LoadScene`。静态字段没有生命周期、没有 `Awake` 顺序问题，
  而且每个字段都是可读值，不会被谁在背地里 Reset。
- **⚠ 只在一次 Play 内有效**（退出 Play / 重开编辑器就归零）。真正的存档要落盘
  （规格 §5.5），那是 P6 的事。这轮的目标是「五个场景能串成一条链路」。
- **能点哪些节点是这里算的**（`IsReachable`）：必须是当前节点的**直接后继**且没走过 ——
  不能跳层、不能往回走、不能在同一层横跳。地图上的高亮与点击**都**调这一个函数。
- **金币**：商店进场景时读 `MapRun.Gold`（只在 `HasActiveRun` 时覆盖调试默认值），
  买完写回。所以「买完离开 → 地图上的金币少了 20」是通的。

## 8. 踩坑（全是「零报错」那一类）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 「走过 / 去不了」的节点外面挂着一个**深色方块** | `Dim` 是**没有 sprite 的纯色矩形**，而节点图是椭圆平台 → 矩形的四个角露在平台外面 | `Dim` 改用**节点自己那张图**当掩膜（`Bind` 里 `_dim.sprite = icon`），形状就永远是节点本身 |
| 2 | 高亮框是**橄榄色**（脏黄），读不出「亮着」 | 拿的是 `Buff_02_RingEmpty.png`（光环槽那块**深蓝灰**石环），乘金色只能得到脏黄 | 换 `CardBox_Line.png`（**白色描边**，染什么色就是什么色，而且本来就是工程里「可点 / 空位」的统一语言） |
| 3 | 第 1 层宽度 1（单行道） | 起点层只有 1 个节点，6 条路径独立随机 → 3% 概率全选同一行；1000 个种子里 38 个中招 | 第 1 层的行号改 **round-robin**（第 p 条路径取第 `p % 2` 行）+ `Validate` 增加「中间层宽度 ≥ 2」硬约束 |

## 10. 本轮边界

- **没有** `Core/Adventure/`（`RunState` / `AdventureEngine` / `AdventureCommand` / `IStore` / 派生种子）
  —— 规格 §11.1 那一整层都还不存在，本轮的运行态是 `MapRun` 这个静态类。
  正式接入时它整块换成「从地图层递进来的 `RunSnapshot` + 提交 `AdventureCommand`」。
- **没有**地图拖拽 / 缩放（整张图一屏放得下，不需要）；规格 §6.4 的「拖动地图不能误触进节点」
  因此不适用。
- **没有**遗物 / 商店服务 / 休息点 / 事件内容。
- **没有**改任何既有 Prefab；`SampleScene` / `Shop` / `Upgrade` / `WitchWorkshop` 四个场景
  只改了「离开 / 结算键」的行为，**场景资产一个字节没动**。
