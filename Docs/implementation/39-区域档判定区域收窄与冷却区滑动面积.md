# 39 · 区域档判定区域收窄 + 冷却区滑动判定面积恢复

> **性质**：现行实现记录 —— 区域档与逐张目标同拍时，区域档只认槽位徽标；不可拖的迷你卡把拖拽转交给滚动层

日期：2026-09-25（用户 3 条调整，接在 [M26](24-M26区域选择改成点冷却槽.md) 之后）。

## 用户口径

> 1. 对于**加速和区域加速同时触发**的情况，区域加速的判定区域过大，甚至覆盖到了卡牌上，
>    需要缩小这个判定区域，至少不能与冷却区域当中的卡牌重叠。
> 2. **区域减速和减速同时触发**的情况同理。
> 3. 常态下，**滑动屏幕来滑动冷却区的判定面积略微有点窄**
>    （经常非得要很靠边才能滑动成功），加宽一下。

## ① 加速 + 区域加速 同拍：区域档的判定区域收窄

### 病因：不是高亮画大了，是「点卡面」这条补路把整片卡面吃掉了

M26 给区域档留了一条补路（`CooldownView.OnCardClicked`）：**点卡面 = 点它所在的那一格**。
理由当时是对的 —— 迷你卡带自己的 `Button`，EventSystem 派发 `pointerClick` 时遇到第一个能处理的
节点就停，点在牌面上永远到不了挂在槽上的 `ZoneSlotClickCatcher`；而一行放满 4 张卡时
槽图露出的空白几乎没有，不补这条路区域档就点不动。

问题出在**这一拍同时还有「逐张目标」的时候**：

- 一张牌同时带 `Haste` 与 `HasteZone`（例如卡表里的 `m/p/q/s`、`i`）时，引擎把两件事
  **合成同一个决策**（`EffectWindow` 的 `combined` → `RequestKind.ChooseCooldownEffects`，
  提示条写「加速 / 区域加速」，`MaxSelect = 1`）—— 选项里既有「哪一张牌」也有「哪一方 · k」。
- 补路一开，**点任何一张卡都被吞成「选了那一格」**：玩家永远选不出「只加速这一张」。
- 屏幕上读到的就是「区域加速的判定区域太大了，盖到卡上」——高亮本身（8 个槽位底图）没画大，
  被盖住的是**点击的归属**。

### 改法：给「并存」加一个开关，补路按它开合

`CooldownView` 新增显示态 `_zoneWithCardTargets`（`SetZoneWithCardTargets(bool)`），
由 `BattleUi.ApplyZonePickState` 在点亮区域态时一起下 —— 判据就是同一处的 `_coolingTargeted`
（本拍 `Options` 里有没有「具体哪张冷却牌」，也就是逐张那一半在不在）：

```csharp
_cooldown.SetZonePickable(true);
_cooldown.SetZoneSeats(seats);
_cooldown.SetZoneWithCardTargets(_coolingTargeted);   // ← 新增
```

`OnCardClicked` 里的补路加一个条件：

```csharp
if (_zonePickable && !_zoneWithCardTargets)   // 并与存时才关掉
```

| 这一拍的形状 | 补路 | 点卡面 | 点槽位徽标空白 |
|---|---|---|---|
| 只有区域档（M26 原本那一拍） | **开** | 算「点了这一格」 | 算「点了这一格」 |
| 区域档 + 逐张目标（加速 + 区域加速） | **关** | 算「点了这张牌」 | 算「点了这一格」 |

### 为什么「收窄到不碰卡面」在几何上成立

迷你卡摆在**槽的外侧**（`BindGrouped` 的 `offset = rowW + SlotMiniCardGap + …`），
槽底图只有 190 / 182 / 183 宽，卡的左边缘在 `槽宽 + 8` 之外 ——
两者本来就不重叠（槽图 `rect` = 它自己的尺寸，卡是**溢出父节点**渲染的子节点）。
所以「判定区域 = 槽位徽标本身」天然满足用户那句「至少不能与冷却区域当中的卡牌重叠」，
不需要再算一个新的矩形。

> 颜色仍然只从 `UiTheme.ZonePickableEdge` 取，`raycastTarget` 仍然只在区域决策那一拍打开
> （M26 定下的两条口径没变）。

## ② 区域减速 + 减速 同拍：同一件事

`Slow` + `SlowZone` 走的是**同一个决策形状**（同一个 `combined` 分支），
所以第 ① 条那一处改动同时覆盖了它 —— **判据是「选项形状」而不是「哪个效果」**，
不需要按极性再分一次支。

## ③ 常态下「滑冷却区」的判定面积：从槽位徽标那一条恢复到整个视口

### 病因：不可拖的牌把拖拽整条吞掉了

`CardInteractor` 为了手牌拖拽实现了 `IBeginDragHandler / IDragHandler / IEndDragHandler`。
而 EventSystem 找拖拽处理器的方式是
**「从射线命中的节点往上找第一个实现了 `IDragHandler` 的节点」**
（`ExecuteEvents.GetEventHandler`）—— 它看的是**类型有没有实现接口**，不看实现了以后做不做事。

于是冷却区的迷你卡（`CardInteractor.Attach(..., draggable: false)`）虽然什么也不做，
**仍然把拖拽整条吞掉**：事件永远上不到 `CoolingScroll_Player / CoolingScroll_Enemy` 上的 `ScrollRect`。

结果：只有点在**槽位徽标那块空白**（槽图 `raycastTarget = false` → 射线落到视口自己身上）
才滑得动。而视口是 674 宽、一行 4 张迷你卡几乎铺满 —— 玩家感受到的就是
**「得贴着最左边那条才滑得动」**。

### 改法：不可拖的牌把拖拽原样转交给所在的 `ScrollRect`

`CardInteractor` 新增 `ForwardDragToScroll(phase, eventData)`：`Draggable == false` 时把
`OnBeginDrag / OnDrag / OnEndDrag` 原样转发给 `GetComponentInParent<ScrollRect>()`（结果缓存，
`Attach` 时重置 —— 池化复用的牌可能被搬到别的滚动层下）。

两处细节：

- 转发**开始拖拽**时顺手 `_pressed = false; _longFired = false;`
  —— 这一拖是「滑冷却区」，不该在途中再弹一次长按看牌。
- **短点不经过这三个回调**（没超过拖拽阈值），所以「点选目标 / 长按看牌」完全不受影响。

效果：判定面积 = 整个冷却视口（674 × 621），而不是槽位徽标那 ~190 宽的一条。

## 遗留 / 已知取舍

- **并存时区域档只剩槽位徽标可点**：一行没有任何牌时槽图整块可点；一旦某一行有牌，
  可点区域就只有徽标本身（约 190 × 95）—— 这是用户要的「不与卡牌重叠」的直接后果，
  不是缺陷。手指细的场合可以接受，真机若是反馈偏紧，优先调 `UiTheme.ZonePickableEdge`
  的亮度而不是把判定区域放回卡面。
- **拖拽转交依赖「牌的祖先是 ScrollRect」**：`GetComponentInParent` 找不到就静默不转交
  （手牌本来就不在滚动层里，行为不变）。将来若有别的「带 ScrollRect 的牌区」，
  这条会自动生效，不需要再改。
- **`RowIndexFor`（按祖先名解析行号）仍是纯区域档那一拍在用**：并存时不再走它。
- **⚠ 验证是「合成指针事件」驱动的**：A/B/C/D 四条断言用代码直接构造 `PointerEventData`
  调 `OnCardClicked` / `OnBeginDrag → OnDrag → OnEndDrag`，**没有经过真人手指那一段**
  （`Input` → `StandaloneInputModule` → 射线 → `ExecuteEvents` 分发）。
  也就是说「选中归属」和「转交逻辑」验的是**被测函数本身**是对的；
  「EventSystem 真的会把冷却区迷你卡的拖拽派发给 `CardInteractor`」这一步，
  目前只有**静态层级**作旁证（卡的祖先确实是 `CoolingScroll_Player`，槽图平时不吃射线）。
  真机若仍有「滑不动」的感受，第一个要看的是输入模块有没有更上层的节点抢走事件，
  而不是 `ForwardDragToScroll`。
