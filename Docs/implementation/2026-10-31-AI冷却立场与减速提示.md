# 2026-10-31 · AI 的加速 / 减速立场、玩家被减速的提示

两条一起改，因为它们指向同一件事：**「减速」这个效果在 AI 与界面两侧都太容易被误用 / 漏看。**

## 1. AI 会给自己减速、给对手加速 —— 真因在「合并拍」

用户口径：

> 加速一般是正面效果，即使自己没有牌能加速，也不能给敌人加速。减速一般是负面效果，
> 即使对方没有牌能被减速，也不能给自己减速。

### 1.1 为什么单张拍是对的，合并拍是错的

引擎给加速 / 减速生成的候选**横跨双方**（`EffectContext.TargetSeats` 走 `Participants`：
`{ 施法者, 对方 }`），因为玩家本来就可以自由选。两个 AI 的 `Decide` 里也确实有
`ChooseHasteTarget` / `ChooseSlowTarget` / `ChooseZoneValue` 三个分支，各自按「牌是谁的」过滤。

**问题出在暴风雪（a）这类牌上**：它同时带「加速」与「区域减速」，`EffectWindow` 会把两条
并列的冷却效果**合成一个决策**：

```
Kind = RequestKind.ChooseCooldownEffects     // 不再是 HasteTarget / SlowTarget
MinSelect = 1, MaxSelect = 1
```

`Decide` 里没有这个 Kind 的分支 → 落进默认的 `FirstNonSkip` = **取选项列表里的第一个**。
而选项是按 `EffectSeats = { 施法者, 对方 }` 的顺序拼的，于是：

| 效果 | 第一个选项通常是 | AI 的旧行为 |
|---|---|---|
| 区域减速 | **施法者自己**那一侧 | 把自己冷却区减速 |
| 加速（自己冷却区空着时） | **对方**的冷却牌 | 拿加速去帮对手 |

海涌（q，加速 + 区域加速）因为两边都是加速、且自己在前，碰巧没暴露；暴风雪是重灾区，
而它正是「减速」怪物卡池的核心牌之一。

### 1.2 引擎：把极性写到选项上

`Option.HasteOption`（`Core/Battle/Decision.cs`）：`true` = 加速、`false` = 减速。

为什么不继续读 `DecisionRequest.ContextHaste`：合并拍里那个字段只等于 template
（第一条效果）的极性，第二条的语义在派生的 Kind 里已经丢了。极性只能在生成选项的地方
（`BuiltinEffects.Cooldown` / `CardOption`）写下来，`EffectWindow` 的 `MemberwiseClone`
会把它一起带进合并列表。

### 1.3 策略：`CooldownTargetPolicy`（Core/Ai，两个 AI 共用）

```
立场 2（有利）：加速 → 自己的牌 / 自己那一侧
                减速 → 对方的牌 / 对方那一侧
立场 1（中性）：Seat == -1（雪崩「双方一起」）
立场 0（不利）：反过来
```

- 先按**立场**过滤，再在同档里比偏好：加速挑剩余冷却最小的、减速挑力量最高的、
  区域挑命中张数最多的（保留 2026-09-20 的「先立场、后密度」口径）；
- **一步有利的都没有 → 跳过**（`bestStance <= 0` 且引擎给了 Skip）。
  ⚠ 判据必须看立场本身，不能看总分 —— 同档偏好会往分数上加正数，
  「立场 0 + 剩余冷却很小」会伪装成正分（第一版就这么错过一次，被自测用例抓住）；
- 引擎不让跳过（`SkipOption == null`）时才退而求其次，挑最不伤的那一个
  —— 旧代码在这种情况下会交空回填，`EffectWindow.Submit` 直接拒收 → 空转。

**雪崩（an）单独处理**：它的区域减速是**双方一起**（`Seat = -1`）。旧逻辑把 -1 一律当
「有利」，于是「自己冷却区 3 张、对面 0 张」照样放 —— 纯自我减速。现在数两边的匹配张数，
**对面更多才放**，持平按中性；拿不到 `BattleState`（简单 AI 未注入）时退回中性，不擅自改行为。

### 1.4 合并拍里「只跳过一半」是怎么成立的

合并拍一次只要求选一个选项；没被选中的那条效果保持休眠，引擎会**再发一条**只含它的拍。
所以「自己没牌可加速」时 AI 会先在第一条拍里选**对方的区域减速**，第二条拍再对加速交
「跳过」—— `EffectWindow.Submit` 在整组里看到 Skip 只丢弃**剩下的**那一条，已结算的减速不受影响。

### 1.5 自测

`Tools/RuleSelfTest/RuleAssertions.cs` 的 `CheckTargetPolarity` 新增
`ChooseCooldownEffects` 分支：合并拍的立场**逐选项**读 `Option.HasteOption`，
不再用请求级的 `ContextHaste`（那会把区域减速当成加速放行）。旧实现在这条断言下必挂。

## 2. 玩家被减速的提示

用户口径：

> 当玩家被减速时，需要给予一些额外的提示，例如某一张牌被减速时，这一张牌上加一个特效，
> 某一个区被减速时，这个区加一个特效，否则很容易注意不到。

现状只有「0.7 秒的位移」（`UiLayout.SlowShiftSeconds`），在对面出牌那一拍很容易被漏掉。

| 触发 | 表现 | 落点 |
|---|---|---|
| 玩家自己的某张冷却牌剩余冷却变大（减速 / 重置冷却） | 卡面**插画**闪两下冰蓝（0.9s，`abs(sin(2πt))` 两个包络） | `CardView.PlaySlowFlash`（`UiTheme.SlowFlashCard`） |
| 区域减速命中玩家那一侧 | 那一格**冷却槽底图**闪两下冰蓝 | `CooldownView.FlashSlowZone`（`UiTheme.SlowFlashZone`） |

- **不新建特效节点**：卡面染的是自己的插画（组成式卡面铺满整卡，闪起来就是整张脸），
  槽位染的是 `BindGrouped` 已经在用的 4 行底图；两者都只是 `Image.color`，池化 / 重绑不留脏状态。
- **时序**：回放按批走 —— 一批冷却事件全部过完才 `RaiseStateChanged` → `RefreshAll` 重绑冷却区。
  所以 `BattleUi.HandleBeat` 只**记账**（`_slowCardUids` / `_slowZoneRows`），
  绑完冷却区之后由 `ApplySlowFx()` 统一下发；`Bind` / `Clear` / `OnDisable` 都会停掉脉冲并复位颜色。
- **时长**：这一拍的等待取 `max(0.7 位移, 0.9 闪烁) + 0.06`，否则下一拍重绑会把还没闪完的脉冲掐掉。
