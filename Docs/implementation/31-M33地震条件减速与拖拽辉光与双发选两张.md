## ① 地震：从「无条件减速」改成「若这是你的最后两张手牌，减速」

### 改动

| 位置 | 内容 |
|---|---|
| `Core/Cards/EffectDef.cs` | 新增算子 `SlowIfLastTwoHand = 31`；登记进 `NeedsDecision` |
| `Core/Battle/Resolvers/AttackContext.cs` | `EffectClassifier` 归到 **③ 冷却阶段**（与 `Slow` 同组） |
| `Core/Battle/BattleEngine.cs` | `StartStage3Decision` 加分支：条件成立 → 换成等价的 `EffectOp.Slow` 走原路 |
| `Core/Cards/CardLibrary.cs` | 地震（i）改用新算子，卡面文字「若这是你的最后两张手牌，减速」 |

### 口径

**条件 = 打出之后手上只剩 1 张牌**（= 出牌那一刻手上共 2 张，地震是其中之一）。

判据取「出牌后的手牌数」而不是「出牌前」，是因为 `DoChooseAttackCard` 在进入第 ① 步之前
已经把手牌移走了 —— 走到第 ③ 步时 `Hand.Count == 1` 就等价于「这是最后两张之一」。
条件不满足时 `return false`，整条效果无事发生（不弹决策、不消耗任何东西）。

### 两个必须写下来的坑

1. **归类必须登记。** `EffectClassifier` 的 `default` 落到 `Stage1Power`，而 `AddEffectToStage`
   对 Stage1 里非 `Aura` 的算子照单全收 → 第 ① 步的 `HandleImmediateStage1` 不认识它、
   `StartStage1Decision` 也不认识它 → **静默不结算**，事件流和统计全绿。
2. **复用减速决策时要把 `_activeEffect` 换成等价的 `Slow`。**
   `IssueStage3Repeat` 与 `DoStage3Repeat` 都是按 `Op == EffectOp.Slow` 分「减速 / 加速」两条路的 ——
   带着新算子进去，卡面写着减速、实际在加速。

### 验证

`Tools/RuleSelfTest/EarthquakeScenario.cs`（新），两条断言：

```
[PASS] 地震（i）的 α 效果是「最后两张手牌才减速」的条件算子（A = 1，卡面「若这是你的最后两张手牌，减速」）
[PASS] 地震在手牌只剩 2 张（它是其中之一）时生效：打出后出现减速目标决策（命中 3 次 / 扫了 3 个种子）
[PASS] 对照组：打出后手上还剩 2 张时地震不减速，不得出现减速目标决策（命中 3 次 / 扫了 3 个种子）
```

做法：不碰随机发牌，只在**冷却区已有牌**（否则减速目标一个都列不出来）的那一拍把进攻方手牌
**裁到指定张数**并强制打出地震，然后看第 ③ 步有没有发出 `ChooseSlowTarget`。
两条一起跑通，才说明卡的是「最后两张」而不是「>= 1 张」之类的近似。

## ② 手牌辉光：拖动中的那张亮，拖完就灭（不再粘在第一次点过的牌上）

### 症状（用户报）

> 第 1 张**点击**过的卡，拖拽结束之后再去拖别的卡，发光提示仍然留在第 1 张上，不会转移。

### 根因

两件事凑在一起：

1. 「点一下」会把 `_selectedUid` 置成那张牌（`HandView.OnCardClicked`），而它**只在决策收尾**
   （`BattleUi.ClearDecision → HandView.ClearSelection`）才清 —— 「拖一下再挪个位置」这种
   不提交决策的操作根本不碰它。
2. `Update` 里 `i == _dragIndex` 那个分支**完全不碰 `SetSelected`**。于是「拖动中的卡发光」
   看着像已经实现了，其实是**上一次点击的残留**在撑着：拖第 2 张时，第 1 张仍满足
   `marked`（辉光不灭），而正在拖的第 2 张如果不是之前点过的那张，反而不会亮。

### 改法（`Unity/Ui/HandView.cs`）

- `BeginDrag`：一开始拖就把点击残留收回（`_selectedUid = -1`）—— 手一旦开始拖，
  这一拍的「选中」就该由拖拽接管。
- `Update` 的拖拽分支：显式 `v.SetSelected(true)`，让辉光由「正在被拖」这件事决定，
  不再依赖别处残留的状态。拖拽结束的下一帧走 `else` 分支按 `marked` 重算，辉光自然收掉。

## ③ 敌方双发：让「必须交出两张牌」真的出现在界面上

### 症状（用户报）

> 敌方使用双发的效果未能正常生效。

### 定位

先用 `Tools/RuleSelfTest` 的 trace 证明**引擎侧是好的**：AI（seat1）打出藤蔓（双发）时，
事件流是 `→ 最终进攻力量 5 [双发]`、`防御 seat0 成功（冰风暴＋湍流）` 后两张牌各自进冷却区 ——
`DefenseResolver.BuildOptions(isDouble)` 的成对选项、`DoChooseDefense` 的双张结算都正确。

问题全在**界面**：

```
grep -n "PairCard\|ContextDouble" Assets/Scripts/Unity/    → 0 命中
```

界面**完全不认识**双发：

1. `ClassifyOptions` 只把 `o.Card.Uid` 塞进 `_handPlayable`，组合里的第二张
   （`Option.PairCard`）没进 → 那张牌是暗的，拖不进判定区；
2. `PickCardOption(uid)` 只按 `Option.Card` 匹配 → 玩家拖第一张，**一张就替他把整对交了出去**。
   第二张牌是被替玩家选的，「必须交两张」这条规则在界面上等于不存在。

所以从玩家视角：要么「我只拖了一张，怎么两张都进冷却了」（像双发没生效），
要么「我想用的另一半拖不动」。

### 改法：这一拍改成「连着拖两张」

| 位置 | 改动 |
|---|---|
| `BattleUi.ClassifyOptions` | 记录 `_pendingDouble`（`Kind == ChooseDefense && ContextDouble`）；成对选项的 `PairCard.Uid` 也进 `_handPlayable` |
| `BattleUi.OnHandCardDropped` | 双发走 `HandleDoubleDefenseDrop`：第一次拖进来只**钉住**，第二次与之配对才提交 |
| `BattleUi` 新增 | `FindDefensePair(uidA, uidB)` / `TipDoubleProgress()` / `ClearPairPick()` |
| `HandView` 新增 | `_pinnedUid` + `SetPinnedUid(uid)`；`marked` 判定并入 `_pinnedUid` |

交互细节：

- 第一张钉住后手牌保持辉光 + 上浮（`SetPinnedUid`，**不会被下一次拖拽清掉** —— 这正是它
  不能复用 `_selectedUid` 的原因），提示条切成「已选 1 张，再拖一张凑成一对」；
- 再拖**同一张** = 取消这一张；
- 两张凑不成引擎给过的组合 → **保留第一张**、提示换一张（不是把玩家已选的清掉）；
- 配对只在引擎给的成对选项里**找**（`FindDefensePair`），界面不拼选项、不判规则（铁律 3）。
