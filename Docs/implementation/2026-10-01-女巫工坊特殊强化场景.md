# 女巫的工坊 · 特殊强化场景（P6）

> **性质**：现行实现记录 —— `WitchWorkshop.unity` 单场景（点水晶球 → 两个空位各选一张牌 → 确认 → 第一张从卡池消耗），Core 的 `WitchWorkshop` 规则、美术归位、构建器与视图族（与当前代码一致，可照此改）
> **最后核对**：2026-10-01

## 背景与目标

用户口径（2026-10-01）：

> 本游戏当中还有另外一种强化卡牌的场景，女巫的工坊。用到的背景美术资源已经放到了 Art 文件夹下。
>
> 1. 玩家点击水晶球之后，弹出强化卡牌界面，如果玩家当前卡池中只有 8 张牌，则改为提示无法进行特殊强化。
> 2. 此强化界面由两张空位来组成。玩家点击其中一个空位之后，就会弹出当前卡池的浏览，然后从中选择一张牌。当两个空位都选择了之后，就可以点击确认。这两个空位当中的牌不可以相同，否则无法确认。
> 3. 第一张牌是会被消耗掉的（从卡池当中移除）
> 4. 第 2 张牌只能放置当前只有一个效果且没有任何强化的卡。
> 5. 先不做强化的具体效果，之后再做。

### 确认口径（一问一答）

| # | 问题 | 用户答复 |
|---|---|---|
| 1 | 「卡池只有 8 张」的判据 | **≤ 8 张就禁止**（8 是起始牌池；「只有 8 张」= 还没额外拿到牌） |
| 2 | 「只有一个效果」怎么判定 | **`CardDef.Effects` 恰好 1 条**（**光环也算一条**） |
| 3 | 第一张牌被消耗后要不要持久化 | **只在本局内存生效**（退出重进场景恢复；正式接冒险 run 时交给存档层） |
| 4 | 两个空位是角色固定还是按顺序 | **固定：左 = 献祭，右 = 强化目标** |

### 本次不含

- **强化的具体效果**（用户明说「之后再做」）—— 确认之后此刻只发生「第一张离场 + 节点结束」，
  **不**生成新卡、**不**改第二张牌的任何字段；
- 地图层 / 存档 / run 持有卡（与 P5 同一条边界，见下 §与 P5 的关系）；
- 卡池正式来源（调试入口里那段「从卡池资产解析」是**调试实现**）。

## 方案与影响

### 一、Core：`WitchWorkshop`（规则收敛在一处）

新增 `Assets/Scripts/Core/Cards/WitchWorkshop.cs`（零 `UnityEngine` 依赖）：

| 成员 | 口径 |
|---|---|
| `MinPoolSize = 9` | 卡池 ≥ 9 张才能开工。⚠ 判据是 **≤ 8 禁止**，不是 `== 8`（用户确认） |
| `CanOpen(poolCount)` / `OpenBlockedReason(poolCount)` | 卡池够不够开；不够时连浮层都不弹，只在场景里提示一句 |
| `CanBeSacrifice(def)` | 第一个空位**不限牌**（已强化过的也能献祭），只要求非空 |
| `CanBeTarget(def, out reason)` | 两条拒绝：**已经是强化过的牌**（`CardUpgrade.IsUpgraded`）、**效果条数 ≠ 1**（`def.Effects.Count`）。理由文案直接给玩家看 |
| `BothSlotsFilled(a, b)` | 只判「两个都填了没有」——**不是**「能不能确认」 |
| `CanConfirm(a, b, out reason)` | 三条：两个都得有牌、**不能是同一张牌**（按 `Id` 比）、目标牌仍然合格 |
| `ConsumedId(sacrifice)` | 确认后该从卡池移除的 ID = **第一个空位**那张 |

**为什么和 `CardUpgrade` 并存而不是合并**：两者是两条不同的口径 ——

| | `CardUpgrade`（P5 · 石台） | `WitchWorkshop`（P6 · 水晶球） |
|---|---|---|
| 代价 | 免费 | **献祭一张牌** |
| 对象 | 一次一张 | 两个空位（素材 + 目标） |
| 目标限制 | 力量不可为 X / 不能带「进攻力量不能增加」/ 未达 9 | **恰好 1 条效果 + 从未强化过** |
| 结果 | 基础力量 +2（封顶 9） | **待定**（本批不做） |

**为什么判据不写卡 ID**：与 `CardUpgrade` 同一条理由 —— 效果条数与 `+` 后缀都是卡表里
已有的**事实**，以后加牌不用回来补分支。

**⚠ 刻意没有排除「力量为 X」的牌（模仿 x）**：`CardUpgrade` 排除它是因为那条口径是
「基础力量 +2」，X 加不了；本批**还没有强化效果**，不该提前替将来的效果定规矩。
等效果定稿再回来看这一条。

**⚠ 「两个空位不能相同」不写进 `CanBeSacrifice`**：那是**一对**牌的性质，不是单张牌的性质。
写成单张判据就必须把「另一个空位放了什么」当参数传进去，反而更难读。

### 二、场景（`WitchWorkshop.unity`）

| 文件 | 职责 |
|---|---|
| `Assets/Scripts/Unity/Editor/WitchUiBuilder.cs` | 构建器（菜单「魔法乱斗/P6 · 构建 WitchWorkshop 场景」）：建场景 + Canvas + 存 Prefab + 场景根挂调试入口。幂等、无确认弹窗（可被脚本 / MCP 反射调） |
| `Assets/Scripts/Unity/Ui/WitchView.cs` | 场景视图：水晶球 / 离开 / 标题 / 提示，并把两层浮层暴露给上层 |
| `Assets/Scripts/Unity/Ui/WitchLayerView.cs` | **主浮层**（两个空位 + 状态行 + 确认 / 关闭） |
| `Assets/Scripts/Unity/Ui/WitchSlotView.cs` | 一个**空位**（底衬 + 卡面 + 「+」+ 献祭暖光 + 描边 + 命中区 + 角色标签） |
| `Assets/Scripts/Unity/Ui/WitchPickerView.cs` | **卡池浏览层**（遮罩 + `Peek_Panel` + 6 列网格 + 关闭） |
| `Assets/Scripts/Unity/Ui/WitchSceneEntry.cs` | 单场景调试入口（E1–E4 契约）：读卡池 → 判门槛 → 开浮层 → 选两张 → 确认消耗 → 结束节点 |

**节点结构**（`WitchCanvas.prefab`，与商店 / 强化同一套画布口径）：

```
WitchCanvas                       ← WitchView
├─ Bg_WitchWorkshop               背景 cover（1920×1080.6，放大 1.14833×）
├─ OrbHit                         水晶球命中区（透明矩形，唯一吃「点水晶球」的东西）
├─ Title / Hint / LeaveButton
├─ Layer                          ← WitchLayerView（默认失活）
│  ├─ Veil                        遮罩（点它关闭）
│  └─ Panel                       Peek_Panel
│     ├─ Title                    特殊强化
│     ├─ SlotSacrifice            ← WitchSlotView（左 · 献祭）
│     ├─ SlotTarget               ← WitchSlotView（右 · 强化目标）
│     ├─ Arrow                    两个空位中间的「→」
│     ├─ Status                   状态行（提示 / 校验失败的原因）
│     ├─ CloseButton / ConfirmButton
└─ Picker                         ← WitchPickerView（默认失活，排在 Layer 之后 = 更上层）
   ├─ Veil
   └─ Panel                       Peek_Panel
      ├─ Title / Hint
      ├─ Cards（ScrollRect → Viewport → Content → CellTemplate[UpgradePickerCell] + Scrollbar）
      ├─ Empty
      └─ CloseButton
```

**卡面只 instantiate、绝不新建第二份**（铁律 9）：空位里与浏览层里的卡都是
`Assets/Prefabs/Ui/CardView_Hand.prefab` 的实例，尺寸由 `CardView.SetFaceWidth` 在运行时给。

**浏览层的格子复用 `UpgradePickerCell`**（不新建第二个格子类）：「一格 = 卡面 + 压暗纱（含原因）
+ 整格命中区」这套结构两个场景一模一样，抄一份只会让「格子该怎么摆」有两个来源。
节点树本身没法跨 Prefab 复用，所以 `WitchUiBuilder.BuildCellTemplate` 里那份**结构**是重写的，
但**组件**是同一个。

**⚠ 主浮层与浏览层是两层**（用户口径「点击其中一个空位之后，就会**弹出**当前卡池的浏览」）：

- 主浮层自己有「确认」，所以**浏览层点一张牌就直接返回**（下单式）——
  在浏览层再来一个「确认」是两层确认，玩家会懵；
- 两层都自己开关自己（`Show` / `Hide` 幂等，`Hide` 时才发 `Closed`），
  上层直接订阅它们的事件（`WitchView.Layer` / `WitchView.Picker`）——
  中间再包一层转发只会多出「忘了接某个事件」的机会。

### 三、版式账

场景层与商店 / 强化**同一条水平带**（标题 `y = 1002`、引导 `y = 158`、离开键右下 64 / 44）。

面板取 `ShopBagPanelWidth × ShopBagPanelHeight`（1620×880），下面这些是**面板内部坐标**
（锚点与轴心都是 `Mid`，原点 = 面板中心，纵向可用 y ∈ [−440, 440]）：

| 元素 | 中心 Y | 高度 | 上下余量 |
|---|---|---|---|
| 标题 | 370 | 60 | 面板顶 440 之下留 40 |
| 两个空位 | 170 | 292 | 标题底 340 之下留 24 |
| 空位标签 | −30（= 空位下缘再往下 30） | 48 | 空位底 24 之下留 42 |
| 状态行 | −160 | 56 | 标签底 −54 之下留 79 |
| 底部按钮 | −378 | 68 | 面板底 −440 之上留 28 |

横向：两个空位中心 `x = ±265`（步进 **530**），中间净空 300 放「→」；
状态行宽 980（±490）；两个按钮各 240 宽、中心 `x = ±630`。

**空位底衬 / 描边复用 `CardBox` / `CardBox_Line` 九宫格**（border 38，与卡面自己的底衬同一批图）——
不新增美术。`Image.type` 必须是 `Sliced`：空位是 230×292 的竖长条，而那两张图是 160×160 的方图，
不用九宫格会把圆角抻成椭圆**且零报错**。

**描边颜色是「逻辑态」不是「提示类颜色」**：未选 = 冷灰、已选 = 暖金，两个色值都在 `UiTheme`，
运行时只做二选一（`WitchSlotView.Bind`）。

### 四、水晶球命中区

四个数是**对着背景图量的像素**（左上为原点）：`(645, 470)–(800, 615)`，
换算走 `UiLayout.WitchBgPointToCanvas`（背景 cover 放大 **1.14833×**；忘了乘缩放会整块缩在
画面左上角，零报错 —— 商店首次落版就是这么错的）。

落成画布坐标 = center **(829.7, 457)**、size **178×166.5**。

**校验方式不是肉眼**：在 Play 截图上按「亮蓝紫」（`B > G+25 && B > R+8 && B > 110`）做像素检测，
球体实际落在**画布 x 767.3…915.3 / y 378.0…525.3**，**完整包含于**命中区之内 ——
也就是说球体 100% 可点，多出来的一圈本来就是球周围的暗色桌面。

### 踩坑（本轮新踩的两条）

- ⭐⭐ **`Rebuild()` 之后同帧连点 UI 时，`GridLayoutGroup` 还没排完，射线会落到面板上**
  （`RaycastAll` 的 `hits[0]` 是 `Panel`、`GetEventHandler<IPointerClickHandler>` 返回 `null`）。
  症状是「点格子显示 `over=Panel handler=NULL`、状态完全没变」——**零报错**。
  真机不受影响（玩家点击必然在下一帧），但**自动化验证里必须补一次
  `LayoutRebuilder.ForceRebuildLayoutImmediate(content)`**，否则会误判成「格子点不动」。
- ⭐ **`AssetDatabase.MoveAsset` 之后 Unity 会留一个模态框**
  「`Unapplied import settings for '<旧路径>'`」——它**挂住主线程**，表现为
  所有 MCP 工具都报 `Unity session not ready (ping not answered)`，
  而 `manage_editor(telemetry_status)`（走 HTTP 层、不需主线程）**照常返回**。
  **判据**：`telemetry` 通 + 其它工具不通 = 主线程被占住（不一定是在跑长任务）。
  **解围**：枚举顶层窗口找 `#32770` 对话框（本轮是 `Inspector - Unsaved Changes Detected`），
  对「Discard」按钮发 `BM_CLICK`。选 Discard 是因为磁盘上的 `.meta` 是导入流程刚写好的正确值，
  未应用的那份是进程内的临时状态。

## 遗留

- **强化效果没做**（用户明确「之后再做」）：确认之后只消耗第一张。等效果定了，
  往 `WitchWorkshop` 加一条「目标牌变成什么」的口径，再接 `WitchSceneEntry.OnConfirmClicked`。
- **卡池只在本局内存里变**（用户确认）：退出重进场景会恢复成资产里那份。
  正式接入冒险 run 后换成「向存档提交一次消耗」。
- **`WitchSceneEntry` 里那段「从卡池资产解析持有牌」是调试实现** ——
  与 `ShopSceneEntry` / `UpgradeSceneEntry` 同一待遇，正式接入时整段换成从 run 读。
- **默认卡池 `UpgradePool` 只有 8 张 → 进 Play 默认看到的是「无法进行特殊强化」**。
  这是**正确行为**；想看能开工的分支，把 `WitchSceneEntry._pool` 指向 `BattlePool`，
  或在 `_cardIds` 里手写 9 个以上的卡 ID。
- **`WitchWorkshopScenario` 没有跑万局回归**：本批对 `Core` 只**新增**了一个不参与战斗的
  判定类，没有改动任何既有结算路径，所以没有重跑（判据：`git diff` 里 `Core/` 只有这一个新文件）。
- **⚠ 千图马克手写体的「7」看起来像「1」**（本轮顺带发现，**既有现象、非本批引入**）：
  卡面上力量 7 的牌（寒流 / 沉重打击 / 地动波 / 淬火 / 充能 / 毒刺 / 闪电球）数字读起来像 1。
  已核实卡面文本确实是 `'7'`（`TMP[0] '7' size=160`），是**字形**问题，不是数据问题。
  要改就得换字体或给该字体换字形。
- 未做真机手指点击（与 M25–P5 同一条遗留：合成指针验过，真人拖拽 / 点击没连起来验）。
