## 2. 需求 1 · 充能（`am`）效果无限循环

### 2.1 卡面与预期顺序

`CardLibrary` 里充能是 `am`：`A(Haste, 1)` + `A(CoolHandForHaste, 1)`。
两者都被 `EffectClassifier` 归到 **Stage3Cooldown（③ 冷却改动）**，所以

```
_atk.Stage1 = []                                   // ① 空
_atk.Stage3 = [ Haste(1), CoolHandForHaste(1) ]    // ③ 两项
```

预期节奏（用户口径，与队列顺序一致）：

```
出牌 → ① （空） → ② 对方防御 → ③ 加速一次 → ③ 问一次「选冷却手牌」→
     每冷却一张再发一次加速 → ④ ⑤ 收尾
```

### 2.2 现象

打完充能之后 `② 防御 → ③ 加速 → ③ 选牌` 会**无限重放**：
防御问了一次又一次，加速与选牌也跟着一遍遍重来，对局永远走不到 ④。

### 2.3 根因：一个游标被两个阶段共用，而 `FinishStage1` 会把它归零

`BattleEngine` 里：

- `RunStage1()` 用 `_cursor` 遍历 **`_atk.Stage1`**；
- `RunStage3()` 用 **同一个 `_cursor`** 遍历 **`_atk.Stage3`**；
- `FinishStage1()` 的第一句就是 **`_cursor = 0`**，随后 **直接落到 `Phase.AwaitDefense`**。

而 `DoCoolHandSelection` 三个分支原先**统一**写 `_phase = Phase.Stage1`：

```csharp
case EffectOp.CoolHandForAtk:   _atk.EffectBonus += ...; _phase = Phase.Stage1; break;
case EffectOp.CoolHandForCombo: ...;                     _phase = Phase.Stage1; break;
case EffectOp.CoolHandForHaste: _pendingHastes += ...;   _phase = Phase.Stage1; break;   // ← 错在这里
```

磁暴 / 电弧是 ① 类效果，回 Stage1 没问题；**充能是 ③ 类效果**，回 Stage1 就同时踩两个坑：

| # | 连锁后果 | 现象 |
|---|---|---|
| ① | `FinishStage1()` 把 `_cursor` 归零 → `RunStage3` 从 `_atk.Stage3[0]` 重来 | 「加速」与「选择冷却手牌」各自**再走一遍** |
| ② | `FinishStage1()` 直接落到 `AwaitDefense` | **又问一次防御** |

两者合起来 = `防御 → 加速 → 选牌 → 防御 → 加速 → 选牌 → …` 的**无限循环**。

### 2.4 修法

```csharp
case EffectOp.CoolHandForHaste:
    _pendingHastes += cooled * _activeEffect.A;
    _phase = Phase.Stage3;   // ← 原来是 Phase.Stage1
    break;
```

一句话规则：**效果回到「它自己所属的那个阶段」继续**。
归属由 `EffectClassifier.Classify` 唯一决定；① 类回 ①、③ 类回 ③。
「获得加速 ×N」的发放仍然在 `RunStage3` 开头那段 `_pendingHastes` 里，位置不变。

### 2.5 为什么万局统计抓不到它

重放期间**每一条事件单独看都合法** —— 冷却值不越界、手牌守恒成立、光环归属正确，
胜负也会照常打出来（只是这一局被拖得极长）。错的只有
「同一段进攻里防御结算了 N 次」这个**跨事件**的事实。所以断言只能加在事件流上。

### 2.6 回归断言（`RuleAssertions.EventWatcher`）

新增 `_defenseResolvedForAttack`：

- `AttackDeclaredEvent` → 结掉上一段、本段计数归 0；
- `DefenseResolvedEvent` → 本段计数 +1（免疫那条臂同样计入，它也发这张事件）；
- `TurnStartedEvent` / `GameOverEvent` → 结掉当前段；
- 结账时 `> 1` 就报 **「一段进攻里结算了 N 次防御 —— 结算阶段被重放」**。

**三个结账点缺一不可**：只挂在「下一段进攻开始」会让每局最后一段永远不被检查，
而那正是缺陷最容易藏身的位置。

### 2.7 负向反证

把 `DoCoolHandSelection` 临时改回 `_phase = Phase.Stage1` 重跑，断言**真的会咬**：

**坏版本（`_phase = Phase.Stage1`）**：同一支探针扫 30 个种子，其中 **16 局真的打出了充能**，
**16/16 全部报违规**，而且**第 2 次防御一发生就抓到**（`steps` 只有 6～35）：

```
seed 2：打过充能  steps=6
   首次充能那一段：AttackDeclared(充能) → DefenseResolved#1 → 选牌→送入冷却 ×5 → DefenseResolved#2
   ✘ 违规：一段进攻里结算了 2 次防御 —— 结算阶段被重放（效果把阶段写回了它已经走过的分支，
           后果是对局卡在同一段进攻里出不来）
```

注意这条序列里 **第一次防御之后又出现了一次 `DefenseResolved`** —— 这正是用户描述的那个错节奏。

**修复版**：同样 30 局、同样 16 局打出充能，**违规 0**，且事件顺序正是用户要的那条：

```
seed 3：打过充能  steps=46
   首次充能那一段：AttackDeclared(充能) → DefenseResolved#1 → 加速
                   → 选牌→送入冷却 ×4 → 加速 ×5 → ── 本段进攻结束（下一段开始）──
```

即「**防御 → 加速 → 选择冷却手牌加速 → 每冷却一张再加速 → 结束**」，与用户口径逐项对上。

⚠ **完整自测在坏版本下跑不完**：实测 8 局 > 11 分钟仍未结束（而修后 60 局 4 秒）——
重放让对局卡在同一段进攻里出不来，只能靠 `RunSingleGame` 的 20000 步兜底打断。
所以负向反证用的是**「一有违规就立刻停」的小探针**：
`E:/UnityProject/_tmp_build/m32_neg/`（`<Compile Include>` 链接 Core 源码 + 本工程的
`RuleAssertions.cs`，不走 `RuleSelfTest.csproj`）；
脚手架 `m32_verdict.py` 自动「临时改坏 → 跑 → 还原 → 再跑」并在 `finally` 里兜住还原。

改回 `Phase.Stage3` 后复跑恢复全绿。

## 3. 需求 2 · 确认键：位置 + 背景

### 3.1 位置：M31 换算时把符号写反了

M31 把确认键从「面板」（尺寸随张数变宽）搬到「满屏根 `HandPickLayer`」下的固定宽
`ConfirmSeat`，注释里写的换算是**对**的：

> 面板底边在屏幕中心下方 `HandPickPanelHeight/2` 处 ⇒ 相对屏幕中心
> `y = CenterFromBottom − PanelHeight/2`

但代码里写成了它的**相反数**：

```csharp
new Vector2(0f, UiLayout.HandPickPanelHeight * 0.5f
                - UiLayout.HandPickConfirmCenterFromBottom)      // = +220.5 ✘
```

于是按钮被**镜像到面板顶部**（y = +220.5），压在标题牌位与「N / M」计数上，
而面板底边那块**原图自带的按钮座**空着 —— 正是用户圈红框的那个位置。
Unity 对这种「位置算错」**零报错**，只能靠截图发现。

**修法**：换算收进 `UiLayout`（尺寸与版式算术的唯一落点），并写成负值：

```csharp
public static float HandPickConfirmCenterYFromCenter()
{
    return HandPickConfirmCenterFromBottom - HandPickPanelHeight * 0.5f;   // = 57.5 − 278 = −220.5
}
```

### 3.2 背景：不再画自己的底图，改用面板自带的按钮座

M30 给确认键换过素材（`HandPick_Confirm.png`，626×174 的亮蓝六边形按钮条），
九宫格横向拉伸后用 258×58 渲出来 —— 纵向被 174 → 58 **硬压**，观感是一条发白的扁条。

而 `Peek_Frame.png` **本身就带**一块做好的底部按钮座（量图：内槽 257×58、中心距底边 57.5）。
用户口径就是「用那个」。

**修法**：按钮不画底图，只留文字 + 命中区。

```csharp
btnImg.sprite = null;              // 没有图 = Image 画一块纯色矩形，颜色透明 → 什么都看不见
btnImg.color = UiTheme.HandPickConfirmOn;   // 纯白：让 Button.colors 的 tint 说了算
btnImg.raycastTarget = true;       // 透明也要吃射线，否则点不动
```

⚠ **透明 `Image` 照样是命中区**：UGUI 的 `Image.IsRaycastLocationValid` 在
`alphaHitTestMinimumThreshold == 0`（默认）时直接 `return true`，
所以不需要另加一块不可见 Graphic。

**两态配色**（`UiTheme`）：

| 常量 | 旧 | 新 | 为什么 |
|---|---|---|---|
| `HandPickConfirmOn` | `Color.white` | `RGBA(1,1,1,0)` **全透明** | 任何不透明色都会盖住面板自带的按钮座 |
| `HandPickConfirmOff` | `#2A3742` 实色 | `RGBA(0.055,0.105,0.155, 0.55)` **半透明暗纱** | 电弧 / 漩涡是「必须选够才能确认」，得有个「现在还不能按」的反馈；它是**纱**不是底图，alpha 一大就会在座的斜角外露出方块边 |

`HandPick_Confirm.png` 素材与它的 border 常量**保留**（仍在 `PeekSpritePaths` 里做导入参数校验），
只是当前没有消费者 —— 将来要用不必再回头收拾 `.meta`。

## 6. 顺带拆掉的地雷：Prefab 里 8 处 `missing script`

本轮第一次跑构建菜单时，Unity 报了 **8 次**
`Error while saving Prefab: 'Assets/Prefabs/Ui/BattleCanvas.prefab'. You are trying to save a Prefab
with a missing script. This is not allowed.` —— **Prefab 一个字节都没落盘**（尺寸与备份完全一致），
而构建流程本身「看起来」是跑完的。

**定位**：`m_Script: {fileID: 0}` 共 8 处，所属 GameObject 是
`SlotL_CD1…4` + `SlotR_CD1…4`（左右冷却槽的 8 行）。

**根因**：`ZoneSlotClickCatcher` 原先与 `CooldownView` **同写在 `CooldownView.cs` 里**。
Unity 的 `MonoScript ↔ 类` 对应关系靠**文件名** —— 同一个 `.cs` 里的第二个 MonoBehaviour
没有自己的 `MonoScript` 资产，一旦被写进 Prefab，`m_Script` 就是 `{fileID: 0}`。
它是怎么进去的：`CooldownView.Awake` 在运行时 `AddComponent`，
只要有人在 **Play 模式下**把场景实例写回 Prefab（构建器存盘 / 手工 Apply），
这 8 个组件就带着空脚本引用进了 Prefab。

这正是 **M25 `PeekCardSlot` 那条教训的第二次发作**（当时也是 8 个牌位、也是零报错）。

**修法**：

1. `ZoneSlotClickCatcher` 拆成独立文件 `Assets/Scripts/Unity/Ui/ZoneSlotClickCatcher.cs`；
2. 重跑 **M11 `RunAll()`** → 重建 ArtLayer 会重新生成那 8 行，坏的组件随之消失；
3. 补跑 **M8/M9 接线**（M11 推倒重建后必须补跑，否则 `BattleUi` 的槽位引用会变空）。

**验证**：`m_Script: {fileID: 0}` 计数 **8 → 0**，Prefab 重新落盘（尺寸 1 186 903 → 1 133 186），
console 0 error。

## 8. 本轮踩的坑（供后来者）

1. ⭐⭐ **`Edit` 工具会静默不落盘**（本项目铁律第 8 条）—— 本轮又中一次：
   改了 `BuildHandPickSlot` 的**形参**却漏掉**调用点**，Unity 报
   `CS1501: No overload for method 'BuildHandPickSlot' takes 3 arguments`。
   **改完关键代码先 `Grep` 一次再跑**。
2. ⭐ **`DecisionRequest` 的 `Kind` / `Options` / `Seat` / `Title` / `MinSelect` / `MaxSelect`
   都是「字段」不是「属性」**（`Option.Card` / `Option.Index` / `CardInstance.Uid` 同理）。
   反射探针里用 `GetProperty` 拿到的是 `null`，然后在 `.GetValue()` 上抛
   `NullReferenceException`，**看不出是哪一行**（`execute_code` 只给一个 IL 偏移）。
   保险做法：反射前先对每个 `MemberInfo` 打一次 `!= null`，再逐句 `AppendLine` 标记。
3. **`BattleEngine.Create` 有可选参数**（`Create(int seed, IDealPolicy dealPolicy = null)`）→
   `GetMethod("Create", new[]{ typeof(int) })` 匹配不到（可选参数仍算一个形参），
   要用 `GetMethod("Create")` 并传 `new object[]{ seed, null }`。
4. **MCP 驱动构建菜单之前，先确认 Prefab 会不会因为「missing script」被拒绝保存** ——
   报错只在 Console 里，构建返回值一切正常，**Prefab 却是旧的**。
   判据：`grep -c "m_Script: {fileID: 0}" BattleCanvas.prefab` 必须为 0，
   并且比对构建前后的 **Prefab mtime / 尺寸**。

   `_available` 就是 0（本轮实测）。
