# 04 · 架构与接口

> `MagicBrawl.Core` 的数据模型与对外契约。Core 是**纯 C#、零 UnityEngine 依赖**，
> 由 asmdef 的 *No Engine References* 在编译期强制。

---

## 1. 分层与依赖

```
Core 基础模块（M1 CardLibrary / M2 PlayerState / M3 CooldownOps / M5 SimpleAi）
        ↓
Core 结算引擎（M4 BattleEngine）
        ↓
表现桥（M6 BattleDriver）
        ↓
表现层 UI（M7 UiKit / M8 BattleUi / M9 DealUi / M10 SettingsUi）

旁路：tools/RuleSelfTest ──链接源码──> Core
```

**铁律**

1. `Core` 出现 `using UnityEngine` = 架构违规（编译期拦截）。
2. 依赖只能向下；**表现层不得反向调用引擎**，只能「读快照 + 订阅事件」＋「提交决策」。
3. 所有随机走自实现 `Rng`（显式种子），保证确定性。
4. 语言锁 **C# 9**，禁用 C# 10+ 语法。

## 2. 数据模型

```csharp
namespace MagicBrawl.Core
{
    // ── 效果定义 ──────────────────────────────────────────
    public enum EffectTrigger { Attack, Defend, Special, Passive }

    public sealed class EffectDef
    {
        public EffectTrigger Trigger;      // α / β / γ / 常驻
        public EffectOp      Op;           // 算子，见 §3
        public int           A, B, C;      // 参数（阈值 / 数值 / 方向）
        public AuraKind      Aura;         // Op == Aura 时有意义
        public bool          Mandatory;    // [强制]
        public string        Text;         // 卡面显示文本
    }

    // ── 卡牌静态定义 ─────────────────────────────────────
    public sealed class CardDef
    {
        public string Id;                  // "a" .. "an"
        public string Name;                // 暴风雪
        public int    Power;               // 力量值
        public int    Cooldown;            // 基础冷却值
        public bool   HiddenPower;         // 模仿：卡面显示 "?"
        public List<EffectDef> Effects;
    }

    // ── 对局中的卡牌实例 ─────────────────────────────────
    public sealed class CardInstance
    {
        public CardDef Def;
        public int  RemainingCooldown;     // 仅当在冷却区时有效
        public int  AuraTokens;            // 未消耗的光环指示物数（双光环 = 2）
        public bool AuraLive;              // 是否已进入冷却区（光环生效的前提）
        public bool RemovedFromGame;       // 漩涡：永久移出
    }

    // ── 玩家状态 ─────────────────────────────────────────
    public sealed class PlayerState
    {
        public int  Hp, MaxHp;             // MaxHp 可被削到 0 → 即刻死亡
        public bool IsAi;
        public List<CardInstance> Hand;
        public List<CardInstance> CoolingZone;
    }
}
```

**为什么不用 ScriptableObject**：Core 需要能在 `dotnet` 下独立编译，`ScriptableObject` 会把 `UnityEngine` 拖进来。后续若需要在 Inspector 里编辑卡表，再加一层只读适配器即可。

## 3. 效果算子（`EffectOp`）

40 张卡全部映射到这 **31 个算子**上（`Assets/Scripts/Core/Cards/EffectDef.cs` 为实现唯一依据）：

| 分组 | 算子 | 语义 |
|---|---|---|
| 冷却 | `Haste` `Slow` | 单张 ±1（A = 次数，可分配给同一张或不同张） |
| | `SlowIfLastTwoHand` | 地震：**本牌是「你的最后两张手牌」之一**时才减速（A = 次数；条件不满足则整条不结算） |
| | `HasteZone` `SlowZone` `SlowZoneBoth` | 区域类（k 由决策给出；Both = 同时作用于双方，A = k） |
| | `Refresh` `ResetCooldown` | 立即冷却完成 / 重置为基础冷却 |
| | `RemoveFromGame` | 永久移出游戏（A = 移出后获得的加速次数） |
| | `HastePerHpLoss` | 己方每损失 1 点生命值加速一张**不同**的牌（瀑流） |
| 力量 | `AtkPlus` `DefPlus` | 本次进攻 / 防御力量 +A |
| | `AtkPlusPerCooling` | 冷却区每有一张牌 +A（不含正在打出的这张） |
| | `AtkPlusPerHpLoss` | 双方每合计损失 1 点生命 +A |
| | `DoubleAtkBonus` | 本牌获得的**全部来源**额外进攻力量翻倍 |
| | `NoAtkBuff` | 本牌的进攻力量不可增加 |
| 攻防结构 | `Combo` `Double` `Guard` `QuickRefill` | 连击 / 双发 / 守护 / 快速回填 |
| | `CoolMinusIfUnblocked` `SlowIfUnblocked` `ExtraDamageIfUnblocked` | 「对方无法防御时」三种分支 |
| 光环 | `Aura` | 记录一枚指示物，配合 `AuraKind` |
| 手牌操作 | `CoolHandForAtk` `CoolHandForCombo` `CoolHandForHaste` | 把手牌送入冷却，换取 +力量 / 连击 / 加速 |
| 情报 | `LookAndCool` | 随机查看对方一张手牌，满足阈值则送入冷却（A = 阈值，B = 方向，C = 额外冷却修正） |
| 生命 | `HealMinusMax` | 恢复 A 点、上限 −B（先回血 → 再削上限 → clamp） |
| 复制 | `Copy` | 模仿（A = 目标的基础冷却值） |
| 特殊 | `ReadyRefresh` | 潮汐 γ：本牌冷却完毕时使另一张牌也立即冷却完成 |

> **与早期草稿的差异**：初版写「24 个算子」但实际列了 29 个；实现时又补了 `HastePerHpLoss`
> （瀑流的「每损失 1 点生命加速一个不同法术」在初版算子表里没有对应项）；
> 2026-09-23 又补了 `SlowIfLastTwoHand`（地震从「无条件减速」改成「最后两张手牌才减速」——
> 本作不允许同一个算子带两种触发条件，所以条件减速是独立算子）。现统一为 31 个。

**算子归属哪一步结算**，由 `Battle/Resolvers/AttackContext.cs` 里的 `EffectClassifier` 决定 ——
这是「六步结算顺序」的唯一落点，新增算子必须同时在分类器里登记。

```csharp
public enum AuraKind { AtkPower, DefPower, Combo, ImmuneHigh, ImmuneLow, AtkOrDefPower }
```

## 4. 引擎契约

```csharp
public sealed class BattleEngine
{
    public BattleState State { get; }
    public DecisionRequest Pending { get; }   // null 表示可以继续推进
    public bool IsOver { get; }

    public void Advance();                         // 推进到下一个决策点或终局
    public void Submit(DecisionResponse response); // 回填外部决策
    public event Action<BattleEvent> OnEvent;      // 结构化事件流
}
```

### 为什么是「暂停-恢复状态机」

规则结算天生**同步顺序**，而 Unity UI **异步等点击**。引擎推进到需要外部输入时就停下、抛出 `DecisionRequest`：

```
AI 座位   → driver 调 ai.Decide(req) 立刻拿答案 → Submit → Advance
玩家座位  → UI 渲染 req.Options → 玩家点选 → Submit → Advance
```

好处：引擎不依赖协程、不依赖 `MonoBehaviour`；自测时两个座位都是即时的，可一路循环到终局。

### 决策请求

```csharp
public sealed class DecisionRequest
{
    public int       Seat;                   // 谁要决策
    public RequestKind Kind;                 // 见下表
    public IReadOnlyList<Option> Options;    // 全部合法选项（含 Skip，除非 [强制]）
    public string    Prompt;                 // 给 UI 的提示文案
}

public enum RequestKind
{
    ChooseAttackCard,     // 进攻：出哪张牌
    ChooseDefense,        // 防御：放弃 / 出哪张
    ChooseAuraUse,        // 是否消耗光环指示物、用哪一个
    ResolveOrder,         // 同优先级效果的顺序
    ChooseHasteTarget, ChooseSlowTarget,
    ChooseZoneValue,      // 区域加速/减速：选剩余冷却值 k
    ChooseRefreshTarget,  // 立即冷却完成 / 重置冷却
    ChooseCoolHandCards,  // 把手中哪些牌送入冷却
    ChooseRemoveFromGame, // 漩涡
}
```

> **关键设计**：「防御方不能打出挡不住的牌」这条规则，在**引擎生成 `Options` 时就已经过滤掉**——
> UI 与 AI 都不可能选到非法项。规则约束只收敛在 M4 一处，上层无需重复判断。

## 5. 事件流

```csharp
public abstract class BattleEvent { public int Seq; }

AttackDeclared      // 进攻方打出某张牌
AuraConsumed        // 消耗了一枚光环指示物
DefenseResolved     // 防御结果（成功 / 放弃 / 无牌可挡）
DamageTaken         // 掉血（含来源）
HpMaxChanged        // 生命上限变化
CooldownChanged     // 某张牌剩余冷却变化（含回手）
CardDrawn           // 补牌 / 回手
HandRevealed        // 查看对方手牌
CardRemovedFromGame // 漩涡
TurnStarted         // 半场开始（触发冷却 −1）
GameOver            // 胜负
```

M6 订阅这些事件做动画，M4 完全不知道 UI 存在。

## 6. 冷却系统（M3）

唯一允许修改 `RemainingCooldown` 的入口，其他模块一律通过它：

```csharp
public static class CooldownOps
{
    // 进攻开始：进攻方自己冷却区全体 −1，归 0 立即回手
    public static void TickOnAttackStart(PlayerState owner, List<CooldownChange> sink);

    public static bool TryHaste(PlayerState owner, CardInstance c, List<CooldownChange> sink); // −1，到 0 回手
    public static bool TrySlow(CardInstance c, List<CooldownChange> sink);                     // +1，上限 = 基础冷却
    public static int  HasteZone(PlayerState p, int value, List<CooldownChange> sink);         // 返回改动张数
    public static int  SlowZone(PlayerState p, int value, List<CooldownChange> sink);
    public static bool ResetToBase(CardInstance c, List<CooldownChange> sink);                 // 寒流
    public static bool Refresh(PlayerState owner, CardInstance c, List<CooldownChange> sink);  // 立即冷却完成
    public static bool RemoveFromGame(PlayerState owner, CardInstance c);                      // 漩涡
    public static bool PutIntoCooldown(PlayerState owner, CardInstance c, int? overrideCd,
                                       List<CooldownChange> sink);
}
```

> **相对初版的两个签名改动**：
> 1. `TryHaste` 需要 `owner` —— 加速可能让牌归 0 回手，得知道把它放回**谁**的手牌。
> 2. `PutIntoCooldown` 需要 `owner` —— 初版漏了「把牌真正挂进 `CoolingZone` 列表」这一步，
>    导致所有依赖遍历冷却区的规则（进攻开始 −1、区域加减速、选目标、回手）全都作用在空列表上。
>    这个 bug 是靠 `--trace` 打事件流看出来的（`dotnet run -- 1 1 --trace`）。
>
> 接口一律用 `List<CooldownChange> sink` 收集改动，由引擎转成 `CooldownChangedEvent` 事件 ——
> 这样 M3 不用知道事件流的存在，M4 也拿得到结构化的每一步变化。

不变量：`1 ≤ RemainingCooldown ≤ Def.Cooldown`（在冷却区中的牌）；等于 0 时立即移除并回手。

`CooldownChange` 是 `struct { Card, From, To, ReturnedToHand, Reason }`；`Reason` 是给自测断言用的
（例如「进攻开始 −1」被用来反查规则 9 与推论 P2）。

### 表现层的只读快照（`Core/Battle/Snapshot.cs`）

铁律第 2 条「表现层不得反向调用引擎」的结构化落实：UI 拿到的**只有值类型快照**，
构造后不可变，拿不到任何写入口，也不可能顺手改坏对局状态。

| 快照 | 内容 | 谁消费 |
|---|---|---|
| `CardSnapshot` | 卡 ID / 卡名 / 有效力量 / 力量文本 / 基础与剩余冷却 / 光环指示物数与激活态 / 所在区域 | `CardView` |
| `PlayerSnapshot` | 座位 / 名字 / Hp / MaxHp / 手牌张数 / 未用光环总数 | `PlayerBarView` |
| `BattleSnapshot` | 回合数 / 进攻方 / 终局与胜者 / 是否连击追加 | M8 的舞台层 |
| `DecisionSnapshot` | 决策类型 / 提示文案 / 选项列表 / 上下文字段 | M8 的 `TargetPicker` |

> 附带好处：M7 的界面骨架可以**脱离规则内核**独立开发和验收（`UiKitPreview` 直接手搓快照铺样本）。

### 决策请求上的上下文字段

`DecisionRequest` 除了 `Options`，还带了几个上下文（给 UI 显示、给自测做独立校验）：

| 字段 | 含义 |
|---|---|
| `ContextPower` | 本次进攻的最终力量（防御决策时用，UI 可显示「需 ≥N」） |
| `ContextDouble` | 本次是否双发 |
| `ContextDefenseBonus` | 本次已主动消耗的防御力量加值，不包括未使用的指示物 |
| `ContextImmune` | 兼容旧字段；免疫直接成功，不产生防御选牌决策 |
| `ContextNoSkip` | 该决策不允许放弃（如「有牌时必须进攻」） |
| `ContextHaste` | 区域类极性：true = 加速，false = 减速 |

`Option` 上也带了 `Count`（区域类该档能影响几张牌），AI 用它判断「数值最集中的一档」。
